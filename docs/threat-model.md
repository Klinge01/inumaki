# inumaki threat model

What the engine, the service, and the MCP gateway protect, what they do not, and the rules that keep it that way. Milestone 3 state plus the milestone 4 gateway, the milestone 5 folder mirror, the milestone 6 harness adapters and tool-result hook, and, in the last section, the milestone 8 model-API proxy as built by plan M8-1 (non-streaming); Protected mode (a separate service user, custody of the source data) is milestone 7.

## What is protected

- **Identifiers in text that leaves the machine.** Names, addresses, emails, phone numbers, IBANs, cards, national and tax ids, plates, customer/contract/invoice ids, and secrets are detected by several independent detectors, replaced by opaque tokens, and the candidate is verified by a second pass (leak check, regex re-scan, independent NER re-scan, combination heuristic) before anything is sent. A failed verification retries with a stricter profile once, then blocks.
- **Originals at rest.** The vault stores originals encrypted (XChaCha20-Poly1305, fresh nonce per value, token as associated data) and indexes them by HMAC of the normalized value. A copy of `vault.sqlite` without the keys is useless; the keys are in the OS secret store or a 0600 key file the vault refuses to use when its permissions are wider.
- **Originals in memory.** Decrypted values live in `Zeroizing` buffers, in a bounded working set that is wiped on eviction, on rotation, and on drop. Session contexts are wiped when their TTL ends.
- **Logs, errors, metrics.** No log line, error message, `Debug` output, API error body, or panic message carries text, tokens, or entity values; only ids, counts, kinds, check ids, timings, route templates (`/v1/datasets/{id}`, or the constant `unmatched` for a path that matched no route), and opaque HMAC dataset ids (`Vault::opaque_id`) — never a raw path, a query string, or a user-chosen dataset slug. A canary test runs the whole daemon at `TRACE` and asserts it. Panic messages come from `expect`/`assert` strings that carry no values, and Rust backtraces print frames, never locals. One exception: when `inumakid` fails to start or stops with an error, it logs the start error's text, which can name the service's own files (the socket, the data directory, the config file) and so the user's home directory. It is the operator's only diagnostic for a failed start; no request text, token, or dataset name is in it.
- **The sanitization cache does not freeze a stale verdict.** A namespace's knowledge grows with every mint, so a `Pass` cached while a name was unknown would, without a check, still be served in clear once that name had since been minted from another document. On every hit the daemon re-runs the namespace's known-entity detector over the cached text and drops the entry on any hit outside its own tokens (a cache miss, processed fresh) (final review I2). Since the L3 engine follow-up (Task 7c) the re-check also runs the forms the engine's consistency pass searches (`StoreDict`: the working set's full values, PERSON name parts, transliterated and folded forms, removed values, every kind), so a block cached with a bare first name in clear is processed fresh once the full name has been minted; a dictionary build error fails the re-check. Measured on the via-daemon bench at the time: about one cached document in five would otherwise have been replayed with a clear copy of a store value.
- **A retry profile cannot silently defeat a `Block`.** `Engine::from_config` rejects a `verifier.retry_profile` that does not keep every entity kind the primary profile blocks (explicit overrides and the `default_action`) as `Block` too, so a document a profile is configured to refuse can no longer be retried into a profile that tokenizes it instead (engine spec §6.3/§6.6, final review I4).

## What is not protected

- **A process running as the same user.** The control socket is protected by its file mode only. Anything running as you can call `sanitize` and `rehydrate`, read the vault file, and (with the key file source) read the key file. Protected mode is milestone 7.
- **Semantics.** inumaki removes what enables identification, not every fact. "My daughter had an accident" is sent as is; the provider learns the story, not who it is about. Public figures, small-population combinations, and side channels through the response content remain (the combination heuristic is a crude placeholder).
- **Linkability within an epoch.** Within a dataset and epoch the same entity keeps the same token, so the provider can link requests about the same person from the same dataset. That is the price of consistent mirrored files and long agent tasks; rotation (default 30 days) bounds it, and the grace period (default 7 days) keeps old outputs rehydratable.
- **The automaton's memory.** The known-entity detector and the verifier's leak check build Aho-Corasick automata from decrypted originals; an automaton's internal pattern bytes cannot be zeroized. They are dropped on rotation and at namespace close. The store-owned leak index (roadmap 4d) lives as long as the store's cached consistency dictionary (see the next item and (n)); a per-call build (a store that keeps no index, a failed index build, or a stale index) is dropped after its check.
- **The consistency dictionary keeps forms of evicted values.** A namespace's cached consistency dictionary (`TokenStore::store_dict`, Task 7e) keeps an LRU-evicted working-set value's forms (never matched) until `churn_limit` writes (256 to 1 024) force a full rebuild or the handle drops; an entry of a closed epoch, which expires, is cleared from it at eviction. The cache's leak index (roadmap 4d, Phase B) holds the same values' leak patterns and shares exactly that lifetime: the same cache holds them, the same writes drop them (now at the write that passes `churn_limit`, not at the next read), and a closed-epoch eviction clears them with the rest. The cache's middle tier, added so that a growing store stops paying a full rebuild, holds `Zeroizing` copies of its values under the same rule, and an eviction of a middle-tier value drops that tier's dictionary and leak layers.
- **Model recall.** Statistical detection misses things. The measured recall per kind and the leak rate are in the engine spec §12 and `docs/quality/2026-10-09-4a-summary.md`; the `support-email` verifier's token classifier catches missed names, not missed street addresses (the `thorough` profile does).
- **The link between surface forms.** A derived token tells the provider that `<PERSON_a7f2c9_3e>` and `<PERSON_a7f2c9>` are one person (and, since the two-character component is random, nothing about how many spellings it has seen); the original text said so too. `[tokens] surface_form = "independent"` hides the link at the cost of coreference for the model.
- **Identifiers wrapped across lines, known limits.** Card numbers and IBANs split by a line break are found (plan 4a), with documented gaps: a phone number on a line followed by a line of digits can lose its phone match; an IBAN with a blank line between its groups is not joined; an IPv4 address directly after a glued run of digit groups can be covered by a card window that passes the Luhn check by chance; and on numeric tables card-window matches rise by design (1 183 → 9 039 matches over 3 000 random tables), which over-redacts but never leaks. Source: the known-limitations note in `docs/quality/README.md` (section 4a-task4).
- **Keyring semantics.** On macOS an unsigned development build prompts for Keychain access after every rebuild; on Linux without a Secret Service the key file is used and a warning is logged once. `[vault] key_source = "file"` makes the choice explicit.

## Bare first names and surnames

*Resolved in plan 4a (2026-10-09); this section replaces "A known behaviour of dataset mode: first-name leak blocks".* Milestone 3 left a bare first name (`LG Sarah`) in clear unless the model tagged it, and a dataset's leak check then blocked the document whenever an earlier, unrelated "Sarah" had been minted into the namespace. Now a name linker runs after detection (engine spec §6.4, M4 spec §16.2). A bare first name or surname that is found (by the model, by the anchor detector after a greeting, sign-off, or honorific, or as a part of a full name or e-mail address in scope) is tokenized either way: as a surface token of the one person in the document or the batch who has that name part, or as its own entity when two people in scope share it or nobody in scope has it. Across requests (the dataset's recent entries) it links only with `[linking] surnames_across_requests` or `first_names_across_requests`, both off by default. The leak check therefore no longer blocks on a bare name the linker tokenized. Measured on the engine path (`docs/quality/2026-10-09-4a-summary.md`): `support-email` block rate 23.3 % → 16.6 % on the tuning corpus and 32.0 % → 23.0 % held-out. A dataset that has accumulated many identities still blocks far more than a fresh context: one persistent dataset over the whole tuning corpus blocks 53 % (`--via-service`), and the persistent-dataset sequences 14.7 %.

**A wrong link.** If a bare name is linked to the wrong person, the model treats two people as one: it sees `<PERSON_a7f2c9_3e>` and may reason about the earlier `<PERSON_a7f2c9>`. Rehydration still returns the mention's own text, so no wrong name is written back. Inside one document or batch a link needs exactly one candidate. The labeled linking and sequence cases measure zero wrong links, but the generated corpora measure one wrong link per corpus (`links.wrong_links` = 1 on the tuning and on the held-out corpus, both profiles; wrong restorations 0): one generated document per corpus (`support-email` and `strict` alike): the sender signs with a bare first name, and the quoted header of an earlier message names a *different* generated person who has the same first name and is the only full name in the text. The document tier links the sign-off to that full name; the text alone cannot tell the two apart, while the gold labels say they are two people. This is the single-candidate case inside one document, not a defect in the rule; it is carried to plan 4c. Across requests a single stale candidate is the common case. With the opt-in flags the sequence corpus measures every such link wrong: `SurnameRecentOther` 4 of 4 links with `surnames_across_requests`, `BareRecentOther` 21 of 21 with `first_names_across_requests`, both profiles. The window (`[linking] window_minutes`, default 30) bounds how stale a candidate can be. That is why both flags are off.

**Own-entity bare names.** A one-word PERSON entry (a bare name that got its own entity) is stored and restores like any other token, but it never enters the known-entity automaton or the clear-value tripwire, because one word matches too much ordinary text. For the same reason a lone given name that reached the dataset through an identifier field is not a tripwire hit when the model later writes it in clear; it was still tokenized at the source.

**A bare name part before its full name in one batch.** *Rewritten 2026-10-10 (L3 engine follow-up, Task 7c); updated 2026-10-11 (Task 7e).* At the end of a batch of two or more blocks that changed the store (its epoch, or the per-process keyed fingerprint of its working set and removed values, differs from the start of the batch), every non-blocked block is scanned for a clear store form outside its tokens and protected ranges: full values, PERSON name parts, transliterated and folded forms, and removed values, of every kind, preserved kinds included, as far as they are in the namespace's working set. The scan uses the namespace's own cached dictionary (`TokenStore::store_dict`), the one the engine's passes and the cache-hit re-check share. An offender is sanitized once more with the batch's scope (a cache hit among them is dropped from the cache); a block that still holds a clear store form, or cannot be checked, is withheld. What is guaranteed: for a batch of two or more blocks, no released block holds, outside its tokens and protected ranges, a clear copy of a form of a working-set value, so a bare first name or surname that detection missed in an earlier block is tokenized, or the block is withheld, when a later block in the same batch mints the full name. Two residuals. (1) Forms of values outside the working set (at most 4 096 entries; a new handle, such as after a daemon restart, starts empty; full known entities are still caught by the known-entity check). (2) A single-block batch is not scanned at its end, so one in which the engine's own second sanitize mints a new multi-part name whose part sits in clear in the same text is not covered. That case was not reproduced (300 documents, six constructed cases) and is re-checked only when the block is next served from the cache.

**Caching.** A block whose links used the batch or the recency window is never cached. A block whose bare name became its own entity can be: a later request that sends the same text with more context in its batch gets the cached result, without the coreference hint the batch would have given (the name is still tokenized).

## Engine follow-up residuals (L3, 2026-10-10)

The L3 engine follow-up (`docs/quality/2026-10-09-l3-engine-proxy.md`, engine spec §6.1 to §6.6) leaves these, each recorded rather than fixed:

- **Shared normalizers.** The sanitizer's consistency pass and the verifier's leak check share their forms and the normalizers `transliterate` and `fold_diacritics`. A bug in those functions would blind both together for the folded spellings. The leak check therefore keeps exact NFC legs for full values and for PERSON name parts, pinned by a test that holds with both normalizers replaced by the identity, so a folding bug alone cannot blind it for the spelling the store holds.
- **Word-list blind spots.** The salutation list holds words that are also rare surnames (`Lieber`, `Liebe`, `Hey`, `Damen`, `Moin`, `Dear`). The verifier ignores such a word as a PERSON hit next to a token, and the sanitizer drops a one-word line piece made of it, so such a surname written alone next to a token, or on its own line inside a model span, passes both. The verifier's role and label list keeps `tel`, `phone`, and `web`, which are plausible names too, with the same effect next to a token. `sie` and `or` are common words, so the surnames Xie and Or are not name candidates for the anchor, the linker, the retry guard, or the leak check's name parts.
- **The retry guard's reach.** A guarded multi-line uncertain name (engine spec §6.3) escalates only when a name candidate abuts it. A surname on a later line that is not adjacent to the span, or that follows terminal punctuation such as `Name,`, is caught only by the leak check (when it is a stored name part) and the verifier's NER re-scan.
- **Order-number lists.** A line that opens with a four- or five-digit number and a surname (`NNNN Surname`, as in an order list) is read as a postal code and a town. If the sanitizer's NER misses the surname, it becomes a CITY span, which `support-email` preserves, and the verifier's postal-code-plus-town rule ignores a PERSON hit over it, because that rule trusts the regex town (a model, dictionary, or store CITY there does not qualify). The surname then passes. Under `strict`, which tokenizes CITY, it is tokenized.
- **Demoted dictionary fragments.** A known-entity fragment inside a longer same-kind span is ranked right after its container (engine spec §6.2). It can lose to a span of another kind ranked between its own slot and the container's, which leaves the fragment's text uncovered; a rare partial overlap.
- **Template-word false positives.** Two ordinary German words from the synthetic mail templates are tagged PERSON or STREET_ADDRESS by the sanitizer's NER and minted. They cost precision and, in the proxy, a closure re-run per later turn (of every cached leaf that holds the word), not privacy; carried to the next plan ("harness-static precision").
- **Store pollution.** A word the `strict` retry minted (a single-word greeting such as `Madam` or `Hallo`, an ORGANIZATION `Support`) stays a store value: the consistency pass tokenizes its later copies in the context, or in the dataset for the epoch. This costs meaning, not privacy; keeping such words out of a dataset is a plan 4c item.
- **Cache and an evicted working set.** The cache-hit re-check covers the forms of values in the namespace's working set. The sanitize cache is an in-memory LRU that a daemon restart empties, so a restart is not the gap; the gap is a value that has left the working set (it holds 4 096 entries and evicts the least recently used) or a namespace handle that was closed and reopened while the cache kept its entries. Until that value is loaded again, a cached block's clear copy of it is re-checked only against the full known entities.
- **Harness static text.** The built-in instructions of some harnesses (Codex) hold words the sanitizer's NER scores as uncertain PERSON spans, which refuses the request under `support-email`. Diagnosed in lane L5; addressed by the "harness-static precision" plan (ruling L60), whose residuals are in the next section. The proxy tells the engine which text is the leading system prompt of a trusted request, within the bounds in (dd) of the M8 section below; every other proxy leaf is still free text.

## Harness-static precision residuals (L3, 2026-10-12)

The harness-static precision plan (engine spec §6.1, §6.3, §6.5, §11; measured in `docs/quality/2026-10-12-harness-static-precision.md`) makes the sanitizer drop model-found `PERSON` spans that are technical text, and gives the verifier one narrow product-name rule for system-prompt text. On the 93-document harness corpus that took `PERSON` spans from 1004 to 25 and refused documents from 7 to 0 under `support-email` (1 to 0 under `strict`), read as harness-static text, with no leak count raised and no `PERSON` recall lost in any eval. Every recall eval runs as free text: recall on harness-static text is unmeasured (the harness corpus holds no names, so it measures precision only), and the chance coverage of a whole lowercase path or URL span that the model tagged is lost, which no eval corpus can show because none holds such a name (below). It leaves these, each recorded rather than fixed:

- **Names and identifiers in structured positions** (integrator rulings L71, L78). *Updated 2026-10-20 (structured positions; the full list is the next section).* When this plan was written nothing looked at name-shaped path, URL, or column pieces: `/home/huber/`, `C:\Users\mhuber\…`, and `https://…/team/gruber` leaked in 3 documents under `support-email`, and the precision rule below removes the model's chance coverage of a whole lowercase path or URL span. Paths and URLs are now covered by a deterministic detector of positional cues (`DetectorId::Position`: the login after a home root, the segment after a person cue such as `/team/`, a code-host account, `~login`, Claude Code's flattened project directories, a first name plus a name part), in every profile and both origins, and a home-folder login left in clear fails the verifier's own check. What the precision rule still does: a model span over the name piece alone (`huber` in `/home/huber/`) is kept, and so are capitalized segments (`Huber.txt`, `C:\Users\Huber\notes.txt`, `@Leitner85`). An `@` handle or a `\` path is kept while it is no machine word (`@leitner`, `C:\Users\mhuber\`). With a digit, a `_`, a `#` glued before a letter or digit, a listed file extension, or an inner capital in the token it is one, and it is dropped when no name part keeps it (`@leitner85`, `@leitner#2`), like a model span over a whole lowercase path or URL; the positional detector then covers the name piece when its position has a cue (`/home/huber/`, `C:\Users\mhuber\notes.txt`, `https://…/team/gruber`), and nothing covers it when it has none (`/projekte/huber/plan.txt`, a lowercase handle with digits). An inner capital is origin-aware (ruling L118): in free text a capitalized CamelCase part that is no vocabulary word keeps the token (`@leitnerHuber`); in harness-static text it does not. Names in table columns (`Branch` as the first column of a CSV row under `Nachname`) are still detected by nothing but the model; that part was deferred (next section, Phase 2).
- **Business numbers the regexes miss** (lowercase licence plates, typo'd invoice and customer labels) are sometimes covered only by the model's `PERSON` tag. The precision rule keeps a word shaped like a business number for that reason (rulings L85, L88), so this is not a new loss, but a regex fix would be the better cover. The structured-positions plan deferred it to its Phase 2 (next section), so it is still model-only.
- **Identifier-shaped names the model alone finds are dropped** when no name part keeps them, in free text as in harness-static text: `leitner85`, `huber_maier` (lowercase, no capitalized segment), a lowercase surname inside a span with code syntax (`a3f9c12 fix invoice for huber`), and a code file named after a Census-surname vocabulary word (`Model.json`; a document extension keeps it: `Model.txt`, `Rechnung_Branch_2026.pdf`, ruling L3-09). Reason: identifier shapes (hashes, UUIDs, paths, tool and model names) made most of the harness corpus's false spans (1004 → 686 after this step alone), and a name glued to digits or underscores without a capital is rare in business mail. A capitalized surname glued to digits, a `#`, or a key is kept in both origins (`Huber85`, `Leitner2026`, `Huber#2`, `nachname=Huber`; final review A1). A surname glued in CamelCase under a model span over the whole token (`HuberMaier`, `GruberAG`) is kept in free text and dropped only in harness-static text, unless a part is a first name (`MaxHuber` is kept in both; ruling L118). In free text that costs precision: the harness corpus read as free text keeps 10 more spans (`$SkillName` 6, `TodoWrite` 2, a git-log line with `localStorage` and its hash 2). The dictionary and known-entity detectors and the verifier's NER re-scan are not filtered; the verifier is the backstop, but it is a model too and may not tag such a shape either.
- **Lowercase vocabulary words that are surnames, standing alone** (`fish`, `rust`, `main`, `head`, `brief`, and the lowercase `ALSO_NAMES` word `page`; rulings L98, R16, R17). In free text (user messages, tool results, mail, files, and every caller that passes no origin) they stay `PERSON` spans and are tokenized (`danke rust`), unless they stand between backticks or carry other evidence in the span. In a harness-static text, and inside an identifier anywhere, they are dropped when the model tags them below 0.85. A lowercase name of that shape in a system prompt is therefore lost to the sanitizer, and the verifier's NER is the backstop. Measured: as free text the harness corpus keeps 41 more spans than as harness-static text (per-word list in the quality report; tokenized, never sent in clear). No recall eval runs as harness-static text, so what this drop costs there is unmeasured.
- **`Claude` with a product cue is the product for the sanitizer** (ruling C3), even where it names a person. The cue is text-wide: when `Anthropic` or `Claude Code` appears anywhere in the text, a standalone `Claude`, a sign-off included, is dropped as the product. Without a cue `Claude` is a first name and is tokenized.
- **A person named exactly like a product, in a harness-static text, is not flagged by the verifier** (rulings L78, L103, L107, L111). The verifier does not fail on a `PERSON` hit that is exactly `Claude`, `Codex`, `Opus`, `Sonnet`, or `Haiku` as a whole word when the caller marks the text harness-static. Example: a system prompt that thanks a real person, `Thanks, Claude`, when the model's hit is the bare name (a hit `Thanks, Claude` as one span still fails). The sanitizer's C3 rule is then the other line: without a product cue in that text it keeps `Claude` and tokenizes it; with one (a Claude Code system prompt names `Anthropic`) neither line flags it. The leak check still refuses `Claude` when it is a stored value of the context. Two boundary effects: the guard that keeps a hit next to a placeholder (`Claude <PERSON_…>` fails) does not reach past two line breaks, as in the salutation filter; and `.` is not a word character, so the `Claude` in `Claude.ai` still counts as a whole word. In free text the verifier is unchanged. Measured: 2 verifier hits discarded under `support-email` and 1 under `strict`, all in one harness-corpus document; 0 in every free-text eval, whose results are byte-identical with and without the rule.
- **The proxy passes the origin for the leading system prompt of a trusted request only** (rulings L3-14, L107, L3-18, L120, L122; M8 spec §20, amendment of 2026-10-20; the bounds and residuals are in (dd) of the M8 section below). Every other proxy leaf runs as free text: user turns, tool results, tool inputs, assistant text, system or developer items after the leading run, and every leaf of a restricted request (a client without the header). A restricted request gets the free-text reading on the harness corpus: 76 `PERSON` spans instead of 25 (tokenized, never sent in clear) and 1 refused document, a Claude Code-shaped system prompt refused because the verifier reads `Claude` as a person. Harness text that arrives in user turns (Claude Code `<system-reminder>` blocks, Codex `<environment_context>` and `AGENTS.md` messages) stays free text, because the proxy knows only that they are user turns; the 16-document corpus subset that stands for them yields no span and no refusal under either origin. `Engine::project`, which re-checks a cached proxy leaf, takes no origin; it runs no NER re-scan and no sanitizer detector, so the origin cannot change its result (design decision D-6 in the M8 spec amendment of 2026-10-20).
- **The vocabulary is curated from the measured corpus.** Words that a new harness release adds may be tagged until the corpus is refreshed (`scripts/harness-corpus/build.sh`). The Claude Code texts in the corpus are synthetic, written for inumaki in the shape of a Claude Code system prompt. The integrator's re-test with the real Claude Code and Codex after the merge is the real check.
- **25 `PERSON` spans remain on the harness corpus**, listed per word in `crates/inumaki-eval/targets/harness-static.toml`: 22 spans of 11 Census-surname or `ALSO_NAMES` words standing alone (for example `Yes`, `Bash`, `Sender`) and 3 identifier keeps that hold a first name (`NotebookEdit`, `edit_mode`, `line_range`). Reason: the 22 are real surnames, and a drop rule for them would also drop `Herr Model` (ruling L3-06). Under `block` none of them refuses in the corpus: each is tokenized, directly or by the `strict` retry. Under `tokenize` each becomes a token without the retry. Either way the cost is meaning (a token in place of a word), not a leak.
- **`on_uncertain = "tokenize"` costs recall on mail and is not shipped.** Wherever it is enabled, a policy escalation of a `tokenize` or `preserve` kind is tokenized in the pass that settles the text instead of sending it to the `strict` retry. Measured: it removed no refusal in any gate, and it let 2 more tuning documents leak under `support-email` (11 → 13), because they settle at `support-email` instead of the retry, whose `DATE` and `ORGANIZATION` tokenization covered a birth date and two mislabelled names. A verifier `Fail` or `Uncertain` still refuses; a band span of a `block` kind still refuses and one of a `remove` kind is removed (ruling L3-13); and a merged span that absorbed an escalation keeps it over `Remove` (ruling L106). Band values it mints stay in the store: 48 distinct values over a shared dataset on the harness corpus, which the referential-consistency pass then tokenizes in every later request of that dataset (`block` mints more there, through the retry).
- **The verifier's NER refuses capitalized common words** (ruling L78, a plan 4c calibration item, not changed here). On the proxy bench with noise transforms (signature and quote blocks, typos, wrapping), 25 of 51 turns are refused on a verifier `PERSON` hit over a capitalized five-letter common word that is not a name, before and after this plan. The `thorough` profile's GLiNER verifier yields 3 810 `PERSON` hits on the harness corpus. Both cost availability, not privacy.
- **An all-letter label value is no longer detected by the label rule.** The shipped `CUSTOMER_ID`, `CONTRACT_ID`, and `INVOICE_ID` label rules take only a value with a digit (`require_digit`), so `Kundennummer: ABCDEFGH` is not tokenized by them. Reason: the rule took `EULA` after `contract` as a contract id. Such a value is caught only if the model or a dictionary finds it.
- **The Claude Code `CONTRACT_ID/Regex` refusal** measured through the proxy on 2026-10-11 is still a hypothesis (ruling R7): probably conversation content shaped like a customer id, kept by design. The re-test records its shape.
- **Values minted into a dataset or session before this change** (`user` or `Codex` as `PERSON`) keep being tokenized by the referential-consistency pass until the dataset rotates or the value is forgotten.

## Structured-position residuals (L3, 2026-10-20)

The structured-positions plan (engine spec §6.1, §6.2, §6.5, §11; M5 spec §4.3; measured in `docs/quality/2026-10-20-structured-positions.md`) covers three gaps. (1) The folder mirror renamed ordinary files into person tokens (`mail-anfrage.txt`, B6); a document vocabulary, file positions (`TextOrigin::FileName`, passed by the mirror's name sanitizer only) and a date-aware detection spelling fix that, and on 107 ordinary stems `PERSON` detections fell from 38 to 7. (2) Names in paths and URLs are read from their position by a deterministic sanitizer detector (`DetectorId::Position`) in every profile and both origins. (3) A home-folder login left in clear fails the verifier's own check (ruling L127). Measured on the 21 new recall cases: `support-email` and `strict` pass all 21 (14 and 18 before), `offline` passes 17 (0 before). On the tuning set extended by those cases, leaking documents went from 18 to 11 under `support-email`, 7 to 4 under `strict`, 437 to 419 under `offline`, and stayed at 0 under `thorough`, with no case worse in any profile. Names in table columns, person labels, and the business numbers the regexes miss were deferred (Phase 2, below). It leaves these, each recorded rather than fixed:

- **A lone surname in a file name, under `offline`** (rulings S8, S26, L127). Four of the new cases still leak there: `shape-fname-surname-capital` (`Rechnung_Huber_2026`), `shape-fname-surname-bare` (`Huber`), `shape-fname-surname-lower` (`huber`), `shape-fname-surname-lower-word` (`leitner-angebot`). Reason: `offline` has no NER, and there is no surname list at runtime (a Census list is large, US-centric, and would make every rare-surname word a name). A first name next to the surname is enough (`anna-gruber-cv`, `CV_Anna_Gruber`, `gruber_anna` are tokenized under `offline`). Under `support-email`, `strict`, and `thorough` the model tags all four.
- **A rare-surname document word in a file position** (rulings S3, L123, L129). A document word that is a rare Census surname (1–999 bearers: `mail`, `foto`, `steuer`, `preis`) is read as a document word in a token with an extension or a path separator, and in every word of a mirrored file or directory name. A person with such a surname, written alone in a file name (`Steuer.pdf`) or next to a document word (`Bewerbung Steuer`), without a first name or honorific, is dropped by the sanitizer when the model tags it below 0.85; the verifier's NER re-scan is the backstop. In prose, JSON values, and one-field records nothing changed (`Herr Mail`, `{"nachname":"Steuer"}` stay `PERSON`).
- **Document words next to unknown or short words** (rulings L139, L140, L141). A document word makes a model `PERSON` span technical only when every other letter run of its token is vocabulary (cut at inner capitals except in harness-static text), so `Bewerbung_mueller.pdf` or `Rechnung Li` keeps its span. Two consequences are recorded: an identifier with a lowercase unknown run next to a document word (`FolderInfo.outbox_destination`) also keeps the span, which costs precision in code text and can block it under `support-email`; and a lowercase `_` token with a two-letter surname and no capital (`bewerbung_ng`) takes the machine-word path, where a whole-token model span is dropped as on `e041659` (no detector tags it today, so nothing changed).
- **A name in a path with no positional cue** (rulings S8, S12). `/projekte/huber/plan.txt` has no home root, person cue, code host, `~`, or first name, so no deterministic detector reads `huber`, and the verifier has no check for it. Only the model can tag it; a capitalized segment the model tags (`/Projekte/Huber/`) is kept, a lowercase one inside a whole-path model span is dropped by the precision rule.
- **A `Position` name inside a longer preserved span** (engine spec §6.2, final fix wave). The `URL` cut keeps a containing URL from evicting a path or URL name, but only a `URL` is cut: a higher-priority span, or a longer span of the same priority, still wins the overlap. A preserved model `ORGANIZATION` of confidence 0.70 or more over the path or URL (profiles built on `offline`'s preserve list) is such a span, and the name under it is then released in clear.
- **Multi-part and multi-word logins.** `weber.koch` (two name-like surnames, no first name, no initial) is a name only after a home root, where every non-generic login is tokenized. After a person cue only `weber` is tokenized and `.koch` is read as a file extension (`https://example.com/team/weber.koch`); as a code-host account neither part is (`github.com/weber.koch/tool`); measured under `offline`, so only the model covers them. A three-word Windows login (`C:\Users\Anna Maria Gruber\`) tokenizes only `Anna`: the detector takes at most one more space-separated word, and only when a `\` or `/` follows it directly. `Maria Gruber` stays in clear under `offline`, and the verifier does not refuse it, because its login ends at the space.
- **What the home-folder login check does not cover** (rulings L127, L134, L135, L136). Its roots are `/home/`, `/homes/`, `/Users/` (exact case), a drive plus `Users` (`C:\Users\`, any case), and `~` in a path or in a login context. Not roots: UNC shares (`\\server\Users\mhuber\`, `\\server\home$\mhuber\`) and Claude Code's flattened project directories (`-Users-mhuber-app`), which the sanitizer tokenizes but the verifier does not check, so a sanitizer miss there has no deterministic second line. A slashless `~login` followed by a word (`frag ~mhuber dazu`), after an operator, or in capitals is neither tokenized nor refused (ruling L3-30: `~` before a word marks an approximation, `~zwei Stunden`); the model is the only line. A URL nested in a URL-encoded query (`?next=https%3A%2F%2Fgithub.com%2Fmhuber`) is not decoded, so its account is not read. A real login equal to a generic account (`/Users/admin/`) passes both lines. A slashless `~login` that starts with a non-ASCII letter (`~müller`) is read by neither side: both read a slashless word as ASCII letters, digits, `.`, `_` and `-` only.
- **Generic accounts and their drift** (rulings S11, L124, L131). `GENERIC_ACCOUNTS` (63 words in `inumaki-core`) is never a name: besides service and CI accounts (`runner`, `deploy`, `ubuntu`, `linuxbrew`) it holds `travis`, `jenkins`, and `guest`, so a person whose login is exactly one of them is not tokenized; route words (`about`, `search`, `jobs`, …) are never a name after a person cue or on a code host. The proxy's identity seeding (`crates/inumakid/src/identity.rs`) keeps its own, smaller `GENERIC_LOGINS` list, so the two decide some logins differently: the seeding can mint a login (`deploy`) that the detector calls generic, never the reverse. Follow-up after both lanes merge: `identity.rs` reads the core list, with an agreement test.
- **Very long pieces** (rulings L133, L135). The detector cuts a whitespace token at JSON and markup punctuation (`" , { } [ ] ' < > ( )`) and skips a piece longer than 4 096 bytes whole, so a long `PATH=` line joined only by `:` or `;` is not read for names. The verifier's home-login check still reads such a piece and refuses a clear home-folder login in it (fail closed); a name after another cue there is left to the model.
- **Precision costs** (rulings S13, L3-28, L3-29, L135, L136). These cost meaning (a token in place of a word), never a leak, and none of them refuses: 0 home-login refusals over 181 code documents and 359 4 KiB repository chunks that hold a root or `~`, and 0 on the harness corpus. An organization account on a code host becomes a `PERSON` token (`github.com/openai`); a directory after a person cue does too (`src/user/model.rs`); every non-generic segment after a home root is tokenized, including `/home/about`, one- and two-letter logins (`/home/kl/`), a rare document word (`/home/foto/`), and a home-root shape inside a URL path; `x=~mask/2` in code becomes `x=~<PERSON_…>/2`; a `~word` in a login context in prose is tokenized. Under `thorough` its verifier blocks 11 of the 21 new cases (12 before the plan), an availability cost of that profile.
- **Glued camera counters** (ruling L3-27). A counter of 1–3 capitals and 5 or more digits (`DSC01234`) is no longer a model `PERSON` in a file name, but the verifier's bare-identifier check then withholds the name, so the mirror gives that file its opaque name. Fail closed, nothing leaks.
- **Year linking across file names** (ruling L130). When the model tags a whole stem such as `Rechnung Huber 2026` as one `PERSON`, the name linker can link a bare `2026` in later stems of the same batch to it and tokenize the year. Precision only; follow-up: the linker never links a digit-only name part.
- **Names in mirrored CSV, and long tables** (rulings S15, L123, L124). The mirror sanitizes a CSV file one record per block, so the engine never sees the header row next to its values, and the mirror and the service cut text files into 4 KiB chunks, so a long Markdown table can lose its header in every chunk after the first. Name columns there rely on the model and the verifier until `MirrorEngine` carries per-record column hints.
- **Phase 2, deferred** (ruling L128; design §9). Still model-only: names in table columns and after person labels (`Branch` under `Nachname` or `Name` leaked under `support-email` when measured before the plan), lowercase licence plates (`w-9666c`), typo'd labels (`Kudnennummer`), labels glued to their value (`Kundennummer_123456`), and long-prefix numbers (`bestellnummer-2026-4711`, released in clear under `support-email` when measured). Under `offline` all 13 such cases leak. They live in `crates/inumaki-eval/cases/structured_positions_phase2.toml`, which is not registered in any gate yet.
- **Origins.** `TextOrigin::FileName` is passed only by the mirror's name sanitizer (`inumakid::service::sanitize_names`); the proxy never produces it and needed no change (its leaf origin falls back to free text, and its static-prompt memo serves `HarnessStatic` leaves only).

## Rules enforced by construction and by test

- `Span`, `Context`, `Namespace`, `Sanitized`, request and response types: hand-written `Debug` with counts, ids, and flags — never an original value or a user-chosen dataset slug (`Namespace`'s `dataset` field is the opaque id, not `dataset_id` itself); no `Display` for anything that could hold text.
- Core and vault errors carry ids, key paths, paths, and SQLite messages, never values or normalized keys.
- Workspace lints deny `dbg!`, `print!`, and `eprint!` outside the CLI and the daemon binary.
- Tests: `logs_and_error_bodies_never_contain_request_text` (daemon at `TRACE`), `hmac_index_never_stores_normkey_or_original` (raw vault bytes), `dataset_name_is_encrypted_at_rest`, `key_file_with_loose_permissions_is_refused`, `debug_*` tests on every store, `edited_journal_rows_fail_to_open`, `journal_and_entity_endpoints_never_log_values`, `forget_evicts_cache_working_set_and_detector`, `variant_in_two_groups_is_a_config_error`.
- Surface rows (other spellings, bare parts, alias variants) are never in the known-entity automaton or the tripwire; `token::parse_token` is the only token parser, shared by the rehydrator, the verifier's suffix masking, and the gateway's unresolved-token check; gazetteer hits and name parts never reach logs, errors, or `Debug` output.
- Fail closed: no vault, no models, no answer. A profile whose model is missing is unavailable (`503`), never served regex-only; a detector error blocks; a storage fault discards the request's text.

## Gateway (milestone 4)

**Scope.** The gateway protects only traffic that goes through it: an agent's calls to a dataset's `/mcp/<dataset>` endpoint (TCP or control socket) and the results that come back. Direct chat with the model, other connectors, files the agent reads itself, another process running as the same user, and re-identification from what the sanitized text still says are outside this boundary. A `Pass` means the configured checks passed; it is not proof that a result contains no identifying information. No profile is yet qualified against the M4 quality gates, and `inumaki doctor` says so.

**Mappings are persistent.** Milestone 1 kept every mapping in memory. Dataset mappings now live in the encrypted vault until their epoch's grace period ends; only session contexts are memory-only. A copy of `vault.sqlite` together with its keys restores every token of every kept epoch.

**Rehydrated arguments leave the boundary on purpose.** A tool argument that arrives as `<PERSON_a7f2c9>` goes to the wrapped server as the real name. That is the point of the gateway: the wrapped server is local business software inside the boundary, and the cloud model only ever sees the token. Whatever the wrapped server does with the value (store it, send it to its own backend, write it to its logs) is outside inumaki's control, so wrap only servers you would give the real data to anyway. Errors after an upstream side effect do not roll anything back.

**HTTP upstreams and proxies.** The HTTP client used for `--http` upstreams honours `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` from the daemon's environment. With a proxy configured, rehydrated arguments to an `http://` upstream pass through it in clear. Set `NO_PROXY` for local upstreams or start the daemon without proxy variables.

**Child processes.** A stdio upstream starts from a cleared environment: it gets `PATH`, `HOME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL`, and `XDG_RUNTIME_DIR` from the daemon, then its configured `--env` values and secrets. Other variables in the daemon's environment (API keys, tokens, proxy and CA settings) do not reach it; an upstream that needs one gets it through `--env` or `--secret-env`. Its stderr is read and discarded, because it may carry the real data the server handles; `status` shows only a byte count and the exit status class. A user debugging a wrapped server runs it outside inumaki.

**Credential custody.** Secret environment variables and headers for wrapped servers are sealed in the vault's `secrets` table (AAD `secret:<name>`), collected through no-echo prompts or a 0600 file, never from the command line, and merged into the child's environment or the HTTP headers only when the upstream starts. Status and API responses show secret names, never values. The daemon does not write harness configuration; the bearer token in a harness's MCP configuration is the user's to protect. Since milestone 6, `inumaki connect` (and the app) writes those files on the user's request; see "Harness connection and the tool-result hook" below.

**Bearer tokens.** A gateway token authorizes any local process that presents it on the loopback listener, for every dataset. The vault stores only `HMAC(index_key, "gw-token:" ‖ token)`, domain-separated from the entry index; the token is shown once at creation. Every request is checked, with a constant-time comparison, so a revoked token stops working on the next request even inside an existing MCP session. A stream that is already open is not a new request: a held `subscriptions/listen` stream (2026-07-28 clients) of a revoked token keeps receiving list-changed notifications until the client disconnects, as the legacy session SSE stream does. Those notifications carry no content (no item, name, or dataset text), only the fact that a catalog changed. The control socket carries no token check: its file mode (0600) is the authorization, as in milestone 3.

**Browsers.** A web page the user visits can send requests to `127.0.0.1`. A guard in front of authentication refuses any request whose `Origin` is not in `[gateway] allowed_origins` (empty by default) and any `Host` other than `localhost`, `127.0.0.1`, `[::1]`, `inumakid`, or the configured listen address (each with no port or the bound port), with a fixed `403`; `Upgrade` gets `501`; no CORS header is ever sent. This defends against cross-site requests and DNS rebinding. Bearer tokens remain the authorization: the guard only keeps browsers from reaching the authorization check at all.

**MCP sessions carry no privacy state.** Every token comes from the dataset's namespace, so two MCP sessions on the same dataset see the same token for the same person, and ending a session loses nothing. Linkability across sessions is the dataset's, bounded by rotation.

**Field coverage is by contract.** Text content items are always sanitized. Structured content is transformed only where a locally reviewed contract says what each field is; anything else, and any binary content, is rejected with `unsupported_content`. Upstream annotations never authorize preservation. Descriptions, titles, examples, and defaults are sanitized on every listing, and a blocked one fails the whole listing. Listing prose (tool, prompt, and template descriptions and titles, schema prose, examples, defaults, enum values, patterns) is sanitized under the dataset profile's metadata profile: the same detectors, verifier, and actions, with no escalation band, PERSON tokenized from 0.65 (and, for `strict-metadata`, city, postal code, organization, URL, and date from 0.60), so a low-confidence span is dropped instead of failing the listing. The cost: `escalate_below` is one floor per profile, shared by every kind — a span below it is dropped in clear, one between it and the kind's own threshold escalates and fails the listing — and both metadata profiles raise it to 1.0, past any kind's threshold, removing the escalation band for every tokenized kind, not names alone. A span the sanitizer scores inside the base profile's old band now passes in clear instead of failing the listing, unless the verifier's re-scan still catches it — a validated identifier such as an IBAN still is, through the verifier's regex re-scan. `support-email`'s floor is 0.50, so `support-email-metadata` reopens a 0.50–0.60 band for a name or a street address (both keep their 0.60 threshold); `strict`'s floor is lower, 0.40, so `strict-metadata` reopens a wider 0.40–0.60 band for names only (it inherits `strict`'s STREET_ADDRESS at 0.40, so an uncertain street is tokenized there, not passed in clear), and, only there, a 0.40–0.50 band for email, phone, and the other kinds that keep a 0.50 threshold. Before plan 2c such a span failed the listing. This is a cost of the metadata profile only: tool results and arguments stay under the dataset profile itself, unaffected. The prose is the upstream's to write, so a server that templates records into its descriptions gets this lighter treatment for them. Listed resources and every result stay under the dataset profile. `fast`, `fast-strict`, `thorough`, and `thorough-strict` have no metadata profile (the first two have no verifier NER to back it; the thorough profiles' verifier re-scan blocks benign descriptions until the quality lane recalibrates it), so under them a low-confidence span in listing prose still fails the whole listing. Names (tools, prompts, their arguments, schema properties and definitions, `required` entries, template parameters) are exposed as they are, so each listing scans them all with the tripwire's detectors (known entities of the dataset, validated identifiers), as written and split into words; a hit fails the whole listing. A known person, organization, or street counts in a name only when the match spans two or more words, so a known `Max` does not fail `max_results`; a single-word name used as a tool or property name is therefore not caught. A server that names things after records the dataset has not seen yet, and that no validator recognizes (a new customer's name as a tool name), still gets that name through. The MCP server name a harness is configured with is model-visible too (Claude Code prefixes it to every tool name): `inumaki status` suggests `inumaki-<opaque label>`, and a server named after a customer would send that name with every request. Two residuals remain. A tool the contract does not name, or any tool of an upstream without a contract, is exposed with text-only treatment, and a change to its description or schema is not flagged as drift (its descriptions are still sanitized on every listing). And an upstream that has never listed takes its creation-order name when it first comes up, so a name that an earlier upstream answered for until then can move to it; agents are notified with `list_changed`.

**Bounded buffering, with one residual.** Results larger than `[gateway] max_response_bytes` are refused with `resource_limit`, stdio lines and SSE events are capped, and in-flight engine work per dataset is bounded. An HTTP upstream that answers with a plain `application/json` body (not SSE) is read whole by the MCP client library before the size check; bounding it needs support in that library.

**Dataset stop is timing-based.** Stopping or deleting a dataset drains in-flight calls for up to 5 s, then waits 100 ms before ending MCP sessions. A response that misses that window leaves the client resuming its SSE stream against a `404`. The client sees an error, never another dataset's data.

**Logging.** Access logs use route templates (`/mcp/{dataset}`, or `unmatched`) and opaque dataset ids, never raw paths, query strings, authorization headers, arguments, tool names that failed the static-name check, resource URIs, or JSON keys. MCP error messages come from a fixed vocabulary, and their data carries classes, kinds, checks, counts, and upstream JSON-RPC codes only; an upstream error message is never relayed, since it may echo the rehydrated argument. The MCP library logs full JSON-RPC payloads at debug and trace level, so its log target is always dropped (and HTTP and TLS library targets are capped at `WARN`), whatever `RUST_LOG` says.

**Deliberate plaintext outputs.** `inumaki tokenize --map` (mapping on stderr) and `inumaki inspect --show-values` (candidate and excerpts, terminal only, labeled as local diagnostic output) print originals on purpose. They are local diagnostics, excluded from the rule that originals never reach logs, and never written to files or logs by inumaki itself.

**Activity records cannot carry text.** Every field of an activity record is an enum, an integer, a timestamp, a boolean, or a fixed-format opaque id; kind labels are limited to `[A-Z][A-Z_]{0,31}` and come from the engine or the operator's configuration, and check labels are a closed set. Stored records are validated on load, so a row edited to hold a name fails to load instead of being shown, and a test that destructures the record type breaks when a field is added. The records are chained with SHA-256, so an edit to a kept row, or a deleted row between kept rows, fails `inumaki activity --verify`. The chain is unkeyed SHA-256 over a published formula, so `--verify` detects inconsistent edits or deletions inside the kept chain (accidental corruption, naive edits). It does not detect a consistent rewrite by a process running as the same user that can write `vault.sqlite`, or truncation at either end: deleting the newest rows leaves a valid chain, and deleting the oldest looks like a sweep. It is not a signature and proves nothing to a third party.

**The tripwire is a signal, not a guarantee.** It recognizes, in model-written arguments (values and object keys), full names and other values this dataset has already tokenized, plus checksum-validated identifiers (IBAN, cards, national ids) and parsed emails, IPs, and URLs. A real name the dataset has never seen passes unflagged, and kinds the profile preserves are not counted. In the default `notify` mode a flagged call still reaches the upstream; only `tripwire = "block"` stops it.

**Test fixture.** `inumaki-test-upstream` is the scripted MCP server the gateway tests use. It is built only with the `test-fixtures` feature and is not in default builds or installs, and has tools that echo arguments and return any environment variable of its process. Never configure it as an upstream outside tests and smoke runs with synthetic data.

### Awareness: journal, entity listing, forget, alias groups

*The journal can contain identifiers the detectors missed.* Every released payload is stored exactly as it left. A name the detectors did not catch is therefore in the journal in clear, but it already went to the provider; the journal keeps a local copy inside the vault's trust boundary (sealed with the vault key, AAD bound to dataset and record id, checked against the activity record's digest on every read) so the user can see the miss and act on it (`inspect`, dictionary, `forget`). Retention defaults to 24 hours and a per-dataset byte budget; `[journal] enabled = false` turns it off. Journal payloads are read over the control socket only; `--show-values` rehydrates locally on a terminal; nothing from a payload reaches a log line (a TRACE canary test covers every journal and entity endpoint).

*Forget is not erasure of history.* Forgetting an entity deletes its mappings in every epoch and evicts it from memory, so the next mention mints a fresh token and the provider cannot link the two; the provider still holds whatever tokens it received, and journal payloads still carry the old token (shown as unresolved). Cached verdicts of the dataset are dropped so no result with the old token is served.

*Alias groups are configuration, not learned.* Variants are exact phrases after normalization from the user's dictionary; nothing fuzzy is ever linked (a reviewed project's Jaro-Winkler merging conflated Christina and Christian Huber). The vault stores the canonical only; a variant seen in clear is caught by the dictionary detector, the known-entity detector, the leak check, and the tripwire. Rows minted before a group was configured stay separate entities (the daemon logs their count at namespace open); forget them or accept the split. Alias groups also widen the gateway's exposed-name scan (see "Field coverage is by contract" above): that scan matches known entities word-bounded, so after a group is configured, a tool, prompt, or argument name equal to one of its variants (a tool literally named `Hansi`) now fails the listing the same way a customer's name would — the scan cannot tell a coincidental match from a leak, so it fails closed.

*Entity listing reveals a dataset's vocabulary on request.* `dataset entities --show-values` prints originals to a terminal for the same-user operator, like `inspect --show-values`; it is excluded from the no-logging claim in the same way, and the default output shows tokens and counts only. `dataset forget --value` is the third deliberate plaintext path: the value is typed without echo and held zeroized in the CLI, but it crosses the control socket in a request body the client does not zeroize.

*What forget does not clean.* A forget checkpoints the vault (TRUNCATE) so no pre-delete page image survives in the WAL, and `secure_delete` zeroes the freed pages. It does not rewrite the gateway's sanitized catalog (tool descriptions that mentioned the entity keep the old token until the next rebuild; a token is never rehydrated without a row, so this is harmless), the provider's copy of the token, or a journal payload's tokens (rehydrating one after a forget shows the forgotten token as unresolved, its text left in place). Rows handled by a `remove` action (`removed = 1`, secrets and any kind a profile removes outright) are not listed by `GET …/entities` and not reached by `forget`; they expire only when their epoch does. A missed identifier — one no detector caught, so it was never tokenized — stays in the journal in clear; forget has no token or stored value to match, so it cannot find or remove it, and only retention or `max_bytes` eventually sweeps it out.

### Mail connector (plan 3)

*(As built, plan 3.)* The mail connector is inside the local boundary: it sees real values (it reads your mailbox and writes your drafts), and the gateway is the only path from it to the model. Everything the agent receives from it passes the content contract and the dataset's sanitization first.

- *Credentials.* The app password lives in the vault's secrets table and is read when a session is opened or reopened, never at any other time, and is held in zeroizing buffers once parsed. That covers the CLI's file or prompt read and the daemon's parsed password; the JSON request body that carries it from the CLI to the daemon (the CLI's JSON value, the daemon's deserialized string, the HTTP buffers) is not zeroized and can linger in freed memory until it is overwritten. The user name, the drafts folder, and the From address are sealed in the vault like dataset names. The control API and CLI never echo a password, and the IMAP client's own log targets (`async_imap`, `imap_proto`, whose trace output includes `LOGIN`) are silenced in the daemon, which a test pins with a canary password.
- *Mail content is data.* Folder names (a folder can be named after a customer), senders, subjects, snippets, attachment names, and bodies are sanitized like any tool result. Attachments are listed by name and type and never fetched.
- *Handles.* Folder and message ids are random, scoped to the dataset and the mailbox fingerprint, and stored sealed. A handle is checked against the vault before use and against the live UIDVALIDITY on every read and draft; a stale or foreign handle answers `context_unavailable` and never resolves to another message. A string that only looks like a handle is not preserved by the contract.
- *Drafts write real values on purpose.* `mail_draft_reply` rehydrates the agent's body and recipients and stores them in your mailbox, because that is the point of the tool (integration spec §6.4). A body with a placeholder the dataset does not know is refused before anything is written. The tripwire scans draft bodies and `cc` before rehydration. An ambiguous `APPEND` (the connection dropped after the literal) is reported as `draft_status_unknown` and not retried, so a network failure cannot silently create two drafts. Nothing in the connector sends mail.
- *Transport.* Implicit TLS with the Mozilla root store only; plaintext IMAP is accepted for loopback hosts only. A private or self-signed certificate is refused.
- *No hammering.* A refused login is remembered for `[mail] auth_retry_after` and not repeated against the provider, so an agent loop cannot lock the account.
- *Errors and logs carry classes only.* Tool errors, logs, `Debug` output, and activity records for the connector hold counts, ids, and fixed class names, never a server message, address, folder name, subject, or body.

*What is not protected.* The provider holds its own copy of every draft (it is your mailbox). The provider also sees IMAP metadata: which folders were opened, which searches ran, which messages were fetched. Reply text the user types into a draft in the mail client is not inspected. The mail-task harness (`inumaki mail-tasks`) deliberately wipes a test account; it is guarded (loopback host unless `--allow-remote`, the dataset's own host, port, and login) but it is a tool for a dedicated test account, never for a real mailbox.

## Folder mirror (milestone 5)

A connected folder is mirrored into `<mirror root>/<label>/` as a sanitized copy that agents read instead of the source, and an `outbox/` inside it turns what an agent writes back into real names in a destination folder you own. The work happens when a source file changes, so a read costs nothing.

**What is protected.**

- **Content and names.** Every file's content and every file and directory name is sanitized under the dataset's namespace. A file is released only as a whole: a blocked or uncertain block, an object-level check that fails (JSON objects and arrays, CSV fields), or a block over 64 KiB withholds the file, and a placeholder naming only the reason class takes its place. Names that fail fall back to an opaque `f-<10 hex>`.
- **A release check and a tripwire pass.** After sanitizing, the assembled output and every mirror path component are checked for known originals of the dataset, as written and as a word-separated variant. A second hit withholds the file. Whenever the dataset learns a new entity, from any front door, every mirrored file and name is checked again; a confirmed original is removed from the mirror before anything else happens.
- **No source metadata.** A mirror file is written from sanitized bytes only: no copy of extended attributes, ACLs, Finder tags, quarantine flags, or "where from" data. The source's modification time is the one thing copied.
- **No symlink is followed.** Source, mirror, and outbox are walked through directory handles opened with `O_NOFOLLOW`. A link in the source gets a placeholder; a link an agent plants in the mirror is replaced, never written through; a link or a hard link in the outbox is refused.
- **Outbox restoration is strict.** A file with a token inumaki cannot resolve, a token of another dataset, or a removed-value marker (a secret) is not written; a sidecar next to it gives counts only. An existing destination file is never overwritten.
- **Logs and errors.** Mirror logs carry the opaque label, counts, durations, and error classes, never a path, a file or directory name, a slug, or a token. Paths are answered on the control socket only, and error bodies are fixed messages. `inumakid` installs a panic hook that logs `file:line` without the payload, and a failed task is logged as `panicked` or `cancelled`, not as its error.

**What is not protected, and known limits.**

- **In Easy mode the agent can read the source folder directly.** The mirror is a convention, not a sandbox: the agent runs as your user. The tool-result hook guards the shell and read tools of the supported harnesses (see the hook section below); nothing guards a tool it does not see.
- **The agent can write in the mirror.** Mirror files are mode 0444, which does not stop the same OS user. An edit is not detected by the periodic reconcile (it compares source files with the manifest, not the mirror file's content) and stays until that source file changes or is re-mirrored (a placeholder for an unchanged source file is not rewritten either); the tripwire pass does remove a known original an agent writes there, and files the manifest does not name are removed at the next full reconcile (at start, hourly, or on `folder rescan`). A mirror directory an agent deletes is rebuilt by the poller. Removing a folder waits at most 5 s for the job in flight and then answers `409` ("the folder is busy; try again in a moment"), with the removal fenced until a retry finishes it; stopping waits 3 s and then leaves the job to end with the process. With the default single worker a directory-heavy first scan or a re-mirror after a rotation also delays other folders until it ends: scheduling is fair per job, not per directory.
- **Names are sanitized with lower recall than content.** A name has little context for detection. The two-variant scan, the release check, and the opaque fallback reduce the risk; they do not remove it. Since 2026-10-20 a mirrored name is scanned as file-name text (`TextOrigin::FileName`), so ordinary document words in it are not tokenized as persons, and a lone surname in a name is released in clear under `offline`; see "Structured-position residuals" above.
- **Placeholders, tree shape, sizes, and times are visible.** A placeholder says a file exists and why it was withheld; the directory structure, the file sizes, and the modification times of the mirror follow the source.
- **Tokens are stable within an epoch.** The provider can link requests about one person across files. During a re-mirror after a rotation (`remirror_pending`), one person can carry the old token in files not yet redone and the new one in files already redone.
- **Known originals are per epoch.** After a rotation the mirror registers the previous epoch's known originals in the new epoch (with fresh tokens) before it re-mirrors, so a name that only seeding or another front door taught is not re-mirrored in clear. Only the most recently closed epoch is carried: a dataset rotated twice while the daemon was down loses the older epoch's names. The gateway and the hook do not carry yet; after a rotation they start without the previous epoch's known entities.
- **Decoding can hide a name.** Text that is neither UTF-8 nor UTF-16 is decoded as Windows-1252 (Excel's default export in the DACH region). A MacRoman file then decodes wrongly (`Müller`, where MacRoman encodes `ü` as byte 0x9F, comes out as `MŸller`), and a mis-decoded name can pass detection. Latin-9 decodes `ü` correctly and differs from Windows-1252 at only eight code points, so it rarely matters. Formats outside the allow-list (`.pdf`, `.docx`, `.xlsx`, `.xml`, `.rtf`, images, ...) are placeholders, never sniffed.
- **A missing source folder leaves its sanitized mirror in place.** Nothing is deleted on the strength of an absent source root; the folder shows `source_missing` until the source returns or you remove the folder. A folder identity adopted over an existing mirror (a restart that lost an unsaved identity) is treated the same way until the folder is added again.
- **Forgetting an entity does not rewrite mirrored files** until their source changes or the dataset rotates.
- **Changed model files do not re-mirror.** The mirror re-mirrors when the configuration, the dictionaries, the code revision, or the model manifest compiled into the binary changes. At load the daemon checks only that each model file is there with the pinned size, not its hash. Pointing the daemon at another models directory, or replacing model files in place with files of the same size, leaves files mirrored by the old models on disk until their source changes, the dataset rotates, or one of those inputs changes.
- **Very long originals.** The tripwire pass reads content in overlapping 64 KiB windows; an original longer than 32 KiB straddling a window can be missed.
- **Outbox destinations hold originals.** Restored files are mode 0600 in a directory you own, and the hook treats the destination like a source folder. A crash can leave a `.inumaki-tmp-*` file there; it holds a restored original and is removed only when a later file lands in that directory. A sidecar note for a source name of 233 bytes or more is silently dropped.
- **Stopping is bounded, not cancelled.** There is no cancellation between a file's blocks. Removing a folder waits at most 5 s for the file being processed, then answers busy; stopping the mirror waits 3 s, then leaves the job to end with the process (writes are temporary file and rename, so a cut job never leaves a half-written mirror file).
- **macOS privacy protection (TCC).** Reading Desktop, Documents, Downloads, iCloud Drive, or an external volume needs a grant for the reading process. A launchd job does get the prompt, and the first read blocks in `open()` until the user answers (`docs/research/2026-09-29-m5-tcc-spike.md`, macOS 27.0.1). While it waits the folder shows `pending` (after 2 s; not an error). A removal of that folder or its dataset answers `409 conflict` after 5 s, "the folder is busy; try again in a moment"; the removal is fenced (no further job of that folder runs, the source is never touched), a retry finishes it, and nothing retries it automatically. Mirror stop waits 3 s, daemon shutdown 4 s for the mirror and 2 s for the runtime, and the end-to-end check's cleanup 8 s, leaving what remains to the next start's sweep. Two limits remain. With the default `[mirror] workers = 1`, one parked first read stalls every folder, the check's own mirror folder included, so the check's mirror path fails closed after its 30 s wait. Whether `lstat`, `realpath`, or an FSEvents stream on an unanswered folder also block is unverified (it needs a spike with the user present); if they do, daemon start or adding and rescanning a folder hang. A denied folder shows `source_not_permitted` until it is granted (`docs/runbook.md`); the mirror keeps what it has and picks up a later grant without re-adding the folder. Builds are ad hoc signed, so every upgrade has a new code hash and **loses the grant** (confirmed by the spike): macOS prompts again on the first read after each upgrade. Installers replace binaries by writing a new file and renaming it, never in place, because the kernel kills a signed binary overwritten in place.
- **Linux is unverified.** The Linux code paths (`inotify`, the no-replace rename) compile but have not been run.

## Harness connection and the tool-result hook (milestone 6)

`inumaki connect` (`inumaki-adapters`) edits an agent harness's configuration files so that it uses the gateway, the folder mirror, and the model-API proxy, and installs `inumaki-hook` for Claude Code and Codex. It runs as the human user, on request, in the CLI or the app process, never in the daemon. Easy mode's limit applies to everything below: the configured path is inumaki, and an agent that deliberately goes around it can succeed. The harness-specific facts are in `docs/harness-adapters.md`.

### What the hook does not guarantee

`inumaki-hook` is defense in depth behind the gateway and the mirror. It sanitizes a tool result only when the tool input references a connected source folder or outbox, or the output contains a multi-word or identifier-kind value the vault already knows. Validated-regex hits alone (an email or URL in code output) do not trigger it. It guards connected data, and it is not a general PII filter. Its limits:

- **The harness decides what the model sees.** A harness passes the original output through when the hook binary is missing, is killed, times out at the harness level (the hook's own deadline is 10 s, the written harness timeout 30 s), or returns the wrong shape. Claude Code ignores a replacement that does not match a built-in tool's output schema, so each block is a per-tool template, not a bare string. Status reads the hook command registered in the harness file and reports the hook as broken when the program it names is missing or cannot be run, or when it names another program or socket than the running inumaki uses. It cannot see a binary removed after status last ran, and it cannot report the other cases.
- **Which tools are hooked.** Codex: shell tools only (MCP results, `apply_patch`, and hosted tools are not hooked). Claude Code: the listed built-in tools and every MCP tool except those of servers behind the gateway, including project-scope, plugin, and later-added servers; `Monitor`, `WebSearch`, subagent output, and a few metadata tools are not hooked. Excluding the gateway's servers relies on a regular-expression lookahead that has not been run against the real Claude Code binary yet. Hermes and OpenClaw have no tool-result hook, so their tool results are covered by the gateway and the mirror only.
- **Some results never reach the hook.** Claude Code failed tool calls (`PostToolUseFailure`: up to about 10,000 characters of a failed Bash or PowerShell command, and MCP error results) and Codex output of a command that is still running cannot be replaced. A sibling Claude Code hook that also rewrites the output races ours, and the last write wins. A Codex hook the user has not trusted does not run. The full list, with the path-extraction gaps, binary outputs, numbers beyond `f64` precision, and discriminator over-blocking, is in `docs/harness-adapters.md` section 9.
- **Availability against recall.** The hook fails closed: when the daemon is down or restarting (for example after a model download), when its deadline passes, or when the daemon cannot check the result, the result is blocked and the model sees `blocked by inumaki (<class>; kinds: …)`. The daemon-down case is a deliberate decision with its own section below: [The hook while the service is stopped](#the-hook-while-the-service-is-stopped). The daemon scans every dataset. If any dataset cannot be scanned (a broken stored profile, a namespace that fails to refresh), every hooked result is blocked until it is repaired. The re-scan after sanitizing also counts single-word known entities of every dataset at any confidence, so a result that also contains a common first name known to any dataset is refused. This costs false refusals and is deliberate: a leaked identifier is the worse failure.
- **What the hook and its endpoint keep.** The hook writes nothing to disk and prints fixed strings on stderr. `POST /v1/hook` is served on the control socket only. Its request type prints counts in `Debug`, errors answer with a fixed message and no dataset id, and a block names entity kinds only. A replace or block writes an activity record; an error answer does not, so the audit trail has a gap there.

### The hook while the service is stopped

Decision (integrator ruling L97, 2026-10-12): when `inumaki-hook` cannot reach the daemon, it blocks the tool result. It never passes the result through and never decides from cached state.

- **Why not a cached pass-through.** Whether a result may pass depends on the vault and the connected folders as they are now: an entity learned a minute ago, a folder connected since, a dataset whose profile changed. A cache of earlier verdicts, or of "nothing here is connected", is stale from the moment it is written, and stale state passes exactly the identifier the daemon would now catch. A pass-through while the daemon is unreachable would also turn every stop, crash, restart, or model download into a window in which hooked tool output goes to the model unchecked. A blocked result is the better failure.
- **What it costs.** While the service is stopped, restarting, or unreachable on the socket the hook was given, every hooked tool result in every session of a connected harness that runs the hook (Claude Code; Codex once the hook is trusted) is replaced by the fixed text `blocked by inumaki (daemon_unreachable; kinds: none). inumaki is not running; start it to restore tool output.` The agent keeps working but sees none of that tool output. The text names no path, socket, or value. Tools the hook does not cover (listed above) are not blocked.
- **How it is made visible.** A Connect that installs the hook (Claude Code, Codex; not Hermes Agent or OpenClaw, which get no hook) reports the fixed warning `hook_blocks_when_stopped`: "While inumaki is stopped, tool output in every connected session is blocked. Start the service to recover; Revert also needs it running." `inumaki connect apply` prints it on stderr and the app shows it with the connect outcome; the app's Protect, which connects again, shows it too. The block text above carries the recovery. When the service is unreachable and a connected harness's connection page shows the hook installed, the grey tray's tooltip, unless a configuration error is shown (the tray is then red and the tooltip reads "inumaki: configuration error"), reads "inumaki: service not running; tool output is blocked in connected sessions". The tooltip follows what the connection pages show: a Codex hook that is not trusted yet does not count (Codex does not run it), and a hook the page shows as broken does not count either, so the tooltip can understate. A service that is up but not ready answers the hook with `timeout` or `daemon_error`, and those block texts carry no recovery sentence; only `daemon_unreachable` does.
- **Recovery.** Start the service and rerun the tool call. The app's Revert (the connection page's button) removes the hook too and works with the service stopped: it records which gateway token to revoke and restores the harness's files, and the service revokes that token before it serves anything at its next start ([Gateway tokens in harness files](#gateway-tokens-in-harness-files)). `inumaki connect revert <harness>` revokes the harness's gateway tokens first and therefore still needs the service: with the service unreachable it reverts nothing. If the service cannot be started and the app is not at hand, the remaining way out is to delete inumaki's group from the harness's `PostToolUse` hooks by hand (`~/.claude/settings.json` for Claude Code, `$CODEX_HOME/hooks.json` for Codex; it is the group whose command names `inumaki-hook`), and to run a Revert once the service runs again. Whether an open session stops running a removed hook at once depends on the harness and was not measured.
- **What the decision does not cover.** The harness, not the hook, decides what happens when the hook program is missing, killed, or times out, and both harnesses then use the original output (first item above).

### Backups

Before the first write of an apply, the adapter stores a backup under `<data_dir>/adapters/backups/<harness>/<id>/` (directories 0700, files 0600). A backup holds only what the harness files held, plus what inumaki wrote:

- `manifest.json` records, per file, its path, SHA-256 before and after, its mode, and for every key inumaki set or removed the previous value and the value written. The written values include the gateway token and the client header value. The previous value of a replaced MCP server entry is the original entry, including any secret that was in its `env` or `headers`.
- Files the user edits (`settings.json`, `config.toml`, `hooks.json`, `config.yaml`, `openclaw.json`) are also copied whole as `<role>.orig`. `~/.claude.json`, which Claude Code rewrites constantly and which holds session state, is never copied; its backup is the manifest alone, and revert restores its values, not its bytes.
- After the Protect switch, the wrapped server's secrets are in the vault and in the backup until the backup is deleted. They no longer sit in the harness file. A backup is deleted after a successful revert unless `--keep-backup` was given, and the newest 5 per harness are kept otherwise (the active one is never pruned). Delete a backup by deleting its directory. A copy of the data directory that includes `adapters/backups` includes those secrets.

### Gateway tokens in harness files

Each connected harness gets its own gateway token, label `app:<harness-id>`, written into the harness's MCP configuration. The file is readable by the user the agent runs as, and that user can reach the control socket anyway, so in Easy mode the token adds no capability. The TCP listener is loopback only, so a token that leaves the machine (a dotfiles repository, a synced home directory, a backup) is useless elsewhere, but any local process of any local user that holds it can use it. Revert revokes the harness's tokens, and Reconnect mints a new one and revokes the old, because a drifted file may have leaked it.

The app's Revert also works while the service is stopped, and then it revokes in two steps. It writes a record, `<data dir>/revocations/<harness>.json` (mode 0600 in a directory of mode 0700), and restores the harness's files. The record holds only the token label (`app:<harness-id>`), never a token, a token id, or a hash, so the app, which cannot compute the vault's index hash, needs nothing else. The service applies every record after it binds its control socket and before its gateway listener binds, so before it serves a single request, and again on every 60 s sweep while it runs. Applying a record revokes every token with that label that exists at that moment and deletes the file. A Connect or Reconnect of the same harness settles a pending record first and mints nothing if it cannot.

- **When the token works.** While the service is stopped, nothing inumaki runs listens on the gateway port, so the token opens nothing. An open harness session may still hold the token in memory and keep sending it to that loopback port; whatever binds the port meanwhile receives a token that inumaki's gateway rejects once the service has started. Nothing in this design revokes the token while the service is stopped: it stops working because nothing accepts it, and it is revoked at the next start. If the service was in fact running but its control socket could not be reached (the socket file was removed while the process runs), the token keeps working until the next sweep, at most 60 s.
- **A record the service cannot trust revokes more.** An entry that is not a regular file, cannot be read, does not parse, carries another version or an unknown key, is larger than 1 KiB, has a `.json` name that is not one of the four harnesses, or names a label other than the harness its file name states counts as unreadable. The service then revokes every `app:` token (all four harnesses and the Other client) and removes the file. Check tokens (`check:`) stay. After that, connected harnesses read "Connected" until a Reconnect, while their tokens are dead; their end-to-end check fails. This fails closed, and nothing yet tells the user to Reconnect. An unfinished write (`.<harness>.json.tmp`) is removed and never applied, because the app reported nothing for it.
- **A directory the service cannot handle stops it.** If `revocations/` exists but cannot be listed (a symbolic link counts), a vault call fails, or an entry cannot be removed (for example a directory named `x.json`), the service does not start: it removes its socket file and exits with code 2, before the gateway listens. During a sweep the same condition shuts the service down gracefully, so the process exits 0. The next start refuses again until the cause is fixed ([runbook](runbook.md#what-the-vault-is)). The app never writes through a symbolic link at `revocations`: it refuses and changes nothing.
- **No new capability.** Whoever can write the data directory can make the service revoke app tokens, which is no more than that user can do through the control socket, and writing a record gives no access to a token or a dataset.
- **Not covered.** A configured `[vault] path` outside the data directory, shared by two data directories, sees only the records of its own data directory. The reader opens a record by path after checking that it is a regular file; without `O_NOFOLLOW` (`libc` was not added for it) a link swapped in between the check and the open can be read (never written or removed through). What it reads only feeds the fail-closed reader, which at worst revokes more tokens. A FIFO swapped in at that moment blocks the open, so the start hangs with the control socket bound and nothing served. Both need write access to the data directory.
- **The CLI is unchanged.** `inumaki connect revert` still refuses when the service is unreachable.

### The client header

When the proxy is enabled, `connect` also writes a per-install header `X-Inumaki-Client: <value>` wherever it writes a chat base URL. By design (M8 spec), the proxy restores dataset values in a model's answer only for requests that carry it, so it is the capability that separates "tokens only" from "restored". Treat it at least like the gateway token: for Claude Code it sits in the more exposed of the two files.

- **Where it lives.** For Claude Code it is a line of `env.ANTHROPIC_CUSTOM_HEADERS` in `~/.claude/settings.json`, not in `~/.claude.json` beside the token. `settings.json` is the more exposed file: it is often mode 0644 and often a symlink into a dotfiles repository (the atomic write keeps the original mode and edits the symlink's target). Claude Code may also pass the `env` block of `settings.json` to the processes it starts; if it does, a Bash tool call can read the header from its environment without reading any file. That is not verified yet (the `harness-tests` run must check it), so assume the agent can read the header. For Codex it is `http_headers` of the `inumaki` provider in `config.toml`, for Hermes `providers.inumaki.extra_headers`, for OpenClaw `models.providers.inumaki.headers`. It is also in the backup manifest.
- **Where it goes.** By design (M8 spec), to the proxy only. The proxy specification (`2026-09-29-inumaki-m8-proxy-design.md`, section on forwarded headers) requires it to drop every `X-Inumaki-*` request header before forwarding upstream, so it never reaches the model provider. That is the proxy's to implement and test; it is not part of the code this milestone adds. A harness that still sends the header to the real provider (because the base URL was removed by hand and the header was not) discloses it.
- **Revert removes the line.** For Claude Code, if the user changed `ANTHROPIC_CUSTOM_HEADERS` after apply, revert removes the lines inumaki wrote (every value recorded in the backup) and keeps the user's other lines. If it cannot (the value is not a string, the file does not parse, the write keeps failing), the secret stays, `RevertReport.client_header_left` is true, and `inumaki connect revert` prints the report and exits 2 with a message to delete the line by hand, because the header would then go to the model provider. A stale `X-Inumaki-Client` line that apply replaced is dropped, not restored. Revert deletes the backup before it strips the line, so a later revert cannot retry the strip by value; delete the line by hand as the message says. Only the Claude Code adapter sets `client_header_left`. For Codex, Hermes, and OpenClaw the header sits inside the `inumaki` provider table, which inumaki owns as a whole. If the user edited that table after apply (for example pointed its base URL at the real provider), revert reports a conflict and keeps the table, header included, and nothing flags the header.
- **If you edit by hand.** Removing `ANTHROPIC_BASE_URL` without the header line sends the header to Anthropic.

### Codex hook trust

Codex runs a user hook only after the user trusts it in `/hooks`. inumaki never writes a trust record: `connect` appends its group last in `hooks.json`, and `inumaki connect status` reports the hook as pending ("needs trust") until `config.toml` holds a non-empty `[hooks.state."<hooks.json path>:post_tool_use:<group>:<handler>"].trusted_hash` for that position. Status checks presence only; it does not compute or compare Codex's hash. The record is positional, so it can be stale: a group that the user adds before ours, or a re-apply with a changed hook command (a new binary or socket path) that moves our group, leaves a record at the old index. Codex then treats the handler as modified and skips it while status still reads "installed". A re-apply with a changed hook also shifts the user's later groups, which then need re-trust. An identical re-apply moves nothing.

**Revert and Reconnect.** A user Revert (the app's Revert button, `inumaki connect revert codex`) removes inumaki's own trust record, the `[hooks.state."<key>"]` table at exactly the key of our handler's position, and nothing else in `hooks.state`: other positions, other files, and other projects keep theirs. It does so because the record exists only for our hook, and leaving it would trust an identical hook command after a later Connect without the user confirming it. If the removal fails, the revert still stands, `RevertReport.codex_trust_left` is set, and the app and the CLI tell the user to remove the record in Codex's `/hooks`. A Reconnect (a revert followed by an apply inside the app) keeps the record, so the hook does not need trusting again. Codex's own model usage counters in `config.toml` are not touched.

### Chat paths that go around the proxy

- **Chat that is not routed is not protected.** The app shows a connected harness whose chat goes straight to the provider as grey "Chat: off, your choice", with a line that the harness talks to its provider directly and that inumaki does not see the chat text, and the reason sentence "Chat is not protected: it goes straight to the provider, and inumaki does not see it." under it. The status was red "not protected" before the 2026-10-12 redesign; the words still say the chat is not filtered, and only the alarm colour is gone, because chat that is off is the default and can be the user's own choice. The tray is not red for it either way. Chat is an explicit opt-in on the connection page of every harness (Claude Code, Codex, Hermes Agent, and OpenClaw, each with its own switch and confirmation) and is off until the user turns it on; the app derives the switch from the setup already in place, so an install from before this change keeps a chat route it already had, and a Revert clears the choice. The CLI's `connect apply` still writes the route unless `--no-chat` is given, and prints a warning when it does. With a ChatGPT login, Codex goes to ChatGPT directly unless the switch is on, and that route is refused today. inumaki does not see unrouted traffic. The Claude Code route is written to the user-level `settings.json`, so turning it on switches every open Claude Code window, in every project, at once; for the other harnesses the change applies from the next session (at the latest, for Hermes Agent and OpenClaw, whose behaviour was never measured). The app and the CLI say so before and after.

- **OpenClaw.** Only `agents.defaults.model.primary` (or the plain string form of `agents.defaults.model`) is repointed. `fallbacks` and per-agent `agents.list[].model` entries still name the real provider, so those requests go direct, and when the proxy or daemon is down OpenClaw falls back direct. Status still says connected.
- **Subscription logins.** OpenClaw's subscription login runs through a command-line bridge with no base-URL setting. Hermes's ChatGPT and Anthropic logins can be routed only through a setting that inumaki does not write, so those chat paths read "Not protected" (OpenClaw) or "Needs one line you add" (Hermes Agent), never as filtered, and the manual snippet applies.
- **Codex profiles.** A profile file `$CODEX_HOME/<name>.config.toml` that sets its own `model_provider` bypasses the proxy for that profile. Status reports it.
- **Tokens only.** A harness that cannot carry the client header gets filtered chat, but values from connected datasets stay tokens in its answers.

### The Protect switch and secrets that are not split

The Protect switch moves a wrapped server's credentials into the vault by name: an environment or header name that looks like a credential goes to the sealed secrets, everything else to stored-in-clear fields that the upstreams API returns. A secret in a stdio argument (`--api-key=…`), in a URL's userinfo or query string, or in a variable whose name does not look like a credential is therefore not split. It is stored in clear in the upstream row and is also in the backup of the original entry. Check a server's arguments and URL before protecting it. Servers that need the MCP OAuth flow are refused. The definition identity that decides whether two harnesses share a dataset is an HMAC under a per-install key in `<data_dir>/adapters/definition.key` (0600, in a 0700 directory), so `definitions.json` alone does not allow confirming a guessed secret. The key file sits beside it with the same owner and mode, and the two together do allow it, so treat them together: a copy of the data directory carries both.

### Refused edits and manual snippets

An adapter edits only the keys it owns, and only when the file parses and prints back unchanged, and the result differs from the original exactly by those keys. Otherwise it writes nothing and prints the lines to add by hand. That snippet contains the gateway token and the client header value by design, so the user can paste them. A refused first connect keeps the minted token valid until `connect revert` (which revokes it even with no backup) or a new `connect apply`. Do not paste a snippet into a shared place.

### Revert and drift

- **The CLI's Revert needs the service; the app's does not.** `inumaki connect revert` revokes the harness's tokens first and refuses to touch the files when the daemon cannot be reached ("is the service running?"). A user who removed the service must start it, use the app's Revert (which records the revocation for the service's next start), or edit the files by hand (and remove the client header line, as above). When a backup directory exists but no backup manifest of the harness can be read, revert revokes the tokens, changes no file, and exits with an error instead of reporting "no backup"; the files may still hold inumaki's entries and the client header.
- **A file changed by the harness during an apply.** The write is a compare-and-rename with three attempts. A harness write that lands between the final hash check and the rename is overwritten, because POSIX has no compare-and-swap. The window is the read and hash of the file; Claude Code can also write back an older copy of `~/.claude.json` later, which status reports as drift.
- **Value-identical, not byte-identical.** Reverting `~/.claude.json` restores values, not bytes, because no copy of it exists. A TOML file with no final newline is edited and still has none afterwards. Revert never recreates a file the user deleted after apply.
- **Managed settings.** Claude Code managed settings and Codex `requirements.toml` can override the user-level keys inumaki writes. The adapters do not detect that yet.
- **The chat route is checked once, at apply time.** `inumaki connect` and the app write the proxy base URLs and the client header only while the proxy reports `running`, read at the moment of the apply; a proxy that is disabled or not listening (it could not bind, or stopped serving) gets no chat route and a fixed warning (an explicit `--chat` fails). This is a check at one instant, not a guarantee. If the proxy stops, or another process takes `127.0.0.1:8787`, after the apply and before the harness next sends a request, the harness points at whatever listens there and sends it the raw conversation and the provider credential (API key or OAuth token). The client header is sent along with it. Nothing re-checks the address afterwards, and a foreign listener answers a request that carries a valid-looking base URL. Not closed. Revert the harness, or restart the proxy, if the port was taken.

### The app, its packages, and the end-to-end check

- **No network from the app.** The app process talks to `inumakid` over the control socket only and opens no network connection; there is no telemetry and no updater. "Run the check" starts the user's harness binaries, which get the switches each harness offers for "no other network traffic" (Hermes has none) and the check route as their model; inumaki passes those switches but cannot enforce them. The daemon's model download (`POST /v1/models/pull`) is the one outbound connection M6 adds: it fetches the pinned manifest's files from its base URL and checks each file's size and SHA-256 before it is used.
- **Ad hoc signatures.** The app and the helpers are ad hoc signed, not Developer-ID signed or notarized. A downloaded `.dmg` is quarantined and Gatekeeper refuses the app until the user opens it explicitly or clears the attribute (`docs/packaging.md`); the helpers the app installs are cleared of `com.apple.quarantine` and re-signed ad hoc. Because an ad hoc signature changes with every build, macOS may ask again after an update whether `inumakid` may read its vault key from the Keychain, and folder grants are lost (above).
- **Check routes and the canary server are shipped surface.** The check runs one at a time for at most 10 minutes, with synthetic data only: a canary identity, a temporary `check-` dataset seeded with it, a temporary gateway token labelled `check:`, a stdio upstream `inumakid canary-mcp` that reads its fixture from a 0600 file, a temporary folder under the system temp directory, and two proxy check routes ("Check routes" in the proxy section below). Everything is removed when the check is deleted or expires, and the generated shapes are swept at the next start. The public endpoints refuse the reserved names. The check's temporary folder is not a protected location, so the check can pass while every real folder waits for a grant: the folder card, not the check, shows that.
- **The hook's limits** are listed above ("What the hook does not guarantee"): a harness passes the original output when the hook is missing, killed, or answers in the wrong shape. **Backups** keep a wrapped server's secrets after Protect until the backup is deleted ("Backups" above).

## Model-API proxy (milestone 8, plans M8-1 to M8-3)

*(As built, plans M8-1 to M8-3.)* The proxy is the Chat path: a harness whose base URL points at `127.0.0.1:8787` sends its system prompt, the user's typed text, tool results, and its own history through inumaki before they reach the provider. Easy mode's limit applies: the configured path is inumaki, and a harness or process that goes around it can succeed. **Streaming is served (plan M8-2)** on all three routes and on `/codex`; the section "Streaming" below describes what changes for a stream. Plan M8-3 adds the check routes of the end-to-end check ("Check routes" below). **Codex with a ChatGPT login is unverified** (`CODEX_CHATGPT_VERIFIED = false`): the user-gated run against the real Codex client has not been done, so the `/codex` route with a ChatGPT login is opt-in (`inumaki connect apply codex --chatgpt`). Until it is on, the app shows that path as "Chat: not protected", because Codex then talks to ChatGPT directly.

### What is sanitized

Every string leaf of a request body on `/anthropic` (Messages) and `/openai` (Responses and Chat Completions), at every depth, is detected, tokenized, and independently verified before the request leaves, unless it is a structural value in its API shape or an opaque signed field. That includes the system prompt, typed text, assistant history, tool results, tool-call inputs (every object key and string separately), unknown top-level parameters, and unknown block types. Tool and schema definitions are scanned, not changed: a known original or a validated identifier in one refuses the whole request (`400 unsupported_content`). Reasoning, citation, and search-source text is scanned and forwarded byte-identical, because it is signed or must match its source. Tool results from the gateway and files from the mirror already hold dataset tokens, and the engine leaves tokens that resolve in the vault or the session untouched. A tool result that no other front door covered is sanitized here like any text. A request that cannot be decided is refused, and the provider receives nothing (fail closed): a detector, model, vault, or store error, a malformed body, an unsupported encoding, an oversized body, a definition hit, a binary-typed object in a tool or schema definition, binary content when `binary = "refuse"`, or a clear value in reasoning text the provider did not write. The provider sees tokens in place of every identifier the configured checks detected; what the detectors miss is sent as is, with the recall limits of the engine's own numbers. **Attachments are removed, not sent.** By default (`binary = "placeholder"`) each image, document, audio, video, or file part outside a tool result is replaced by a fixed text part, `[inumaki: an attachment (image, document, audio, or file) was removed here and not sent to the model.]`, on every wire, so the session goes on. Its payload, URL, `file_id`, file name, title, and media type do not leave and do not reach the engine, the cache, or the journal. Nothing inside an attachment is read or detected (no OCR), so inumaki makes no statement about what an attachment contained. `binary = "refuse"` refuses the request instead (`400 unsupported_content`). `binary = "forward"` sends the attachment **unchecked, with no detection on it**; it is the explicit opt-out, no screen of the app turns it on, and the daemon logs one warning at start when it is set. Session tokens are random per session. A value that a dataset already knows keeps that dataset's token, so the provider can link chat and dataset traffic about the same person for one rotation epoch, the price already accepted for datasets.

### Streaming

A streamed answer goes through the same restoration rules as a whole one, one event at a time (`stream.rs` and the codecs in `wire/`), and the request side is unchanged. What differs:

- **The holdback can only leave a token unrestored.** A channel holds the longest suffix of its text that is still a live prefix of the token grammar and emits everything before it. When the held bytes complete a token, the token is resolved by the provenance column above; when the hold reaches its cap (the longest token the grammar allows) or the channel ends, the held text is emitted as it is. So a cap, an odd split, or a label longer than 32 characters split across deltas shows the client a token, never a value it should not see. A resolver error while a token is split aborts the stream; the partial token is not forwarded.
- **A stream that aborts shows the client only the abort event.** Held text is not flushed. The abort event is the wire's own error event with a fixed class and no text. A client that has already received earlier text keeps it; nothing after the abort reaches it. An upstream cut mid-token ends the answer without the partial token.
- **Reasoning shows tokens.** Reasoning, signature, and citation deltas pass unchanged, because a rewritten block would fail its signature check on the next turn. A client that displays reasoning shows the tokens the model saw, not the originals. Only the summary text of a completed Responses reasoning item and the thinking and citation text are recorded as provider-written for the next turn's check.
- **The tripwire on model output.** Each channel's raw text is scanned for known originals when it ends, and a Responses or Codex repeat (`…done` events) is scanned before it is released. In `notify` mode the stream is not delayed, so a tool call whose arguments hold a known value in clear has already reached the harness when the record is written; the record (check `ClearValue`) is the signal, not a guarantee. In `block` mode every function, custom, `tool_use`, and Chat tool-call channel is queued until its end and a hit aborts the stream with `privacy_block` before any of it is sent, so no such tool is dispatched with the value. Codex shell, patch, computer, and MCP items are covered too: an `mcp_call`'s streamed arguments are a channel like a function call's, and every string and key of a `shell_call`, `local_shell_call`, `apply_patch_call`, `computer_call`, or `mcp_approval_request` item except its `id`, `call_id`, `status`, and `type` (whatever the item's shape) is tripwired as arguments in every event that carries the item, with the item withheld from its `output_item.added` event until its `output_item.done` event passed. Any other event of these items that carries more than ids aborts the stream (its shape is not known offline, so it cannot be checked), and the non-streaming path tripwires the same fields and refuses the answer (`451`). Visible text is never blocked. A stream aborted by the tripwire is recorded as `blocked` and does not mark the route as failing; any other abort records `stream_aborted` and marks it `failing`.
- **Tool arguments are checked against the deltas.** A Responses or Codex `…arguments.done` or `output_item.done` argument text must equal the deltas the client already saw, or the stream aborts, because Codex runs tools from the `done` events. A differing text repeat is tripwired and released whole. Provider framing the proxy cannot restore or scan (a Messages `tool_use` start that already carries input, a Messages `message_start` whose message already holds content, a Responses item added with arguments, a Chat `custom` tool call) aborts the stream. So does any data payload that does not scan as JSON (duplicate keys, a lone surrogate, nesting deeper than 127), whatever its event name, because a client's lenient parser would still read it, and, on Messages and Responses, a named event whose payload `type` is missing or differs from the name. One byte-order mark at the start of a stream is dropped before parsing, as a client's decoder drops it, so the first event is checked like any other. A channel cut off by an abort or an upstream error event is still tripwired for the record; that scan takes scan permits like any other (over 64 KiB), and when none come in time the record is skipped (the stream ends either way) with a fixed log line, so the record can be missing under scan load. Restored text written into a re-serialized event never adds a field or an event: every line break in the data (CR, LF, or CRLF) ends a `data:` line, and an event name or id with a line break aborts the stream. The block-mode queue, the only event bytes kept between events, is wiped when it is dropped.
- **Restricted mode on streams.** A stream without the client header (or with a wrong value) restores session tokens only; dataset tokens stay tokens in text, as for a whole answer. Trusted and restricted requests still never share a session.
- **Seeding on streams.** A completed stream seeds the next turn's cache exactly as a whole answer does, with the same unverified stamps. A stream that aborts or is cut, or an answer in which the tripwire found a known value, seeds none of its text or arguments. The seeds of an answer the client saw in full can survive a client that leaves between the last delta and the terminal event; a seed only lets provider-written text pass again.
- **A panic in a streamed body** ends the stream with the abort event; the payload is not formatted into any log line.
- **Memory.** One streamed answer holds at most `max_request_bytes` of model text, arguments, thinking, and reasoning; a larger one aborts (`stream_aborted`), as a whole answer over it is refused. An event over 64 KiB, or any event while an open argument channel is over 64 KiB (any event can end that channel, which is then scanned whole), takes weighted scan permits from the same budget as an answer; if the wait runs out the stream aborts (it cannot answer `503` after its headers). The permits go back once the event is rewritten, before the driver waits on the client. The queue to the client holds 32 events, and a client that stops reading releases its in-flight slot after the idle timeout (300 s).

### The released-block skip

A tool result the gateway, the mirror, or the hook already sanitized under the proxy's own profile need not run through the engine again. The daemon keeps a keyed digest of each such block it released (an HMAC of the SHA-256 under a per-process key, one hour, at most 65 536 entries, memory only, nothing that identifies the text), and the proxy skips detection for a tool-result leaf that matches. The skip is not a bypass. The leaf must be NFC, every token-shaped string in it must be a real token (a forged `_REMOVED` marker does not count), the chat dictionary (closure forms of every session value, host and identity values the policy does not preserve, dataset values the request resolved) must find nothing outside real tokens, and the validated-regex tier on the masked text must find nothing the policy does not preserve. Any other result sends the block through the full engine. A skipped leaf is still re-checked by the closure against values the same request mints, and is not cached if its tool result is withheld. Digests are recorded only for blocks that passed, are free text, belong to a non-check dataset, and were sanitized under the profile that `[proxy] profile` names, so text released under a weaker profile never skips the proxy profile's NER. The re-check does not run the secret scanner: the secrets were removed when the daemon released the text (every profile removes or blocks `SECRET` at a `min_confidence` no higher than the scanner's fixed 0.95; a configuration with a profile that does not is refused at load).

### Restricted mode and the client header

The proxy restores the tokens in a model's answer. Which tokens depends on whether the request names itself with the per-install header `X-Inumaki-Client`:

| Content of the answer | Session tokens | Dataset tokens |
|---|---|---|
| Model text | restored | restored with the matching header; left as tokens in **restricted mode** |
| Tool-call arguments | restored | left as tokens (the gateway rehydrates them under its field contract) |
| Upstream error bodies | restored | left as tokens |
| Reasoning, removed markers, unknown tokens | left | left |

A request without the header, or with a wrong value, is in restricted mode: session tokens are restored, dataset tokens never are. Trusted and restricted requests never share a session. A harness that cannot send the header (the adapters write it where the harness supports custom headers) gets filtered chat, but values from connected datasets stay tokens in its answers.

**The header value is a secret as sensitive as a gateway token.** It is a random 64-hex-digit value generated once per install and stored in the vault's secret section as `inumaki-chat/proxy/client_key`. Anyone who can read it, and who can reach the proxy with a provider credential, can have dataset tokens they know restored in answers (see the rehydration oracle below). It sits in the harness configuration file and in the backup manifest beside the gateway token, and `GET /v1/proxy` returns it on the control socket only. The proxy removes every `X-Inumaki-*` header before forwarding, so the header never reaches the provider; the section "The client header" above covers where adapters write it and what revert does. The proxy never logs it.

### The rehydration oracle

A process that can reach `127.0.0.1:8787` and holds a provider credential can send text that contains tokens it already knows and read the restored originals in the model's answer. Three things limit this. The `Origin` and `Host` guard stops web pages and DNS rebinding. Dataset tokens are restored only for requests with the client header, so a process without the header gets session tokens only, and to have a session token restored it must reach that live session (it needs the session's key, from its session header or its first system and user text) and know a token of it. Other OS users cannot read the header unless the harness file is world-readable. What the guard does not stop is a same-user process: it can read the header from the harness file (Easy mode's stated limit). The M7 local token covers API-key custody only and does not change this.

### Check routes

The end-to-end check's routes (`/check/<id>/<upstream>/…`, `docs/architecture.md`) are shipped surface on the proxy listener, not a test fixture. The id is a capability: 128 random bits, registered for at most the check's 10-minute lifetime (the registry clamps any TTL to one hour), removed when the check is deleted or expires (they live in memory, so a restart drops them), and never logged. The routes sit behind the proxy's `Origin`, `Host`, and `Upgrade` guard. A check route forwards nothing (the scripted upstream answers in process) and restores only the check dataset's tokens, which stand for its synthetic canary, never a session's or another dataset's tokens. A leaked live id lets another local process send text through the sanitizer and read a restored echo of check-dataset tokens only; it exposes no real data. Scanned leaves (reasoning, citations) are tokenized on check routes, not passed through, so a canary there reaches the record as a token, and a clear value there fails the check.

**The harness check runs only against a running proxy.** The daemon hands out check routes only while the proxy reports `running` at `POST /v1/check`. The app refuses to run any harness against them unless `GET /v1/proxy` also reports `running` and the authority of every route URL equals the loopback `listen` address the daemon reports; it then shows a fixed warning and keeps the direct check's report. A proxy listener that ends for any reason reads as not listening. Both checks hold at one instant, not for the whole run: between the status read and the harness run the proxy can stop and another process can take the port (time of check to time of use). The app reads the status again before each connected harness runs, one after another, each for up to 120 s, so the window is one harness run; the daemon also refuses the proxy direct run once the listener has ended. A refusal in the middle stops the remaining harness runs and keeps the reports already made. The route ids are random and TTL-bound, and every check invocation runs in a temporary configuration with a dummy credential, so the gate is defence in depth. The `bind_failed` state's text is neutral ("not listening") and claims no cause.

### A blocked history, and what to do

A privacy refusal answers `451 privacy_block` with the message `blocked by inumaki (kinds: …; checks: …). Nothing was sent. Edit or rewind the message.` It names entity kinds and check ids only. The harness keeps the refused message in its history and resends it with every later turn, so every later turn is refused until the message is gone. Edit the message, rewind the conversation to before it, or start a new one, using the harness's own commands. Remove or rewrite the identifier the kinds point at. The refusal is recorded in the activity log (`inumaki activity`: verdict `blocked` or `uncertain`, front door `proxy`, kinds and checks, no text). When the refusal is a verifier-uncertain verdict, `[proxy] uncertain = "pass"` lets such blocks through with the response header `X-Inumaki-Verdict: pass-uncertain`; it trades privacy for convenience and is off by default.

A blocked or uncertain **tool result** never causes this: the result is replaced by the fixed placeholder `[inumaki: tool result withheld (kinds: …). Nothing was sent.]`, the verdict is remembered for the session so every resend of that history is byte-identical, and the conversation continues. A `400 unsupported_content` is a different refusal: a tool definition holds a known value (rename or remove that tool or server, or the entity), or (with `binary = "refuse"`) the request holds an attachment. Nothing was sent in either case.

### Identity seeding

A harness's system prompt carries values about the user: a working directory, a git author. The daemon reads these once at start and adds them to the chat dictionary, so they are tokenized in chat even though no dataset knows them: the account's full name, `user.name` and `user.email` from the global git configuration (`~/.gitconfig`, `$XDG_CONFIG_HOME/git/config`), the login name, and the home directory's own name. The last two are used only when distinctive (four or more characters, not a generic account name such as `admin` or `ubuntu`, not an ordinary word). A change needs a daemon restart. **What is not covered:** the full names and the email also refuse a tool definition that contains them, but the login and home directory names do not, so a login name inside a tool description (a path such as `/Users/<login>/…` in an MCP tool's text) is forwarded in clear, because refusing every request for a path under the home directory would make the proxy unusable. Definitions are scanned, never rewritten. `[proxy] definitions_account_values = "refuse"` closes this gap: the login and home directory names then refuse a definition that contains them like the full names do, at the cost of refusing every request whose tool list names a path under the home directory. It is recommended with the `strict` profile; the default is `"allow"`.

### Activity and the journal

A forwarded request writes one activity record under the reserved dataset `inumaki-chat`; a refusal, a withheld tool result, and a tripwire hit write records too (kinds, checks, counts, never text). **The journal keeps only the blocks that missed the session cache**, which is what the turn added: resent history and seeded answers hit the cache and are not journaled again, so the journal is not a full transcript of what the provider received. A turn whose blocks all hit the cache writes a record with an empty payload. Revealing a chat journal entry restores dataset tokens through their namespaces; session tokens show as unresolved. The same awareness as the gateway journal applies: a missed identifier is in the journal in clear, and it already went to the provider.

### Known limitations

Each is stated with its reason. None is a silent gap: the limits are the price of a rule that keeps requests valid for the provider, or they are costs the design has not removed yet.

- **(a) Signed, cited, and reasoning text is forwarded byte-identical.** Text at the real `cited_text`, `summary_text`, `thinking`, and `search_result.source` positions is scanned for known originals only (a hit refuses the request, or withholds the tool result that holds it) and otherwise forwarded as received; signed and encrypted fields (`signature`, `encrypted_content`, `encrypted_index`, `redacted_thinking.data`) are not scanned at all. Reason: signed or cited text cannot be rewritten without making the provider reject the next request. So an IBAN or an unknown name inside a real citation passes: only values already known to a dataset, the session, or the identity are caught there, not NER or validated identifiers. A thinking block the provider wrote in an earlier answer is not blocked even if it contains a known original.
- **(b) JSON numbers are never changed or scanned.** A card or phone number sent as a JSON number, or a tool call whose arguments hold only numbers, crosses unchanged. The response tripwire does not scan numbers in tool arguments either. Reason: changing a number would change its type, and the engine works on text.
- **(c) Object keys are sanitized only inside tool inputs, definitions, and caller-keyed maps** (`metadata`, `prompt.variables`). A key elsewhere in a body, for example under an unknown parameter, is forwarded as received. Reason: keys are API vocabulary, and a request whose keys changed would be rejected.
- **(d) Structural fields are trusted only in their API value shapes, with these residuals.** A UUID under any `id` or `*_id` key; a versioned type name such as `name_19800101` (the `snake_case_YYYYMMDD` rule cannot tell a date of birth from a tool version); and a single bare word inside a structural configuration subtree (`"tool_choice": {"name": "sarah"}`). Each is much narrower than free text (no whitespace, no `@`, one token), and they cross unsanitized. The reverse cost: the item ids of `shell_call` and `apply_patch_call` items have prefixes that are not yet in the id table, so they are treated as data and go through the engine, where they normally pass unchanged; this costs a pass and is not a leak.
- **(e) A placeholder can make the provider refuse a request.** A withheld tool result replaces the whole value; for an object-typed `computer_call_output.output` the provider rejects the placeholder string (an upstream `400`). This is a failed request, not a leak.
- **(f) Error bodies and non-JSON answers.** A non-JSON upstream error body (status 400 or higher) is relayed unchanged, since it can only echo tokens; JSON error bodies get session tokens restored. A 2xx answer that is not JSON is refused with `502 upstream_unreachable`, and none of it is relayed.
- **(g) The tripwire never blocks visible text.** A known value the model writes in its visible text is recorded (check `ClearValue`) and shown to the user, because it is local. In `block` mode, a known value in a tool-call argument answers `451 privacy_block` and none of the answer is relayed. The tripwire uses known originals only, not the validated-regex tier, so an identifier the model invents is not a hit.
- **(h) Redirects and encodings.** An upstream `3xx` answers `502`, the `Location` is never relayed (a client that followed it would resend its unsanitized body and credentials to another host), and the upstream client never follows redirects. An upstream answer with a `Content-Encoding` other than `identity` answers `502`.
- **(i) Memory.** Worst-case resident memory is `max_inflight` (32) times up to 16 MiB of raw plus decoded body while a request is decoded, plus the scan admission budget (about 1 GiB of scan heap; a body takes 64 permits per decoded byte), plus the cache budget (`cache_bytes`, 256 MiB by default). The scan of an upstream answer takes weighted permits from the same budget and waits for them for up to `min(upstream_timeout, 10 s)`, so answers are scanned within the figure above. A streamed answer is capped at `max_request_bytes` like a whole one; an event over 64 KiB (counting the largest open argument channel it may end) takes permits the same way and gives them back before the client is waited on, and a stream whose wait runs out aborts instead of answering `503`. If the wait runs out, the client gets `503 resource_limit` with the message "The request was sent; the answer could not be checked in time and was withheld. Retrying will resend it.": the request had already gone upstream, so its cache commit stands and the answer is lost, and a retry sends the message again. Lower `max_inflight` and `max_request_bytes` on a small machine.
- **(j) The client header value is a per-install secret** stored in the vault as `inumaki-chat/proxy/client_key` and written by adapters into harness configuration (see above). It is generated once and read back on every start; this version has no command that rotates it, and the secret's name is the only handle on it.
- **(k) Attachments are not inspected, in any mode.** By default they are removed and not sent (see "What is sanitized"); with `binary = "forward"` (alias `allow_binary = true`) image, document, audio, and file payloads cross unchecked, with no detection on them, and text inside an image or a PDF is not detected. In `placeholder` and `refuse` modes a tool result that holds an attachment is withheld whole; with `forward` it crosses like the rest.
- **(k1) Removing an attachment has costs.** The model loses it, and there is no OCR, so a user who expected the model to read a screenshot learns this only from the model's answer. A tool result with an image loses its text too, because the whole result is withheld. A removed Messages part drops its `cache_control` breakpoint for that turn. Base64 that does not start with `data:` (embedded mid-text, under an unknown key, a Responses `image_generation_call.result`) and data URIs inside JSON-text function arguments are sanitized as text, not treated as an attachment.
- **(k2) What the attachment rule does not reach.** The list of attachment types is closed: a content type that a provider adds later is sanitized as text until it is listed. An object key goes out as written (a data-URI key, or a name used as a key). A file reference in a definition (a code-interpreter `container.file_ids`) is scanned as definition text and forwarded; an `image_generation` `input_image_mask` refuses the request in every mode except `forward`. A binary-typed object inside a tool or schema definition (for example a Swagger-2 `{"type":"file"}`) refuses every request that carries the tool, in every mode except `forward`. Replaced parts are counted in the `released` record once per session; their memo keys share the 1,024-entry session memo with withheld tool results, so many distinct attachments evict older entries and an evicted attachment counts again.
- **(l) A restart loses session mappings.** The next turn re-sanitizes the resent history (which the harness holds restored) with new tokens; tokens left in earlier output that was never restored stay tokens. The first turn after a restart, or after the session expired (`session_ttl`), also loses the seeded and incremental cache, which live in memory, so it costs an engine pass over the whole history: seconds for a long conversation, and more on the Responses and `/codex` wire, which carries about 2.5 to 2.9 times as many strings as Messages for the same text. Later turns pay for the new text only.
- **(m) Seeded reasoning and citation text is checked only against values minted after the producing request's claim (its session-dictionary position, read before that request minted).** A value the provider wrote in clear in a signed or cited block before that stays forwarded, because signed text cannot be rewritten and the provider already holds it. A value the producing request held (including a dataset value) is not re-checked, since the provider saw it only as a token; the seed's dataset claims are transitive, so a value forwarded in clear under an exemption keeps that exemption for the next answer's seeds.
- **(n) The dictionary automata keep copies of originals in memory that cannot be wiped.** The session, dataset, and identity matchers are Aho-Corasick automata, and the library keeps its own copy of the pattern bytes. This is the limit core's `check_leak` documents for the verifier. Every copy the proxy and core make themselves is `Zeroizing`, except the transient buffers of core's `transliterate`. The store-owned leak index (roadmap 4d) is the same: its patterns are `Zeroizing`, but the automaton built over them keeps its own copy of the pattern bytes, in every tier, for as long as the index lives (the lifetime of the cached dictionary above).
- **(o) Dataset matches in step 2 and in the first pass resolve longest-first.** They use the host's resolved detector (`ProxyHost::dictionary` is type-erased), not `detect_all`. A longer preserved dataset match can hide a shorter one inside it. Identity matches report every overlapping match (`detect_all`). Session matches resolve longest-first in the first pass; the leak check after it examines every overlapping session match, so a shorter value a longer match hid is caught (closure re-run or refusal) and never forwarded in clear. Closing this needs a trait method across `inumaki-proxy`, `inumakid`, and `inumaki-vault` (M5 residual).
- **(p) Dataset coverage of a cache entry is keyed on the token string, not on its dataset and epoch.** The host's `resolve` and `dataset_token` do not say which dataset or epoch a token came from. If two datasets share a token string and a scope change makes it resolve to the other dataset's value, a cached leaf can read as already checked against that value.
- **(q) The tripwire uses full originals only** (decision 20), not name parts or closure forms. A model that writes only a first name of a known person in an answer is not a hit. Its dataset ORGANIZATION check spans every live dataset, so an identifier-shaped match from one dataset can make another dataset's ORGANIZATION row count (errs toward recall).
- **(r) Scanned leaves refuse more often.** A scanned leaf in a user turn or in assistant reasoning now refuses (`451`, check `ClearValue`) when it holds a name part or a preserved value the session holds, or a host or identity value the policy does not preserve; a tool result is withheld instead. Closure rounds re-check seeded leaves against every view entry, so a conversation whose signed reasoning quotes a value the producing request held can see an intermittent false `451`. A token-shaped string in a scanned leaf that the view does not resolve counts as forged. All of these are precision costs.
- **(s) An availability race.** When a hits-only request meets an empty view while another request on the same session mints at the same moment, the request is refused rather than forwarded unchecked.
- **(t) A value equal to a built-in kind label word hides inside a forged marker of that label.** A store value such as an ORGANIZATION named "Person" is not detected inside a forged `<PERSON_REMOVED>`, because the label is a real kind word. The value is a bare kind word, not an identifier.
- **(u) Streamed reasoning and citations are not restored.** They pass unchanged, so a client that renders them shows tokens. Only Responses `reasoning.summary[].text` of a completed item is recorded as provider-written. Whether a provider signs `reasoning.content[].text` is an open question (it is neither restored nor recorded); it stays open until the user-gated runs of plan M8-3.
- **(v) Shell, patch, computer, and MCP items: what is still open.** Every string and key of these items except `id`, `call_id`, `status`, and `type` (so `action`, `operation`, `arguments`, and any variant field such as a top-level `command`; an `mcp_call`'s `output` too) is restored by the arguments column, tripwired, and withheld in block mode on both paths; a text is checked once per kind, so text seen as a plain string is still checked as JSON arguments when it appears as such. Residuals: on streams a key of these items (an `env` variable name, a field name) is tripwired but not restored, so a token there stays a token (a re-serialized event is not re-parsed, so a restored key could collide); events of these items whose shape is not known offline (diff or command deltas, any event of the item carrying more than ids) abort the stream instead of passing, so a provider that streams them fails closed until their shapes are confirmed by the user-gated Codex runs of plan M8-3; an `mcp_call` is run by the provider against a remote MCP server before the answer arrives, so withholding it stops the client's view, not the call. Item types not named here pass as before (unknown `*.delta` events of other types, such as audio transcripts and logprobs, pass untouched).
- **(w) Notify mode does not hold a streamed tool call.** With `tripwire = "notify"` the arguments of a streamed tool call are forwarded as they arrive and the hit is recorded when the channel ends; only `"block"` withholds the call. A streamed answer is scanned per channel, so it can produce more `ClearValue` records than the same answer would whole (one per channel that hits, and one per differing repeat).
- **(x) The effectiveness of the released-block skip is unmeasured.** The gateway releases per field while the proxy's leaf is the whole tool-result text, so a match is likely only for text the hook sanitized. A one-off timing of the re-check on a 20 KB block was 11 to 14 ms in a debug build against 75 ms for the same block through a test engine with no NER model; the real engine costs more. The table keeps at most 65 536 entries, and once it is full with no expired entries each insert costs a linear pass under a mutex.
- **(y) A Chat tool call without `index`** falls back to its position in `tool_calls`; a provider that omits `index` and streams several calls in separate chunks would merge them into one channel. Restoration still works per token; only the end-of-channel JSON check is skipped when the merged text does not parse. A stream also drains until the upstream closes after the terminal event (up to the idle timeout), and drops anything that arrives.
- **(z) Request headers pass by a per-upstream allowlist, and local paths in harness text pass unless a detector catches them.** The proxy forwards only the request header names it lists for the upstream (M8 spec §20 amendment of 2026-10-12) and the names the user adds under `[proxy.upstreams.<id>] extra_headers`. For every listed name except credentials (`authorization`, `x-api-key`, `chatgpt-account-id`) it checks the value against a shape (an id, a word, a list of words, a media type, a product-style `User-Agent`) and drops a value that fails. Dropped headers are counted in the log by a closed label (never by the received name or value); a header a harness adds in a later version is dropped until the list is amended or the user names it. It always removes hop-by-hop headers (and any header a `Connection` header names), `Host`, the body-framing headers (`Content-Length`, `Content-Encoding`, `Accept-Encoding`, which it sets to `identity`), every `X-Inumaki-*`, and Codex's `x-codex-turn-metadata`, and `extra_headers` cannot re-enable them. `x-codex-turn-metadata` is stripped (ruling L58, M8 spec §5.8 amendments of 2026-10-10) because, when Codex runs inside a git repository, it holds the repository root's absolute path (with the login name and the project's directory names), the fetch remotes' host, organization, and repository names, and the HEAD commit hash, and no detector looks at headers; its copy in the body, `client_metadata["x-codex-turn-metadata"]`, is removed before sanitizing, but only as the member of the top-level `client_metadata` object on the Responses wire; the same key anywhere else (a history item, a nested object, a Chat Completions or Messages body) is ordinary text, sanitized like any other and in clear unless a detector catches what it holds. Residuals of the header allowlist:
  - The value rules are shape checks, not detectors. A `User-Agent` comment can carry words, so a name inside the parentheses passes (comments are kept because they hold the OS, architecture, and terminal). A single path segment such as `Users/x` still passes as a product. One bare word directly after a comment passes (the slot where Codex puts the terminal name), so a login name there (`p/1 (x) huber`) leaves the machine. A shape-valid value can be any single word, or a comma-separated list of words (`list` values), a harness or user chose; a name in `x-app` would pass.
  - What still leaves in allowed headers: `User-Agent` and the `x-stainless-*` headers name the OS and its version, the architecture, the runtime, and the terminal program; session, thread, and window ids let the provider link one conversation's requests, as they do without the proxy. Unknown names under `anthropic-*` and `openai-*` pass with list-shaped values.
  - Credentials and `extra_headers` values are not checked. A header the user lists that carries a path or a name sends it.
  - A value that is shape-invalid but legitimate is dropped: a `x-codex-turn-state` in standard base64 with a `/` (Codex then falls back to an unpinned backend for that turn, a cache miss), or a user agent with more than one `/` in a word (the Vercel AI SDK; harmless with an API key). A header a new release needs and the list lacks degrades a feature or draws an upstream 4xx, visible to the harness.
  - What a Claude Code subscription (OAuth) login sends was not recorded, nor the Codex ChatGPT login's header names; a header those need and the list lacks is dropped.
  - Dropped counts are in the log only, not in `GET /v1/proxy` or `inumaki status`. Response headers are still relayed by exclusion; they come from the provider.

  Separately, harness context that is text in the body carries local paths with the login name: Codex's `<environment_context>` names the working directory (`cwd`), and Claude Code's system prompt holds the working directory and a git status. These are ordinary text leaves: they are sanitized like any other text, so a login, client, or project name in them is tokenized only when a detector (the identity seed, a dataset, the model) finds it, and crosses in clear otherwise.
- **(aa) Closure projection rests on the hit premise (roadmap item 4d).** When the leak closure opens a *cached* leaf only because the store grew, the leaf is no longer re-run through the whole engine. Instead, the new values in clear in the cached sanitized text are replaced by their tokens, and the result is re-checked deterministically: real tokens, the leak check, a regex re-scan, and the host and identity dictionaries. Every check that can abandon runs before anything is minted (M8 spec §20, amendment of 2026-10-12); the consistency check after the mint fails the request, it does not abandon. Nothing becomes clear that was not already clear in the cached text, and this is checked on every projection. What the full re-run could still add are context effects: a word that the verifier's NER re-scan or the `strict` retry would flag only now that a token sits near it, or the rest of a preserved organization or URL that holds the new value. Those bytes already crossed on this upstream route under this session key, and that premise is what the proxy relies on. It does not bind the provider account: two clients with the same first system and user text share one session under the content-fallback key. Leaves verified in the same request are never projected. Rewriting a cached leaf, by projection or by the full re-run, puts the entity's token where the provider saw the clear value one turn earlier. Comparing the two sends links that token to the value for the whole session, including content that this turn tokenized with it. This is pre-existing in the closure. Projection can link more often, because the full re-run sometimes tokenizes a wider span under its own, unlinked token. Round 0 scans a cached seed as received, so a seed in NFD that holds a value may not be opened. This is pre-existing and changes no privacy property, because the provider wrote every byte of the seed.
  - **Measured residual: words left in clear next to a token (D1).**
    - *What it is.* The full re-run folds a store match into any detected or preserved span it overlaps and tokenizes the union; projection replaces the store's forms only. So a first name next to a projected surname, or the rest of a preserved organization, e-mail address, URL or address that a token cut, stays in clear where the full re-run would have tokenized it. Concretely, for a PERSON: when a surname is stored after the cached text was sent, projection tokenizes the surname and leaves the adjacent first name in clear (first name plus surname token), where the full re-run would send one token for the whole name. The first name is clear in the cached text and has already left.
    - *Measured* against the full re-run, in 528 projections of the proxy bench: EMAIL 434, ORGANIZATION 1 062, PERSON 381, STREET_ADDRESS 107, CITY 1, INVOICE_ID 4; in 3 559 projections of the differential harness: ORGANIZATION 162, STREET_ADDRESS 38, PERSON 35, CITY 23, EMAIL 18, INVOICE_ID 5; and URL 2 in the adversarial fixtures.
    - *Why it is covered.* Every such word is clear in the cached text, which is checked on every projection (0 violations: the production byte invariant in the 528 shadow projections, the weaker word-set check in the 3 559 harness cases), and that text already left on this route under this session key. Projection never reveals a byte that had not already left in clear; it does not add the tokenization the full engine would add for preserved kinds and union remnants. The newly stored value itself is always tokenized. No new value leaves.
    - *The cost* is one of quality, not privacy: the same person can then appear in one session under different shapes, a full-name token in newly sanitized content and a first name plus surname token in the projected history, so the model may not tell that they are one person.
    - *The direct check.* The differential harness also checks each such word: every word of a D1 replacement that projection keeps in clear must be a clear word of the cached text, a hard check with 0 allowed outside (in a smoke run of 209 harness projections, 33 such words were checked, 0 outside). It restates the harness's word-set invariant for those words only (it cannot fail unless that invariant fails too), so it adds a visible count, not independent evidence. Like the D2 check below it is set-based, not positional, and blind to runs of fewer than two letters; the production byte invariant is the real gate.
    - *Limit.* Where the hit premise does not hold (see above), this residual is not covered.
  - **Measured residual: forwarded where the full re-run blocks (D2).** In 17 of 3 559 harness cases the full re-run blocks on the NER re-scan flagging a PERSON, and projection, which runs no NER re-scan, forwards. In each, every clear word of the full re-run's candidate is a clear word of the cached text (442 words checked, 0 outside). The check is a superset over words, because the flagged span's range is not public; it is blind to runs of fewer than two letters (initials, digits), and it is set-based, not positional. The production byte invariant is the real gate. The proxy bench produced no D2.
  - **Harness limits.** Its "projected" count is an upper bound on production (its caller check always passes; production also vetoes on host and identity matches), it samples the first 8 capitalized words of a document, and its invariant is word-based. Its hard checks on every projected case: no store form in clear by the projector's own consistency dictionary, the word-set invariant, the D1 and D2 word checks, and (added after the 12-shard run, so far a smoke run only: 209 projections of sources (i) and (ii), exit 0) no leak by the verifier's leak check, built per call and so independent of the store's leak index and of the projector's dictionary (0 leaks in any source; the same check fires on the cached text, which still holds the new value, in 208 of the 209 cases, and the one exception is a value made only of greeting or sign-off vocabulary, which by design has no leak pattern, Task 7d, ruling L56).
  - **Deferred (not built):** projecting leaves verified in the same request needs the settling pass's replacements, a guard against `merge_redaction` widening, neighbour guards, and a zero-divergence gate over about 2 000 cases; wiring projection into `inumakid` (the hit premise does not hold there, so it is the same case); a closed-epoch eviction that does not force a full rebuild of the vault namespace's dictionary and leak index (it clears at once, by Task 7e's design); and widening a projected surname's token over the first name next to it. That widening is not built because the first name already left under the hit premise, and it would either put the token over a word the store does not map to it (rehydration would restore only the surname, or the wrong person if the first name belongs to another stored entry) or mint a new value inside projection, which is the union problem deferred with same-request projection. The middle tier is rebuilt whole on each merge, so merge time grows with very large namespaces (merge p99 18.5 and 18.9 ms in the two instrumented `support-email` bench runs and 23.3 ms in the `offline` run; the `offline` session store reached 14 007 entries in an earlier measurement at `7a9b40c`, per the L3 quality doc, and this item's runs did not count entries).
  - **Reason order.** The leak check returns its reasons in a canonical order. This changes the visible order of the kinds in a withheld result, a refusal or a record, and which kind is recorded as the single withheld reason for a file name in `inumakid`. It discloses nothing; 10 eval runs found no difference in verdict or reason set.
- **(bb) The static-prompt NER cache is shared across sessions of trusted clients (M8 spec §20, amendment of 2026-10-12, Part 1).** A harness's static system text is the same in every new session. When `[proxy] static_cache` is on (the default), the proxy keeps the NER models' output for it in memory, for requests that carry a valid client header (decision 23) only: system and developer leaves of at least 2 KiB, plus the verifier's re-scan of their masked candidate, in a separate key namespace. A new session that sends the same bytes skips only the model inference. The rest of the engine runs again in the new session, with that session's tokens and store: dictionaries, detectors, policy, minting, the consistency pass, the leak check, the regex re-scan, the retry, and the closure. So what is sent is what the engine would send without the cache, assuming the models' inference is deterministic. A models-gated test checks that across session-pool slots and concurrent calls, and a differential gate over the eval corpora checks it end to end with 0 differences allowed.
  - *Residual.* If inference were not deterministic, a span scored close to a threshold could come out differently on a fresh run, and the cache freezes one run's result. A local prober able to evict and refill an entry could also choose which run's result is frozen; with the client-header gate that prober is a same-user process.
  - *What is kept.* Span offsets, kinds, confidences, and detector ids, under a keyed hash of the exact input. No text, slice of text, token, or original is kept, and nothing prints the entries. Nothing goes to disk. Normal routes are not dataset-scoped: one cache serves every dataset the proxy sees. It is cleared on restart and whenever the dataset set, an epoch, a detector, or a known-entity count changes (counted as `static_cache.clears`). At most 256 entries and 8 MiB.
  - *What it can leak: membership, by timing.* It reveals whether a given text, byte for byte, was processed since the entry was created. A prober that can enumerate candidates (a known template with a small set of candidate values, for example a name, an email, or a working directory inside a harness's or an app's system text) can confirm which one was processed, one probe per candidate. The proxy's `X-Inumaki-Latency-Ms` header makes the timing exact, and no provider credential is needed. Any system or developer leaf of at least 2 KiB qualifies, including dynamic system text an application builds from business data.
  - *Who can probe.* Only a caller with the client header. A process of another OS user cannot read it (unless the harness file is world-readable), so it cannot probe; a same-user process can, Easy mode's stated limit. Requests without the header run the models and never touch the cache.
  - *Eviction.* A trusted prober can evict entries by sending 256 eligible leaves; that costs it the model time and costs other sessions their speed-up, not their privacy.
  - *How this compares.* The content-fallback session key (two clients with the same first system and user text share one session), the per-process clean-definitions set, and the released-block set are older channels of the same kind.
  - *Turning it off.* Set `[proxy] static_cache = false`.
  - *Measured.* The A/B in `docs/quality/2026-10-12-timing-and-prompt-cache.md` (after the rebase, on a shared machine) shows the speed-up: a new session's cold turn costs about 10 to 13 % of the same turn on a build without the cache (`support-email` `codex` 426.8 and 418.3 ms against 3935.2 and 3133.1 ms; `fast` `codex` 117.3 and 133.8 ms against 1126.4 and 1386.6 ms), and the time saved is all engine time (the engine stage is about 99.9 % of a cold turn). The timing overhead target (`offline`, p50 and p95 within 3 % or 1 ms) was missed on the two required rounds and is inconclusive under noise, and the `offline` cold turn is 8.6 to 17.3 % slower on the new build for a reason not isolated; both are open. The equality checks are recorded in that document's "Equality gates" section. The determinism test (at pre-rebase `e1179ba`) found 0 differing results over 12 detector-and-input pairs at 12 calls each. The memo-on/off differential (at pre-rebase `7a08bce`) found 0 differences in forwarded output and equal refusals over 802 documents (3 208 requests, 2 327 memo hits, 8 release shards), with a hit in every second-session document. The first session after a start or a dictionary change still pays in full.
- **(cc) Per-request timing is local metadata (M8 spec §20, amendment of 2026-10-12, Part 2).** `GET /v1/proxy`, `inumaki status`, and the daemon log hold per-request stage durations: the last request, the median, and the 95th percentile over the last 64 requests. A stage duration grows with the size and the entity density of the text (`engine_ms` especially), so a reader of the status or the log learns roughly how large and how name-dense recent requests were, and whether the static-prompt cache was hit. The control socket and the log are readable by the same OS user only, and the log already carried each request's total duration. The timing fields carry no text, token, key name, or digest.
- **(dd) The leading system prompt of a trusted request is read as harness text (M8 spec §20, amendment of 2026-10-20; rulings L107, L120, L122; built on branch `l2/origin-wiring`).** The proxy tells the engine that a text leaf in the leading system prompt of a request with a valid client header is harness-static text. The leading system prompt is the Messages top-level `system`, the Responses `instructions` together with the leading run of system and developer `input` items, and the leading run of system and developer `messages` of a Chat Completions request. The run ends at the first item that is not a system or developer message: a user, assistant or tool message, an unknown role, a role-less item, a typed item, or an item that is not an object. That trust is bounded by what the origin changes in the engine, and nothing else:
  - *What changes (what `HarnessStatic` relaxes).* The sanitizer drops a model `PERSON` span below 0.85 that is a lowercase vocabulary word which is also a surname (`rust`, `page`) standing alone, or a CamelCase-glued identifier with no first-name part (`HuberMaier` as one token); the verifier does not fail on a bare `Claude`, `Codex`, `Opus`, `Sonnet` or `Haiku` with no placeholder next to it. A real name of exactly those shapes in that position crosses in clear unless another detector catches it; the verifier's NER re-scan stays the backstop for the first two, and identity seeding still tokenizes the account's own login and home-directory names. Capitalized names, emails, numbers, identifiers, dataset and session values are detected as before.
  - *Where the trust ends.* Trusted clients only, and leading positions only. Restricted requests stay free text in every position: an unknown local process (a harness set up by hand, an application that puts business data in its `system` field) gets no relaxation. Codex's responses-lite `additional_tools` item (its tool definitions, checked as definitions) continues the leading run when it is a developer item; any other typed item ends it. System and developer items after the leading run are free text too, and so is a Chat message's `name` and any off-shape value of a structural key inside a leading item (everything else under a leading item inherits the reading), and so are user turns, tool results, tool inputs and assistant text, including harness text that arrives there (Claude Code `<system-reminder>`, Codex `<environment_context>`). Check routes and the gateway, mirror, hook and mail paths never pass an origin.
  - *Residual: the leading prompt is not purely static.* A trusted harness's leading system prompt can carry an environment block, git status, a configured instruction file or, for an application the user gives the header, business data. All of it gets the harness-static reading, and the proxy cannot tell these apart by position (it does not guess from the text, ruling L60). Two cases are known. (i) Names in the dynamic part. Measured with a Claude Code-shaped prompt plus an environment block (Messages, trusted): a capitalized name is tokenized in every position tried, and the proxy's result equals the engine's `HarnessStatic` result (five positions: a `Git user: Sarah Leitner` line, the working directory as `/Users/Leitner/project`, `/Users/Sarah.Leitner/project` and `/Users/Sarah Leitner/project`, and a commit subject). A lowercase surname in a working-directory path (`/Users/huber/project`) or in a branch name is left in clear under both origins (0 of 4 candidates tokenized as harness-static text, and 0 of 4 as free text, against a baseline prompt that both origins accept). That gap was not caused by the origin: it was the "names in structured positions" gap listed above under the L3 residuals, which existed on main for every proxy request, and neither `HarnessStatic` nor the lowercase-word drop of ruling L98 is involved. *Updated 2026-10-20 (structured positions, ruling L127):* a home-folder login is now a detected `PERSON` in both origins, so `/Users/huber/project` is tokenized and rehydrates to the original path (a proxy-free engine round trip is tested under `Free` and `HarnessStatic`), and the verifier's home-folder login check refuses one left in clear; Codex's environment text has the same shape and the same cover. Still in clear: a lowercase surname in a branch name, and one in a path with no home root or other cue (`/projekte/huber/`); the rest is under "Structured-position residuals" above. (ii) A false positive minted in the leading system prompt is tokenized across the whole conversation (the context's referential consistency; it fails closed and costs tokens, not privacy). Example: the role word `assistant` in a short system prompt such as "You are a helpful assistant." is read as a `PERSON` under either origin (ruling L126; the false positive is on main already, queued for lane L3), and the same word is then tokenized in the user turns.
  - *Measured, before the final gate.* The harness-origin gate (`crates/inumaki-proxy/tests/harness_origin_models.rs`, release, 2 shards, at `46a8de9`, pre-rebase `4182230`; the final gate re-runs it, record in `docs/quality/2026-10-20-origin-wiring.md`): over 95 inputs, a trusted request's forwarded system leaf equals the engine's `HarnessStatic` result and a restricted one's equals its `Free` result, with 0 mismatches. 22 inputs differ between the two readings; the forwarded system leaf holds 88 `PERSON` tokens for trusted requests against 298 for restricted ones, and refusals are 0 against 1. A name in a trusted request's user turn is tokenized, and harness text sent as a user turn equals the `Free` result. The gate sends each input as Messages top-level `system` or Responses `instructions`, so it measures the top-level positions; the leading run of `input` and `messages` items is covered by the unit tests (`walk::tests::only_the_leading_system_prompt_is_leading` and `origin_tests`), not by models.
  - *Separation.* The session cache keys on the origin, so a leading-prompt entry never answers a user-turn leaf with the same bytes; the static-prompt cache serves harness-static leaves only, and a `Free` leaf never reads or writes it.
