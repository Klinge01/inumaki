# M5 Task 0: TCC spike (LaunchAgent vs SMAppService folder access)

Run on 2026-10-09 with the user present and consenting, on macOS 27.0.1 (build 26A434), Apple silicon. Both probes are ad hoc signed (`codesign -s -`, no team identifier), as the MVP ships (M6 spec §2 decision 4). The probe binary reads one file, `~/Documents/inumaki-tcc-probe/probe.txt`, and appends `ok <n> bytes` or the `io::ErrorKind` and errno to a log. No USB volume was attached, so the `/Volumes` column was not tested.

## Results

| | Bare LaunchAgent (`~/Library/LaunchAgents/inumaki.tccprobe.plist`) | `SMAppService.agent` inside `TccProbe.app` (`dev.inumaki.tccprobe`) |
|---|---|---|
| Prompt shown (`~/Documents`) | yes, names the binary (`tcc-probe-bin`) | yes, names the app (`TccProbe`) |
| Read while the prompt is open | blocks: the process stays in `open()` until the user answers (`launchctl print`: running, never exited) | same |
| Result after Allow | `ok 6 bytes` | `ok 6 bytes` |
| Grant survives a restart of the job (same code) | yes, no new prompt | yes, no new prompt |
| Grant survives a new code hash (rebuilt binary, re-signed ad hoc) | no: a new prompt | no: a new prompt, after re-registration (below) |
| Replacing the binary in place | works | the job is killed: `OS_REASON_CODESIGNING` when the file is overwritten (same inode), `EX_CONFIG` (78) after a fresh copy and re-sign, until `unregister()` + `register()` |
| `/Volumes/<usb>` | not tested (no volume) | not tested |
| Identity listed in Privacy & Security | not inspected during the run | not inspected during the run |

`register()` returned status `1` (enabled) both times; no Login Items approval was requested.

## Findings

1. **A launchd job does get the prompt.** The spec's worry that "a daemon started by launchd may never show the prompt" does not hold on macOS 27.0.1, for either form.
2. **The first read blocks until the user answers.** A mirror worker that opens a protected file waits inside `open()` for as long as the prompt is on screen. Nothing in the daemon may wait on that worker without a timeout (API handlers, the check runner's 30 s wait, shutdown), and a folder whose first read is pending should show `pending`, not hang the status endpoint.
3. **Ad hoc signing loses the grant on every upgrade, in both forms.** The grant is bound to the code hash. This confirms the §9.1 ruling: after every upgrade the app re-checks every folder and shows the grant card again.
4. **An `SMAppService` agent must be re-registered after an upgrade.** Replacing the bundled binary leaves the registered job unrunnable (`OS_REASON_CODESIGNING`, then `EX_CONFIG`) until the app calls `unregister()` and `register()` again. Replacing a signed binary in place (same inode) is killed by the kernel in either form; installers must write a new file and rename it over the old one.

## Recommendation (integrator ruling, 2026-10-09)

Keep `inumakid` as the bare LaunchAgent that M6-3 part B1 already installs, for the MVP. Both forms lose the grant on an ad hoc signed upgrade, the prompt for the bare agent names `inumakid`, which a user can recognize, and moving the daemon into the bundle would add a re-registration step to every upgrade without saving a prompt. Revisit when releases are signed with a Developer ID: a stable designated requirement is the likely way to keep grants across upgrades (not tested here), and at that point the bundled `SMAppService` agent gives the nicer prompt name and ties the daemon's lifecycle to the app.

Carried to M6-3 and the mirror: findings 2 and 4 (no unbounded waits on a first protected read; upgrades replace binaries by rename, never in place). The §9.1 picker-warning fallback is not needed, since the prompt works; it stays as guidance for users who deny the prompt.

## Cleanup

Both agents were booted out and the `SMAppService` agent unregistered (`unregistered`), the plist, the app bundle, the probe sources and `~/Documents/inumaki-tcc-probe` were deleted. `tccutil reset SystemPolicyDocumentsFolder dev.inumaki.tccprobe` failed with `-10814` because the bundle was already gone, so the grants for `tcc-probe-bin` and `TccProbe` stay listed in System Settings → Privacy & Security → Files and Folders until the user removes them.

## G3 follow-up: what blocks while the prompt is open

Run on 2026-10-11 with the user present, same machine and macOS version as above. The probe (`tcc-probe-g3`, ad hoc signed) runs one step per `launchctl submit` job against `~/Documents/inumaki-tcc-g3`, a folder holding one synthetic file, and logs when each step starts and finishes. The first run's prompt was answered within 3 s, so the open-prompt steps were repeated with a second copy signed under a new identifier (`tcc-probe-g3b`), which got a fresh prompt.

| Step | Before any prompt | While the prompt is open | After Allow |
|---|---|---|---|
| `lstat` on the folder | done in under 2 ms | done in under 2 ms | – |
| `realpath` on the folder | done in under 2 ms | done in under 2 ms | – |
| FSEvents watch on the folder (registration only, then 3 s idle) | `Ok`, does not block | `Ok`, does not block | – |
| First directory listing | raises the prompt | blocks until the user answers (23.6 s in this run) | `Ok`, about 10 ms |
| Read the first file | – | – | `Ok` |

Findings:

1. Only reading inside the protected folder (listing, opening a file) waits on the prompt. `lstat`, `realpath` and registering an FSEvents watch return at once, granted or not, so arming watches and resolving folder paths at daemon startup or on `folder add` cannot hang on an unanswered prompt.
2. This confirms finding 2 above: the first listing or read blocks for as long as the prompt is on screen, so the mirror worker's first scan must stay off any path that waits without a timeout.
3. Not tested: whether FSEvents delivers events for a folder whose grant is still pending or denied (only registration was timed), and `/Volumes`.

Cleanup: the jobs were removed, the folder, binaries and logs were deleted. The user removes the `tcc-probe-g3` and `tcc-probe-g3b` entries in System Settings → Privacy & Security → Files and Folders by hand.
