# inumaki architecture

inumaki is a local privacy boundary between business applications and cloud LLM providers. This document is the map: crates, the pipeline, the token store abstraction, the service and its vault, and where to extend. This file describes what is built.

## Crates

| Crate | Depends on | Holds |
|---|---|---|
| `inumaki-core` | nothing that does IO | entity kinds and spans, detectors (regex with checksums, secrets, domain rules, dictionaries, names in paths and URLs), overlap resolution, policy profiles, the `TokenStore` trait with the in-memory `Context`, the sanitizer, the second-pass verifier, the rehydrator, the `Engine` |
| `inumaki-models` | core, `ort`, `tokenizers` | `NerBackend` (GLiNER span mode, BIO token classifier) over pooled ONNX Runtime sessions, chunking, `NerDetector`, the pinned model manifest and download, `BackendCache` |
| `inumaki-vault` | core, `rusqlite`, `chacha20poly1305`, `hmac`, `keyring` | the encrypted SQLite token store: datasets, epochs, `Namespace` (a persistent `TokenStore`), rotation and sweep, the known-entity detector; upstream rows, sealed secrets, hashed gateway tokens, chained activity records, the egress journal, and entity listing/forget (schema v4) |
| `inumaki-gateway` | core, vault, `rmcp` | the MCP gateway: upstream clients and their supervisor, the per-dataset catalog, field contracts, discovery metadata, the content path, resource handles, limits, the tripwire, activity records; reaches the engine only through the `Blocks` trait |
| `inumaki-proxy` | core, `axum`, `reqwest`, `tokio` | the model-API proxy: route table, the JSON scanner and the string-leaf rule, sessions and their caches, restoration of answers, fixed errors, status. Reaches the vault, the models, and the activity writer only through the `ProxyHost` trait |
| `inumakid` | core, models, vault, gateway, proxy, `tokio`, `axum` | the service: configuration, engines per profile and dataset, session contexts, the sanitization cache, the control API over a Unix socket, the gateway listener, the proxy listener and its `ProxyHost`, the shared socket client |
| `inumaki-mcp` | `rmcp`, `tokio`, `clap`, `dirs` | the stdio shim: relays an MCP client on stdio to `/mcp/<dataset>` over the control socket |
| `inumaki-eval` | core | hand-written cases, the synthetic generator, metrics, baselines |
| `inumaki-adapters` | no inumaki crate (`serde_json`, `toml`, `toml_edit`, `jsonc-parser`, `json5`, `yaml-edit`, `serde_yaml_ng`, `sha2`, `hmac`) | harness adapters for Claude Code, Codex, Hermes Agent, and OpenClaw: detection, format-preserving edits of their configuration files, backups and revert, drift status, and the pure parts of the Protect switch. Talks to no daemon: the caller fills `ConnectPlan` and `SystemState` |
| `inumaki-mirror` | core, `inumaki-mail` (renderers), `notify`, `rustix`, `csv`, `encoding_rs` | the folder mirror (milestone 5): watcher, queue, per-file pipeline, formats, names, reconcile, release check and tripwire, outbox, directory-handle file operations; reaches the engine and the manifest only through the `MirrorEngine` and `ManifestStore` traits, never `inumakid` |
| `inumaki-hook` | `inumaki-client` | the tool-result hook binary `inumaki-hook claude-code\|codex [--socket PATH]` for Claude Code and Codex, plus its library (payload parsing, output shapes, block templates) |
| `inumaki-cli` | core, models, inumakid, eval, adapters, client | `scan`, `tokenize`, `models`, `eval`, `bench`, `daemon`, `status`, `activity`, `dataset` (with `upstream`), `gateway token`, `doctor`, `sanitize`, `rehydrate`, `inspect`, `connect`, `folder` (see `docs/cli.md`) |

Dependency direction is strict: `core ← {models, vault} ← gateway ← inumakid ← cli`, `core ← proxy ← inumakid`, with `inumaki-mirror` (core and the mail renderers only) beside the gateway and `inumakid` driving it, and `inumaki-mcp` links none of them. `inumaki-adapters` links no other inumaki crate, `inumaki-hook` links only `inumaki-client`, and `inumaki-cli` links both next to the chain. The vault never sees a model; the core never sees a socket or a database; the gateway never assembles an engine or imports the daemon; the proxy never links the vault or the models.

`inumaki-client` — the control-API contract as Rust types (M6 spec §9), one JSON fixture per response shape, a Unix-socket client, and a mock daemon (feature `mock`). It depends on no inumaki crate. The app and `inumaki-hook` use it, and `inumakid`'s tests use it to check that the live router's bodies match the contract.

## The pipeline

```
text ──NFC──► detectors (rayon fan-out) ──► overlap resolution ──► link ──► policy ──► sanitize ──► verify ──► Pass | PassUncertain | Blocked
              regex · secrets · domain · dictionary · known entities · anchors · positions · NER        │             ▲
                                                                                                        └── retry once with the strict profile (same spans)
```

`Engine::process(text, &mut dyn TokenStore)` runs detection once. On a verifier `Fail` it reruns policy, sanitize, and verify with the retry profile over the same spans; the retry profile is validated to use the same detectors, so detecting again would only repeat work. A detector error blocks immediately. The verifier never sees the original text: it gets the candidate, the replacement ranges, and the token store's working set (for the leak check). Its checks, in order: leak check, regex re-scan, home-folder login check (`verify/home_login.rs`, a clear login after `/home/`, `/Users/`, `C:\Users\` or `~`), NER re-scan, combination heuristic (engine spec §6.5).

`positions` is `detect::path_names::PathNameDetector` (source `DetectorId::Position`, structured positions plan): names in paths and URLs read from their position (the login after a home root, the segment after `/team/` or `/people/`, a code-host account, `~login`, a first name plus a name part). It runs in every profile and origin and is sanitizer-only; the verifier's home-folder login check is its independent backstop and shares no code with it. Before overlap resolution a `URL` span is cut around the `Position` names it contains, so a preserved URL does not forward the name (engine spec §6.1, §6.2).

`link` (`inumaki_core::link::link_mentions`, plan 4a) runs once per document after overlap resolution. It takes the full PERSON names found in the document, in the batch's earlier blocks (`LinkScope`), and, only when `[linking] surnames_across_requests` or `first_names_across_requests` is on, in the store's recent entries; then it emits a PERSON span for each bare first name or surname that one of them has, linked to that person, or as its own entity when two candidates share the part. A three-letter part qualifies only when the first-name gazetteer (`gazetteer::is_first_name`) knows it. The anchor detector (`detect/anchor.rs`) finds names after greetings, sign-offs, and honorifics. `Engine::process_scoped` and `detect_scoped` take the batch scope; `process` is the single-document case.

## `TokenStore`

`sanitize`, the verifier's leak check, and `Rehydrator` are written against `inumaki_core::token::TokenStore`:

- `token_for(kind, original)` mints or reuses a token; `original(token)` answers for known tokens; `entries()` is what the leak check may scan; `record_removed` and `removed_entries` hold values taken out by a `Remove` action (never rehydrated); `prepare(tokens)` lets a lazily loading store fetch originals before a rehydration.
- `surface_token(parent, surface)` mints a surface form of an entity (another spelling, a bare name part, an alias variant): `<PERSON_a7f2c9_3e>` with `[tokens] surface_form = "derived"` (the default), an unrelated token with `"independent"`; it restores to its own text. `link_candidates(kind, window)` lists the full names used within the recency window for the linker's window tier. In the vault a surface row is an `entries` row with `surface_of` naming its parent token (schema v6); it never enters the known-entity automaton.
- `Context` (in memory, per session, `suffix_len` 4) implements it with the milestone-1 behaviour.
- `inumaki_vault::Namespace` (persistent, per dataset and epoch, `suffix_len` 6) implements it over SQLite with a bounded, zeroized working set of 4 096 decrypted entries. `entries()` is that working set; older known entities are covered on the detection side by the known-entity detector, so an undetected second copy cannot reach the verifier.

Token strings from the two stores differ in length, so a session token can never collide with a vault token.

## The service and the vault

`inumakid` owns everything expensive once: the models (`BackendCache`, one load per model file, a small pool of sessions each), one `Engine` per `(profile, dataset)` (a dataset's engine carries that dataset's known-entity detector), the vault, session contexts (`ContextStore`), and the sanitization cache. Requests come in as JSON over HTTP/1.1 on a Unix socket (mode 0600); engine work runs on the blocking pool.

The vault is one SQLite file (WAL, `secure_delete`, incremental `auto_vacuum`):

- `datasets` → `epochs` → `entries`; the current epoch of a dataset is the namespace requests write to; closed epochs stay readable for a grace period, then their rows are deleted by the sweeper.
- Every original is XChaCha20-Poly1305 encrypted under a fresh nonce with the token as associated data; lookups go through `HMAC-SHA256(index_key, normalized value)`, so neither originals nor normalized keys are stored readable.
- Keys live in the OS secret store (macOS Keychain, Linux Secret Service) or, when none is reachable, in `<data dir>/vault.key` (0600). The source is pinned in the vault's `meta` table and checked at open, as is a key fingerprint.
- Tokens are unique across all datasets and epochs (a unique index on `entries.token`); a rotation mints new tokens for every entity when next seen.
- Schema versions: v2 adds `upstreams`, `secrets`, and `gateway_tokens`; v3 adds `activity`; v4 adds `journal` and `entries.created_at`/`entries.uses`; v5 adds mailboxes and mail handles (plan 3); v6 adds `entries.surface_of`, the surface-form rows (plan 4a); v7 adds `folders` and `mirror_files` (the folder mirror, M5). Later plans take the next free version. `SCHEMA_VERSION` (`inumaki_vault`) is the current one; a v1–v3 file migrates through every intermediate step, one transaction per step.

The sanitization cache maps `(dataset, epoch, profile, configuration fingerprint, SHA-256 of the NFC text)` to the result; the fingerprint covers the parsed configuration values (canonically encoded, so comments, key order, and formatting do not count), the crate version, and every dictionary file, so a changed configuration never serves an old verdict. A hit costs one hash; entries of a rotated epoch are dropped; a cached result whose tokens the namespace no longer knows is discarded and recomputed.

`inumakid::service` (`sanitize_blocks`/`rehydrate_blocks`) is the shared path both the control API and, later, the gateway call for a dataset request that carries more than one block of text. It opens one `Namespace` lock for the whole batch rather than one per block, and looks each block up in the cache by `CacheKey` (`dataset`, `epoch`, `profile`, `DaemonConfig::fingerprint`, `sha256(NFC text)`; `crates/inumakid/src/cache.rs`) before running the engine on a miss. Before any block is released, `sanitize_blocks` re-checks every non-blocked block against what the namespace knows *now* (the same policy-aware re-check the cache hit path uses), so a full name a later block in the same batch — or a concurrent request — taught the namespace cannot leave in clear through an earlier block that was sanitized before that name was known. That release check matches known entities (full values). When a batch of two or more blocks changed the store (its epoch, or the per-process keyed fingerprint of its working set and removed values, moved), every non-blocked block is also scanned at the batch's end, outside its tokens and protected ranges, for the forms the engine's consistency pass searches (`StoreDict`: the working set's full values, PERSON name parts, transliterated and folded forms, removed values, every kind); an offender is sanitized once more with the batch's scope and withheld if a store form is still in clear, so a bare first name or surname that detection missed in an earlier block does not leave in clear when a later block mints the full name. The batch-end scan and the cache-hit re-check run the same dictionary: the namespace handle's own (`TokenStore::store_dict`, Task 7e), shared with the engine's passes, extended by each write and cleared with the working set on rotation, forget, and deletion, when a closed epoch's entry expires, and when the LRU evicts such an entry (an evicted current-epoch value's forms stay in it, never matched, until the next full build). What neither covers (forms of values outside the working set, a single-block batch, which is not scanned at its end, whose own second sanitize mints the full name) is listed in `docs/threat-model.md`. `rehydrate_blocks` takes a `RehydrateMode`: `Permissive` leaves unknown tokens in place and counts them (existing control clients), `Strict` fails the whole batch on any unresolved placeholder, including a `<KIND_REMOVED>` marker, which is never restored. A `StoreError` from the vault at any point discards the batch's text entirely (fail closed, M4 spec §5.3) rather than returning partial or placeholder output; session contexts never go through this path.

The batch is also the linker's scope: a full name in an earlier block lets a bare name in a later block link to it (a tool result's blocks share one scope), and a block whose links used the batch or the recency window is not cached, because its tokens depend on more than its own text. Each `BlockResult` carries `replaced`: the applied decisions as offsets and kinds, never text, which the evaluator uses to score link and restoration quality.

**Measuring the service path.** `inumaki eval --via-service` runs the corpus through `sanitize_blocks` in an in-process daemon state (temporary data directory, file key, one dataset for the whole corpus), so release-check blocks and cache hits are counted the way the gateway sees them. `--sequences` drives labeled persistent-dataset sequences through the same path, with restarts, a rotation, cache repeats, and grace expiry, gated by `crates/inumaki-eval/targets/sequence.toml`. `--track tool-json` evaluates MCP-shaped tool results (nested JSON, typed identifier fields) instead of mail. The reports and the gate status are in `docs/quality/2026-10-09-4a-summary.md`.

## Extension points

- **A new detector**: implement `inumaki_core::Detector` (`id`, `detect(text, ctx) -> Result<Vec<Span>>`), pick a `DetectorId` tier for overlap priority, and add it to the stack in `Engine::from_config` or per engine with `Engine::with_detector`. A detector that needs its own source for measurement gets a new `DetectorId` (as `Position` did for the path detector; only `DetectorId::priority` matches it exhaustively). A detector is sanitizer-only unless the verifier gets its own, independent check for the same thing (as the home-folder login check is for `Position`).
- **A new model backend**: implement `inumaki_models::NerBackend` and wrap it in `NerDetector`; register the files in `models/manifest.toml`.
- **A new verifier**: implement `inumaki_core::Verifier` (`verify(&Sanitized, &dyn TokenStore) -> Verdict`).
- **A new token store**: implement `TokenStore`; the conformance checks in `inumaki-core`'s `token` tests and `inumaki-vault`'s `namespace` tests say what is expected.
- **A new front door** (folder mirror, proxy): call `POST /v1/sanitize` and `POST /v1/rehydrate` on the socket, or use `inumakid` as a library (`AppState`, `Engines`, `Vault`, `service::sanitize_blocks`).
- **A built-in upstream** (the mail connector): implement it as an rmcp `ServerHandler` and hand it to the gateway through `BuiltinUpstreams`; it then takes the same content path as a wrapped server.

## Gateway (milestone 4)

**Components.** `inumaki-gateway` holds everything MCP-specific: upstream clients (a child process on stdio, or Streamable HTTP) under a supervisor, the per-dataset catalog, field contracts, discovery sanitization, the content path, resource handles, limits, the tripwire, and the activity sink. It reaches the engine only through the `Blocks` trait. `inumakid::glue` implements `Blocks` over `service::sanitize_blocks`/`rehydrate_blocks` and supplies `BuiltinUpstreams`; both hold a weak reference to the daemon state. `inumaki-mcp` is a stdio MCP server that relays to `/mcp/<dataset>` over the control socket, so a harness without HTTP transport can connect with no bearer token and no model or vault in its process.

**Dataset lifecycle.** A dataset's upstream rows (vault v2 `upstreams`, secrets in the `secrets` table) become upstream handles under a supervisor. A stdio child is spawned with a cleared environment holding `PATH`, `HOME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL`, and `XDG_RUNTIME_DIR` from the daemon, then the stored environment and its secret environment, is killed when its handle drops, and restarts on exit with backoff (1 s, doubling, capped by `[gateway] upstream_restart_max_backoff`, 30 s by default; the counter resets after 30 s of stable uptime). The catalog is rebuilt when an upstream connects, sends a list-changed notification, or exits. A down upstream keeps its names through its last-known lists, so a call to it answers `upstream_unavailable` instead of reaching another server. Any change to a dataset's upstream rows reloads the whole dataset: its upstreams restart, its MCP sessions and `subscriptions/listen` streams end, and its handles go stale. Deleting a dataset stops new requests, stops its upstreams, drains in-flight calls for up to 5 s, waits 100 ms, then cancels its MCP sessions and listen streams; later requests to `/mcp/<id>` answer `404`.

**Content path.** `tools/call` and `prompts/get` arguments are checked against the exposed schema and strictly rehydrated through the contract and the upstream's input schema: every token must resolve in the dataset namespace, and typed identifiers go back to their original JSON type (a customer number that left as `<CUSTOMER_ID_1a2b3c>` arrives upstream as the integer it was). An unresolved token fails the call with `unresolved_token` before anything is dispatched. Results are walked by the contract: every `text` content item is a sanitized block; `structuredContent` is sanitized field by field (free text as blocks, identifiers as typed tokens, quantities and reviewed booleans or nulls kept); embedded text resources and resource links take the resource path. Binary content (`image`, `audio`, blobs), an unknown content kind, and structured content the contract does not cover answer `unsupported_content`. If any block of a result is `Blocked`, the whole result becomes a tool error (`isError: true`) naming kinds and checks only; `PassUncertain` is treated the same way and counted as uncertain. Namespace locks are never held while waiting for an upstream.

**Discovery metadata.** Tool and prompt names are exposed only when they are static (`[A-Za-z0-9_.-]{1,64}`), and every exposed name (tools, prompts, prompt arguments, schema properties, definitions and `$ref` segments, `required` entries, template parameters) goes through one clear-value scan per listing, as written and split into words at `_`, `.`, `-`, and case changes: a known entity of the dataset or a validated identifier in any name fails the whole listing (`unsupported_content`, class `name`). A known person, organization, or street counts in an exposed name only when its match spans two or more words; an identifier kind and a validated identifier still count on a single word. A listing that failed because models or the vault were unavailable is rebuilt again with backoff (0.5 s doubling to 30 s). A later upstream's colliding name is prefixed `<upstream>__<name>`, resolved over configured upstreams in creation order. Descriptions, titles, examples, and string defaults are sanitized blocks under the dataset profile's metadata profile (`support-email-metadata`, `strict-metadata`; `fast`, `fast-strict`, `thorough`, `thorough-strict`, `offline`, and `offline-strict` have none, so their listing prose stays under the dataset profile itself); `enum` and `const` values and patterns must survive sanitization unchanged; `$ref` must be a local JSON pointer. The schema walk follows only `properties`, `items`, `prefixItems`, `additionalProperties`, `anyOf`/`oneOf`/`allOf`, local `$ref`, and `$defs`/`definitions`; `discriminator` is checked and stripped, and a local `$ref` on the way to an identifier rule is inlined as an `allOf` branch; any other keyword that carries a subschema still fails the listing. An identifier field is exposed as a plain `{"type": "string"}` with sanitized prose, and definitions reachable from it lose their samples (`default`, `examples`, `enum`, `const`, `pattern`, numeric bounds). Extensions, `$schema`, `$id`, `_meta`, icons, and annotations are stripped. Resource URIs become opaque handles (`inumaki://res/<16 hex>`), keyed by the owning upstream's identity and generation, capped at 16 384 per dataset; templates are exposed as `inumaki://tpl/<16 hex>/{param}` only under a reviewed parameter mapping. A blocked or uncertain block, or an unsupported shape, fails the whole listing with `unsupported_content`; the gateway never returns a partial list.

**Contracts and fingerprints.** A contract (`--content-policy`, JSON, `docs/examples/scripted-upstream.policy.json`) has `version: 1` and optional `tools`, `prompts`, and `resource_templates`. Tool rules are keyed by JSON pointer under `arguments` and `result` (`*` matches any array index or map key); a rule is `"free_text"`, `"quantity"`, `"preserve"`, `{"identifier": "KIND"}`, or `{"map": RULE}` for an object with dynamic keys. Kinds match `[A-Z][A-Z_]{0,31}` and may not be `SECRET`; a contract that types a field with a kind the dataset's profile blocks or removes is refused, at add time and whenever the profile or contract is loaded. Every identifier rule must match a node the discovery walk visits, otherwise the listing fails. The first listing records a fingerprint of the contract-reviewed parts of the schema (trust on first use). A later listing whose reviewed parts differ hides that upstream (contract state `drift`) until `inumaki dataset upstream accept-schema` records the new fingerprint. Tools the contract does not name are exposed with text-only treatment, and their structured content is refused.

**Limits.** The gateway defaults below (limits, timeouts, `activity_retention_days`) are provisional until plan 4's load tests measure them. `[gateway] max_response_bytes` (default `4MiB`) bounds an upstream result before it is sanitized; a stdio line is capped at six times that plus 64 KiB (worst-case JSON escaping), and HTTP SSE events at the same bound. `max_inflight` (default 8) bounds concurrent engine work per dataset and `queue_timeout` (default `30s`) bounds the wait for a slot. Exceeding any of them answers `resource_limit` with no partial content. `upstream_call_timeout` (default `60s`) bounds one upstream call. At most 64 `subscriptions/listen` streams are open per dataset (`MAX_SUBSCRIPTIONS`, not configurable); one more is acknowledged and then ended with `resource_limit` (`limit: subscriptions`).

**Protocol versions.** Both MCP lifecycles are served on `/mcp/{dataset}` by rmcp 3.4.1 (pinned exactly). A 2025 client sends `initialize`, gets an `Mcp-Session-Id`, and receives list-changed notifications on its session. A 2026-07-28 client (Claude Code 2.1.296 and later) has no session: it probes with `server/discover`, then sends every request as its own POST carrying its protocol version, client info, and capabilities in `_meta` and the `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` headers, and opens a held `subscriptions/listen` stream for list-changed notifications. The gateway accepts the three list-change kinds there (no resource subscriptions) and tells those streams what it tells sessions. That schema requires `resultType: "complete"` on every result (the gateway sets it on call, prompt, and read results built from upstream replies; rmcp removes it again for 2025 peers) and cache hints on list and read results; the gateway sends `ttlMs: 0` (the catalog changes while a client is connected) and `cacheScope: "private"` (results are sanitized per dataset). Without them a 2026-07-28 client rejects every list and ends up with no tools. On that path rmcp maps a JSON-RPC METHOD_NOT_FOUND to HTTP `404`, so a method the gateway does not serve (`logging/setLevel`, and `ping` and `resources/subscribe`, which that version removed) is a `404` there and a JSON-RPC error with `200` on a session. `crates/inumakid/tests/gateway_lifecycle.rs` replays both sequences as raw HTTP.

**Authentication.** The TCP listener (`[gateway] listen`, loopback only, default `127.0.0.1:8789`) requires `Authorization: Bearer <token>` on every request, checked per request against the HMAC stored in `gateway_tokens` with a constant-time comparison, so a revoked token is refused on the next request even inside an existing MCP session. The same `/mcp/{dataset}` route on the control socket carries no token check; the socket's file mode is the authorization. A bind failure stops the daemon with exit code 2.

**Errors.** An MCP error message is exactly one of `model_unavailable`, `vault_unavailable`, `privacy_block`, `upstream_unavailable`, `unsupported_content`, `unresolved_token`, `context_unavailable`, `resource_limit`, `upstream_error`, `unknown_tool`, `unknown_prompt`, `unknown_resource`. Its `data` carries only `class`, `kinds`, `checks`, `unknown_tokens`, `removed_markers`, `limit`, and `code` (an upstream's JSON-RPC code as an integer), never the tool name, URI, pointer, label, message, or argument the caller or the upstream supplied. A blocked result is a tool error with the text `blocked by inumaki (kinds: PERSON, IBAN; checks: Leak)`.

**Logging.** Access logs carry route templates (`/mcp/{dataset}`, `/v1/datasets/{id}`, or `unmatched`) and opaque dataset ids; upstream names, exposed tool names that passed the static-name check, counts, verdicts, check ids, and timings are the only other fields. Child stderr is read and discarded; `status` shows its byte count. Every `rmcp` log target is dropped and `hyper`, `h2`, `reqwest`, and `rustls` are capped at `WARN` by a filter that `RUST_LOG` cannot override, because `rmcp` logs full JSON-RPC payloads at debug and trace level.

**Activity.** Every gateway call that reaches the content path produces a typed record in the vault's `activity` table (schema v3): opaque dataset and upstream ids, front door, direction, verdict, check ids, kinds with counts, flags, byte counts. Records are written off the request path by one writer thread in batches; when its queue is full a record is dropped and counted (`status` shows `activity records dropped`). Each row stores `hash = SHA-256` over the length-prefixed previous hash, record id, timestamp, dataset id, and record body, so `inumaki activity --verify` (`GET /v1/activity/verify`) detects an inconsistent edit or deletion inside the kept chain (accidental corruption, naive edits). The hash is unkeyed and the formula is public: a same-user process that can write `vault.sqlite` can rewrite the chain consistently, and truncation at either end (dropping the newest rows, or the oldest, which looks like a sweep) is not detected. The sweeper deletes the oldest rows as a prefix by sequence number once they are older than `[gateway] activity_retention_days` (default 30), so the kept rows still form one chain. Recorded are released results, results refused by the content path (`blocked`, `uncertain`, `unsupported`), arguments refused before dispatch (`unresolved`, `unsupported`), and tripwire hits. Not recorded are listings, availability failures (`model_unavailable`, `vault_unavailable`), `resource_limit`, `upstream_error` and `upstream_unavailable` (timeouts included), `unknown_*`, and `context_unavailable`; `status` counters and logs cover those. A `notify`-mode tripwire record says `released` even when the call is refused afterwards.

**Journal.** Vault v4 adds a `journal` table. For every released `tools/call`, `prompts/get`, or `resources/read` result, the released result as the handler produced it (protocol metadata such as `resultType`, `ttlMs`, and `cacheScope`, which rmcp and the handler set after `released()` has computed the digest, excluded; so the journaled bytes and their `released` digest differ from the bytes a 2026-07-28 client receives by those fields only, never by content) travels with the activity record through the same writer thread (`ActivitySink`), bounded by `JOURNAL_INFLIGHT_MAX` (64 MiB of payload bytes in flight); a payload that does not fit is dropped and counted (`GatewayStatus.journal_dropped`), while its activity record is still written. Each entry is sealed under AAD `journal:<dataset>:<record id>`, and the activity record's `released` digest links the two entries, checked again on every read. `[journal] retention` is one global setting; `[journal] max_bytes` is a per-dataset byte budget; both are swept by the existing sweeper, oldest entries first. The journal is read only over the control socket (`GET /v1/datasets/{id}/journal[/{record}]`), never on the gateway TCP listener and never as an MCP tool.

**Entities and forget.** Vault v4 also adds `entries.created_at` and `entries.uses`; `uses` counts store-level uses (a mint plus every database hit), a lower bound, since counting working-set hits would add a database write per mention on the request path. `GET /v1/datasets/{id}/entities` lists tokens with kind, first and last use, use count, and epoch; `show_values=true` adds the original, on a terminal only in the CLI. Forget (`DELETE …/entities/{token}`, `POST …/entities/forget {value}`) deletes the mapping rows for `(kind, key_hmac)` in every epoch of the dataset (current and closed) under the namespace lock; `Namespace::forget_tokens` then evicts the working set and rebuilds the known-entity automaton synchronously, and a background rebuild that started earlier is superseded by generation (`replace_if`) rather than swapping stale rows back in. The dataset's sanitization cache is invalidated while still under the lock. After the lock is released, a TRUNCATE checkpoint (`Vault::checkpoint_truncate`, retrying 5×20 ms while busy) removes the pre-delete page images from `vault.sqlite-wal`; if it stays busy the entity is already forgotten and the response is `503 vault_busy` ("the change was saved, but the vault write-ahead log stayed busy and was not truncated; the pre-delete pages stay in vault.sqlite-wal until the next TRUNCATE checkpoint (at the latest when the daemon stops)"), and a retry then answers `404`. `forget_by_value` forgets the typed value's own normalized match in every kind, plus each alias canonical (from the value's alias group) in that group's own kind only, so forgetting a variant does not remove an unrelated entity of another kind that happens to share the same literal text.

**Bench note.** The journal writer uses its own SQLite connection, so a multi-megabyte INSERT never holds the shared connection's mutex the request path takes; SQLite still serializes writers at the WAL level, so a mint that coincides with one INSERT waits for that INSERT — tens of milliseconds for 5 MB, bounded by `busy_timeout`. Reads and working-set hits are unaffected, as `journal_burst_does_not_stall_request_path_reads` pins. Sweeps delete 8 rows per statement and release the connection in between.

**Alias groups.** `AliasTable` (`inumaki_core::alias`) is built from `persons.txt` ` | ` lines and `[[dictionary.aliases]]` entries. The engine wraps every store a pass touches in `Aliased`, so alias expansion reaches the dictionary detector, the known-entity detector, and the verifier's leak check uniformly. Since plan 4a every variant is a surface token of the group's canonical entity and restores to its own text (vault schema v6, `entries.surface_of`); canonical rows did not change. One shared token could not say which variant a later model-written argument meant.

**Tripwire.** Before rehydration, model-written `tools/call` and `prompts/get` arguments and resource-template values (percent-decoded) are scanned with the namespace's known-entity automaton at full-match confidence and the validated regex tier (IBAN, card, national ids, email, IP, URL); JSON numbers are scanned as text, and object keys too (a key under a `map` rule is rehydrated like a value). Kinds the profile preserves are skipped. A hit is counted in `status` (`clear-value hits`) and recorded with check `ClearValue`; in `notify` mode (default) the call proceeds and its record carries verdict `released` with the tripwire flag, in `block` mode it fails with `privacy_block` before dispatch.

**Transport.** A guard in front of authentication refuses any request with an `Origin` header not listed in `[gateway] allowed_origins` (entries must be browser-serialized origins: lower case, no default port) and any `Host` other than `localhost`, `127.0.0.1`, `[::1]`, `inumakid`, or the configured listen address, each with no port or the bound port, with a fixed `403`. `Upgrade` requests get `501`, `Access-Control-*` response headers are stripped, and no configuration enables CORS. rmcp's own `allowed_hosts` check stays as a second layer.

**What plan 3 adds.** The draft-only mail connector is a built-in upstream behind `BuiltinUpstreams`: an in-process rmcp server that takes the same content path, contracts, handles, and activity records as a wrapped server. *(As built, plan 3.)*

**Mail connector (`inumaki-mail`).** The crate has no engine and no vault dependency: it asks for credentials and handles through two traits, `MailCredentials` and `MailHandles`, which `inumakid::glue` implements over the vault (`VaultCredentials`, `VaultMailHandles`). It exposes four tools, `mail_list_folders`, `mail_search`, `mail_read`, and `mail_draft_reply`; there is no send tool and no SMTP code. One IMAP session per mailbox dataset is opened lazily on the first call (implicit TLS, or plaintext only to loopback), reads use `EXAMINE` and `BODY.PEEK` so nothing is marked as read, a `NOOP` keepalive runs while idle (`[mail] keepalive`), and the session is dropped and re-established on connection-class errors. The socket is wrapped in a tolerant reader (`inumaki_mail::tolerant::TolerantStream`) that inserts the single space RFC 3501 requires before the literal of a partial-fetch response (`BODY[TEXT]<0>{200}`), which GreenMail 2.1.14 omits and `async-imap` cannot decode; literal data and everything the connector writes pass through untouched. It has been run against GreenMail only. A refused login is remembered for `[mail] auth_retry_after` and answered from memory, so an agent loop cannot hammer the provider.

**Handles.** Folder and message ids shown to the agent are `mf_` and `mm_` followed by 16 random lowercase letters. The vault table `mail_handles` stores, per handle, the sealed payload (folder, UIDVALIDITY, UID), a keyed hash of its key, and a `last_used` time; it is scoped to the dataset and the mailbox fingerprint, so a handle minted for one mailbox never resolves in another. The connector compares the live UIDVALIDITY on every read and every draft; a change drops all handles of that folder and the call answers `context_unavailable`. A periodic sweep removes handles unused for `[mail] handle_retention_days`, and deleting or replacing the mailbox removes all of them. The next free schema version at merge carries the `mailboxes` and `mail_handles` tables (see the schema-version bullet above).

**Content contract.** `crates/inumaki-mail/contract.json` is the field contract the gateway applies to the built-in `mail` upstream: dates and status fields are preserved by rule, free text (subjects, snippets, bodies, folder display names, attachment names) is sanitized, and every id field carries the `handle` rule. A *connector-minted, provenance-checked handle* is kept only when the daemon finds it in `mail_handles` for this dataset and mailbox; a string that merely looks like a handle is refused as `unsupported_content`, class `handle_provenance`. An absent or `null` `draft.id` is allowed (the draft could not be located after it was stored). `mail_read` returns text only; attachments are listed by name and type and never fetched.

**Drafts.** `mail_draft_reply` validates the handles, the recipients, and every header, then stores the reply with IMAP `APPEND` and the `\Draft` flag. If the server refuses the flag, the draft is stored once more without it; if the `APPEND` never reached the literal (a desynchronised session), it is retried once, without the flag, on a fresh session. A draft stored by either retry therefore lacks `\Draft`. An ambiguous failure after the literal was sent is reported as `draft_status_unknown` and never retried, so a network error cannot silently create two drafts. `To` is the original `Reply-To` when it is exactly one valid address, else the original `From`. The drafts folder is the configured one, else the `\Drafts` special-use folder, else a folder named `Drafts`, else `Drafts` is created. The stored draft is found again by its `Message-ID` to return its handle; when that fails the draft is still reported as created, without an id.

**Errors.** Mail failures are tool errors (`isError: true`) whose text is a fixed class and a fixed sentence: `mail_unreachable`, `mail_timeout`, `mail_tls_failed`, `mail_auth_failed`, `mail_protocol`, `context_unavailable`, `invalid_argument`, `draft_rejected`, `draft_status_unknown`, `drafts_folder_missing`, `resource_limit`, `mail_handles`, `mail_credentials`. They carry no server text, address, or folder name, because the gateway reduces upstream MCP errors to `upstream_error` and a message from the mail server could hold personal data.

**Mailbox control API and `[mail]`.** `GET`, `POST`, and `DELETE /v1/datasets/{id}/mailbox` and `POST /v1/datasets/{id}/mailbox/check` are on the control socket only. Creating a mailbox stores the app password in the vault's secrets table under `<dataset>/mail/password`, installs the built-in `mail` upstream with the shipped contract, and discards the dataset's old handles; deleting the mailbox deletes the secret first. `GET /v1/status` and `inumaki status --json` list mailboxes (`mailboxes[]`: dataset, preset, IMAP host, IMAP port, TLS, handle count); the human `inumaki status` output prints no mailbox line. The `[mail]` table has six keys: `keepalive = "5m"` (at least 30 s), `command_timeout = "30s"`, `max_message_bytes = "4MiB"` (at least 64 KiB), `snippet_chars = 200` (40 to 2000), `handle_retention_days = 30` (1 to 365), and `auth_retry_after = "60s"`. A key that fails validation stops the daemon at start, naming the key.

**Harness.** `inumaki mail-tasks` plays the agent against a test mailbox: it wipes the INBOX and drafts folder of the account it logs into, seeds the deterministic fixture mails from `inumaki-eval` (`mail_fixture`), drives search, read, and draft through the dataset's gateway, reads the drafts back over IMAP, and writes a report (`--report-json`) whose keys are frozen so that the quality plan can consume them. The IMAP helpers it needs live behind the `harness` feature of `inumaki-mail`; the gated `mail-tests` feature of `inumakid` adds a GreenMail suite. This plan states the mechanism and the 90 % completion target of the M4 spec; measuring the target on the real profiles is plan 4's work.

## Folder mirror (milestone 5)

A connected folder keeps a sanitized copy, the **mirror**, that agents read instead of the source; what an agent writes into the mirror's `outbox/` is restored to real names in a destination folder the user owns. The work happens when a source file changes, so a read costs nothing. The M5 design spec's dated amendments record where the build differs from the first draft.

**Components.**

```
inumakid                              inumaki-mirror
  api/folders.rs   control socket       service   watcher, poller, workers, per-folder status
  folders.rs       Folders: registry,   queue     one queue, five priorities, per-path serialization
                   owns the Mirror;     pipeline  one file: read, blocks, sanitize, names, write
                   MirrorGlue (engine), reconcile walk, stale and orphan removal, deletes
                   VaultManifest        guard     release check, tripwire pass, removal of confirmed originals
  service.rs       + sanitize_names,    outbox    settle, strict restore, no-replace write, sidecars
                   known_in_clear       formats   classify, decode, blocks, reassembly
                                        names     component sanitization, collisions, opaque fallback
                                        fsops     directory-handle walk, O_NOFOLLOW, atomic write
```

`inumaki-mirror` never imports `inumakid` or the vault. The daemon passes the engine as `MirrorEngine` (`sanitize`, `sanitize_names`, `rehydrate_strict`, `known_in_clear`, `scan_clear`, `state`, `carry_known`, `record`) and the manifest as `ManifestStore`; both map their errors to fixed classes that carry no text. `Folders` also implements the hook's `FolderRegistry`, listing every connected folder whatever its mirror state, so the hook guards a source folder even while its mirror has failed.

**The pipeline, per source file.**

1. `lstat` through the parent's directory handle: gone means delete; a symlink, a cloud-only file, or an oversized file becomes a placeholder; anything not regular is skipped. A file whose size, mtime, epoch, and policy fingerprint match its manifest row is skipped.
2. Open with `O_NOFOLLOW` and read; unchanged content only refreshes the mtime.
3. Classify by extension (an allow-list), decode (UTF-8, UTF-16 with a BOM, else Windows-1252 for text, CSV, and JSON), split into blocks (paragraphs, CSV records, JSON keys and values).
4. Sanitize the blocks through the daemon's `sanitize_blocks` in sub-batches of about 8 KiB, so no call holds the namespace lock for long. Any blocked or uncertain block, a block over 64 KiB, or a failed object-level check (JSON objects and arrays, per-field CSV records) withholds the whole file.
5. Sanitize the path components that have no name yet (`sanitize_names`: the stem as written and in a word-separated variant), with an opaque `f-<10 hex>` fallback and collision suffixes.
6. Release check: the assembled output and every path component are scanned for known originals. A hit re-sanitizes once; a second hit withholds the file. A hit in a directory component only renames that component at once, with no re-sanitize.
7. Check the file is still the version that was read, write to a temporary name, `fsync`, rename into place (mode 0444, source mtime), update the manifest, write an activity record (front door `mirror`).

**Queue priorities**, highest first: removal of a confirmed original; outbox files; live source changes (and requeues from the tripwire pass); reconcile, rescan, and re-mirror work; the tripwire pass. `[mirror] workers` (default 1) blocking workers run the jobs, so the mirror takes at most that many engine sessions from the gateway and the hook. Scheduling is fair per job, not per directory: with one worker, a directory-heavy first scan or a re-mirror after a rotation names every directory inside one job, and a tripwire pass is one job, so another folder waits until that job ends.

**Manifest.** Two vault tables (schema v7), both sealed. `folders` holds, per dataset, the sealed configuration: source, outbox destination, and the source root's (device, inode), plus its inode generation on Linux, where a deleted directory's inode number is reused at once. `mirror_files` holds records per `(dataset, side, path MAC)` where side is `source`, `dir`, or `outbox`: a source record carries the relative and mirror path, size, mtime, a content MAC, the epoch, the policy fingerprint, and the state (`mirrored`, `blocked`, `unsupported`, `pending`); a `dir` record is the directory-name table, keyed per epoch and fingerprint; an outbox record carries the content MAC and the outcome. The lookup key is an HMAC under the vault's index key, so no path is stored in clear, and deleting a dataset cascades.

**Startup order.** `AppState::start` loads the folder rows, builds the `Folders` registry (no watcher yet), prepares the mirror root (created 0700 with a `.inumaki-root` marker and a README, or refused if it exists and is not ours), and sets `AppState.folders` and `AppState.mirror`, so the hook can use the registry from the first request. `serve_with` runs the check sweep, then starts the mirror service, directly before the gateway loads datasets. Each folder then scans (state `scanning`): it checks the source root, queues every path whose record is missing or stale, deletes mirror entries whose source is gone, removes every mirror entry the manifest does not name, and runs the tripwire pass once; then the state is `watching`. `Folders::start` runs before the control socket answers (it decrypts the manifests and arms the watches), so a large folder lengthens daemon start; the number is in `docs/quality/2026-09-29-m5-mirror-latency.md`.

**Re-mirroring and the rotation carry.** Every 10 s the service compares each folder's recorded epoch and policy fingerprint with the dataset's `DatasetState` (epoch id, entries generation, fingerprint of profile, configuration, and model manifest) and queues stale files at re-mirror priority; a rotation, a profile or model change, and a configuration or version change all arrive this way. Because known originals are stored per epoch, a new epoch would start with an empty known-entity detector. Before the mirror sanitizes anything in an epoch it has not seen, it calls `carry_known`: the daemon reads the previous epoch's identifying originals (`Vault::previous_epoch_known`) and registers them in the current epoch with fresh tokens. Canonical entities only: surface-form rows are spellings of one of them and are not carried. Only the most recently closed epoch is carried, and the gateway and the hook do not carry yet. When the entries generation changes without a rotation (a name learned from another front door, or a new surface form of a known one), the tripwire pass re-checks every mirrored file and name and removes a confirmed original before anything else runs.

**Files and handles.** Every source, mirror, and outbox operation walks directory handles opened with `O_NOFOLLOW` one component at a time; a link is never followed, and a link an agent plants in the mirror is replaced. Writes are temporary file, `fsync`, rename; the outbox uses a no-replace rename (`renameatx_np` on macOS, `renameat2` on Linux, the latter untested) and falls back to `O_EXCL` on file systems without it.

**macOS privacy prompts and bounded waits.** On macOS the first read of a protected folder (Desktop, Documents, Downloads, iCloud Drive, removable volumes) blocks inside `open()` until the user answers the system prompt (`docs/research/2026-09-29-m5-tcc-spike.md`). Nothing waits on such a read without a deadline:

- **`pending`.** A folder whose source root open, first listing, first file read, or outbox destination open has waited more than 2 s shows state `pending`. It is not an error and clears as soon as the call returns. The mark stops once a listing or read has succeeded in this process, so a later slow read never shows `pending`. Precedence: `stopped`, then `pending`, `failed`, `scanning`, `watching`. `GET /v1/folders` never waits on a worker.
- **Removal.** `Mirror::remove` waits at most 5 s for the job in flight. After that, `DELETE /v1/datasets/{id}/folder` and `DELETE /v1/datasets/{id}` answer `409 conflict` with `the folder is busy; try again in a moment`. The removal is fenced: `removing` stays set, the watches are dropped, the queue is purged, and no further job of that folder runs, while the source is never touched. A later call finishes the removal; nothing retries it automatically. Other folders' adds and removals keep answering meanwhile.
- **Stop and shutdown.** `Mirror::stop` waits 3 s for its workers and then detaches them. Daemon shutdown waits 4 s for the mirror and 2 s for the runtime's blocking threads. The end-to-end check's cleanup waits 8 s for its folder removal and leaves what remains to the next start's sweep.
- **Known limits.** With the default `[mirror] workers = 1`, one parked first read stalls every folder, the check's own mirror folder included, so the check's mirror path fails closed after its 30 s wait. Whether `lstat`, `realpath`, or an FSEvents stream on an unanswered protected folder also block is not verified; these run on request and startup threads (`Folders::add`, arming the watches at start and on rescan), so if they do, daemon start or `POST …/folder` and `…/rescan` would hang.
- **Upgrades.** Installers replace a binary by writing a new file and renaming it over the old one, never in place: the kernel kills a signed binary that is overwritten in place (spike finding 4). An ad hoc signed upgrade has a new code hash and loses the grant, so macOS asks again.

## Harness adapters, the hook, and `POST /v1/hook` (milestone 6)

**Adapters.** `inumaki-adapters` implements `HarnessAdapter` once per harness: `id`, `owned` (the exact key paths the adapter may create, change, or remove), `config_files`, `detect`, `mcp_servers(inst, gateway_base)`, `plan_edits`, `status(inst, sys)`, `apply`, `revert`, and `check_invocation`. Running in the CLI or the app process, never in `inumakid`, an adapter receives resolved values (gateway base URL and bearer token, proxy base URLs and the client header, mirror root and outboxes, hook command and socket) in a `ConnectPlan`, and the daemon's facts in a `SystemState`, and writes files only. `engine::apply_files` is shared by all four. It checks every edit against the owned patterns before reading anything, edits every file in memory first (one refusal writes nothing), then writes each file with a temporary file, `fsync`, a SHA-256 compare against the bytes read, and `rename`, retrying up to three times. An edit must print back byte for byte when nothing changes, and the result, parsed by a standard parser (`serde_json`, `json5`, `toml`, `serde_yaml_ng`), must differ from the original exactly by the owned keys; otherwise the adapter refuses with `CannotEditSafely` and a snippet to add by hand. The editors keep comments, key order, and trailing commas: `jsonc-parser` (JSON and JSON5), `toml_edit`, and `yaml-edit` (flow style and anchors are refused by an own syntax check). Backups go to `<data_dir>/adapters/backups/<harness>/<id>/` and revert is byte-exact when the file is unchanged since apply, key by key otherwise (`docs/threat-model.md` lists what a backup holds). `protect.rs` holds the Protect switch's logic (dataset ids, the credential split by name, definition identity, mailbox entry names) and `DefinitionIndex`, which reads and writes `adapters/definition.key` and `adapters/definitions.json` in the data directory; the caller makes the API calls. What each adapter writes, with the verified harness versions, is in `docs/harness-adapters.md`.

**The hook.** `inumaki-hook <harness>` reads a `PostToolUse` payload on stdin, walks the tool output in a fixed order (every object key, string value, and number as text), extracts the paths the tool input references, and sends one `POST /v1/hook` over the control socket through `inumaki-client`. It prints the harness's replacement on stdout: for Claude Code `hookSpecificOutput.updatedToolOutput` in the tool's own output shape (a bare string is refused for built-in tools), for Codex `{"decision":"block","reason":<text>}`. For a known harness name, every failure (daemon down, a 10 s deadline, `451`, `413`, any other non-200, an unparsable payload, a panic) prints a block, `blocked by inumaki (<class>; kinds: …)`, in the tool's template (a `daemon_unreachable` block adds the fixed sentence "inumaki is not running; start it to restore tool output."; no cached verdict ever replaces the daemon, see `docs/threat-model.md`); it exits 0 and never prints the original. An unknown harness name prints a usage line and exits 2. The hook writes nothing to disk and stderr carries fixed strings.

**`POST /v1/hook`.** Control socket only. Body `{harness: "claude-code"|"codex", tool: "bash"|"read"|"grep"|"glob"|"edit"|"web_fetch"|"mcp"|"other", cwd, paths, texts}`; unknown fields are refused, and `cwd` must be absolute (else `400`). Answers `{"action":"pass"}`, `{"action":"replace","texts":[…],"kinds":[…]}` with `texts` of the same length and order, `451 privacy_block` (kinds and checks only), `413` over the body limit, or `400`, `404`, `422`, `500`, `503` with the status class kept. Every error message is a fixed string with no values: a failed check answers `the tool result could not be checked; it was withheld`, a relative `cwd` answers `cwd must be an absolute path`, and a body that does not decode or is too large gets the router's fixed message. `inumakid::hook::run_hook` works in this order:

1. Resolve each referenced path against `cwd` (`~/` expanded, symlinks canonicalized; a path that does not exist is normalized lexically and its longest existing ancestor canonicalized). A path under a connected source folder or outbox destination (deepest root wins) selects that folder's dataset. Paths under the mirror root are exempt from this rule only.
2. Run the trigger over every dataset: `service::scan_known_names`, the same known-entity rule as the gateway's name scan (confidence 0.9 and up, a person, organization, or street counts only with a match of two or more words, an identifier kind counts on one word), without the validated-regex tier, so a URL or email in code output does not trigger it. No NER runs on this path.
3. Choose the dataset: the path's, else the one with the most trigger hits (ties go to the smallest id). With neither, answer `pass`.
4. Sanitize all texts in one `sanitize_blocks` call with the dataset's own profile. A `Blocked` or `PassUncertain` text blocks the whole result.
5. Re-scan the sanitized texts against every dataset with `service::known_left` (any confidence, single words included, only preserved kinds exempt). A leftover known original blocks; otherwise the answer is `replace`.

A replace or block writes one activity record (front door `hook`, direction `result`, kinds, checks, tripwire flag, byte count, and a digest of the released text on replace). A pass writes none. An error answer writes none.

**`FolderRegistry`.** The hook endpoint learns about connected folders through a trait in `inumakid::hook`:

```rust
pub trait FolderRegistry: Send + Sync {
    fn source_roots(&self) -> Vec<(String, PathBuf)>;        // (dataset id, source directory)
    fn outbox_destinations(&self) -> Vec<(String, PathBuf)>; // (dataset id, outbox destination)
    fn mirror_root(&self) -> Option<PathBuf>;
}
```

`NoFolders` is the empty implementation and applies while `AppState.folders` (`OnceLock<Arc<dyn FolderRegistry>>`) is unset, in which case the hook uses the trigger rule only. The folder mirror (M5) implements the trait and sets `AppState.folders` inside `AppState::start`, before the server accepts requests. Outbox destinations count as source roots because the rehydrated files there hold originals.

**`inumaki connect`.** `inumaki connect status|apply|revert` drives the adapters from a terminal (`docs/cli.md`). It asks the daemon for datasets, folders, the proxy's base URLs and client header, and the binary directory, mints one gateway token per connected harness (label `app:<harness>`), and revokes it on revert.

## The app, the service, and the end-to-end check (milestone 6)

**The app process.** `apps/inumaki-app` is a Tauri 2 app: a React UI and a Rust side, in its own Cargo workspace outside the root one. It runs as the user. Its Rust side reaches `inumakid` only through `inumaki-client` over the control socket, edits harness files through `inumaki-adapters` (as `inumaki connect` does), and manages the login service in its `service` module. It opens no network connection.

**Service and binaries.** "Install and start" copies the four helpers (`inumakid`, `inumaki`, `inumaki-mcp`, `inumaki-hook`) from the bundle into `<data dir>/bin` (on macOS `~/Library/Application Support/inumaki/bin`), mode 0755. Each copy is written as a new temporary file `.<helper>.tmp` (created exclusively, so a planted link is not followed), cleared of extended attributes and re-signed ad hoc on macOS, and only then renamed over the previous binary, which keeps working until the rename. `.<helper>.sha256` records the bundle's digest and the installed copy's digest after signing, so an unchanged helper is not copied again at every start. The service is the LaunchAgent `~/Library/LaunchAgents/inumaki.inumakid.plist` (on Linux a systemd user unit), written by temporary file and rename, which runs `<bin>/inumakid` with `INUMAKI_MANAGED_BY=app`. The app changes only a service file that carries that marker; a service from Homebrew, the `.deb`, or a manual start is used as it is. `GET /v1/service` (control socket only) answers `version`, `pid`, `started_at`, `exe`, `bin_dir` (for Homebrew the `opt/inumaki/bin` path, not the versioned keg), `managed_by` (`app`, `homebrew`, `deb`, else `manual`, from `INUMAKI_MANAGED_BY`), and `restart_required`. Harness entries and the hook command refer to `bin_dir`.

**Models.** `POST /v1/models/pull` starts the daemon's one download job over the pinned manifest (`409` while one runs); `GET /v1/models/pull` reports each file's progress and verification and an error class (`network`, `hash_mismatch`, `disk`, `manifest`). The daemon does not reload models: a finished job sets `restart_required`, and the app restarts its service. The download is the one outbound connection M6 adds to the daemon.

**The end-to-end check** (`crates/inumakid/src/check/`, M6 spec §8) is a shipped feature, not a fixture. `POST /v1/check` creates one check at a time (`409` while one is live) for 10 minutes: a synthetic canary identity (`canary.rs`); a dataset `check-<12 hex>` with profile `offline`, the canary seeded as known entities; a temporary gateway token `check:<12 hex>` and a stdio upstream running `inumakid canary-mcp` (`canary_mcp.rs`); a folder dataset `check-<12 hex>-f` over a temporary source and outbox under the system temp directory (`mirror.rs`); and two check routes on the proxy, one for the harness runs and one for the direct run (`proxy.rs`, `proxy_m8.rs`; see "Check routes" below). `POST /v1/check/{id}/direct` runs the daemon's own probes: the gateway over TCP with the token (`gateway_probe.rs`), the mirrored canary file and the outbox round trip (each waiting at most 30 s), and a request through the direct check route. `POST /v1/check/{id}/harness` takes one harness's output. `verdict.rs` reports booleans, counts, and reason codes per path, never a canary value; a path fails when a recorded upstream body holds any canary component, when no token was seen, when the answer was not restored, or when the route lost a body. `DELETE /v1/check/{id}`, or the expiry, removes the routes first, then the datasets, the token, the upstream, and the temporary directories. The public endpoints refuse the reserved prefixes `check-` (datasets) and `check:` (token labels); the check's own in-process calls carry an `Internal` marker. At start, before the mirror runs, the sweep removes only the generated shapes (`check-<12 hex>`, `check-<12 hex>-f`, `check:<12 hex>`) and this data directory's temporary directories.

**The app's side of the check** (`apps/inumaki-app/src-tauri/src/check/`). "Run the check" creates the check and runs the direct check. When the daemon offered proxy routes, it then runs each connected harness that has a `check_invocation` non-interactively in `<data dir>/app/check-tmp/<check id>-<harness>/{work,config}` (0700, removed when the run ends and at every app start), with only the check's gateway entry and check route, and passes its output to the daemon; the output is held in memory, wiped, and never logged. Before the first harness run the app reads `GET /v1/proxy` and refuses unless the state is `running` and the authority of every route `base_url` (`http://` only) equals the daemon-reported `listen`, which must parse as a loopback socket address; an unreadable status refuses too. On a refusal no harness runs and the reports hold the direct check only, with a fixed warning that names no address, port, or id: `run_check` returns `CheckRun { reports, warning }`, and the check panel shows the warning above the table. The check is deleted at the end in every case.

## Model-API proxy (milestone 8, plans M8-1 to M8-3)

*(As built, plans M8-1 to M8-3.)* The proxy is the Chat path: a harness whose model traffic goes through `127.0.0.1:8787` sends its system prompt, the user's typed text, tool results, and its resent history to the provider only after sanitization, and gets the answer back with real values restored locally. This section describes what plans M8-1 to M8-3 built (M8-2 adds streaming and the `/codex` route, M8-3 the check routes of the end-to-end check).

**Crate and host trait.** `inumaki-proxy` depends on `inumaki-core` and the HTTP stack only. Everything that needs a dataset, a model, or the activity writer goes through one injected trait, `ProxyHost` (`crates/inumaki-proxy/src/host.rs`), which `inumakid::proxy_host::DaemonHost` implements over the vault, the engines, and the gateway's `ActivitySink`: the profile's `Engine` and policy, the chat dictionary, `scan_known` for the tripwire, `scan_definitions`, `dataset_token` and `resolve` for dataset tokens, the OS identity, `record`, and `sanitize_dataset`, which sanitizes a check route's request with its check dataset (`service::sanitize_blocks`) and answers `unsupported` for any dataset id that does not start with `check-`. Every call blocks and runs on the blocking pool. A `HostError` carries a fixed class (`model_unavailable`, `vault_unavailable`, `unsupported`, `internal`), never text. `inumakid` builds the proxy in `chat::start`, binds its listener, and stores it in `AppState.proxy`.

**Request path.** For every served `POST`:

1. The shared transport guard (`tcp_guard.rs`, the gateway's `Origin`/`Host`/`Upgrade` rules) runs before routing. The route table serves `/anthropic` (`/v1/messages`, `/v1/messages/count_tokens`, model lists), `/openai` (`/v1/responses`, `/v1/chat/completions`, model lists), and `/codex` (`/responses`, `/models`); any other path answers `404 not_served` and is never forwarded, and only the query strings recorded for harnesses are allowed. Limits are applied in order: in-flight (`max_inflight`), body size after decompression (`max_request_bytes`; `gzip` and `deflate` are decoded, any other encoding is `400`), and a byte-weighted scan admission budget.
2. **The JSON scanner** (`json.rs`) reads the body once into a flat node list. Each node stores its parent index, one path segment, its byte range, and its decoded text, and a node's path is rebuilt on demand, so memory grows with the body and not with nodes times depth. Nesting beyond 127 containers is refused. The rewriter later splices re-escaped literals into a copy of the received bytes: every byte that is not a sanitized string (numbers, whitespace, key order) is forwarded as received, which keeps resent history byte-identical.
3. **The string-leaf rule** (`walk.rs`, `wire/`): every string leaf of a request is sanitized, one block per leaf, unless its key is structural or it is an opaque signed field. A known type only changes how its leaves are handled: tool inputs make each object key and each string its own block, tool results are a group that is replaced by a fixed placeholder when blocked, definitions (`tools`, JSON schemas, MCP server lists) are scanned and never changed, and reasoning, citation, and search-source text is scanned and never changed. The **structural shape table** (`wire/shape.rs`) decides which values stay structural: a key such as `type`, `role`, `id`, or any `*_id` is trusted only when its value has the shape the provider APIs give that key (a closed enum, an API-issued id with a known prefix, a model id, a media type, a configuration token), and any other value is an ordinary data leaf. Scanned and signed fields are recognized only at their documented positions, so the same key under an unknown parameter is data. **Attachments** (`[proxy] binary`): by default each binary part outside a tool result (image, document, audio, video, file) is replaced by one fixed text part and is not sent, so the rest of the history is served; `refuse` refuses the request, `forward` sends the attachment unchecked, with no detection on it. Inside a tool result a binary part withholds the whole result behind the placeholder (not in `forward`). Replacement is a pure function of the bytes, so a resent history forwards identical bytes.
4. **Sessions and the per-session cache** (`session.rs`, `cache.rs`). A session key comes from `X-Inumaki-Session`, else `x-claude-code-session-id`, else Codex's `session-id` (alias `session_id`), else an HMAC of the first system text and the first user text, scoped by route and client mode, kept in memory only. A session holds a core `Context` (session tokens), its block cache, its blocked-verdict memo, the digests of provider-written reasoning blocks, and an automaton over its own originals. Sessions expire after `session_ttl` idle, at most `session_cap` live at once (least recently used goes first), and the daemon's sweeper drops expired ones. A daemon restart loses every session. The cache maps a keyed hash of the leaf (wire format, leaf class, profile, configuration fingerprint, bytes) to the sanitized leaf and its tokens, bounded by `cache_bytes` over all sessions. A hit is forwarded as stored once its tokens still resolve; entries are inserted only after the upstream accepted the request, so a hit means these bytes already went to this upstream in this session.
5. **Protected tokens.** The per-request `SessionView` is the engine's token store. Tokens already in the text that resolve there, as session tokens or as dataset tokens looked up through the vault, are protected by the engine (`inumaki-core::protect`): detection sees them masked, and detections overlapping one are clipped, not dropped. Dataset mappings are never copied into the session, so forget and rotation apply at once. A value a dataset already knows keeps that dataset's token. The chat dictionary (every live non-check dataset's known entities, the session's originals, and the OS identity) is an extra detector, so a resent original gets its existing token even when its cache entry is gone.
6. **The verifier.** Cache misses go through `Engine::process_with` as the profile's engine, which includes its independent second pass (leak check, regex re-scan, home-folder login check, NER re-scan, combination heuristic). A blocked or uncertain block in user text or `system` fails the request; in a tool result it becomes the placeholder, memoized in the session so every resend is byte-identical.
7. **Fail closed.** The upstream receives the body the pipeline produced and nothing else. A detector, model, vault, store, or host error, a definition hit, a clear value in an unseeded reasoning block, or any panic leaves the upstream with nothing and gives the client a fixed error in its wire format (messages carry entity kinds and check ids only). After the upstream took the request, the new cache entries and memoized verdicts are inserted and the activity record and journal payload are emitted. Headers are forwarded by a per-upstream allowlist (names the proxy lists plus the user's `extra_headers`, values checked against a shape; never hop-by-hop headers (nor any header a `Connection` header names), the body-framing headers, every `X-Inumaki-*`, or Codex's `x-codex-turn-metadata`, which names the repository path with the login name, the git remotes, and the commit hash; threat model, M8 limitation (z)); on the Responses wire the walk also drops the body's top-level `client_metadata["x-codex-turn-metadata"]` before sanitizing, and the rewriter splices it out with its comma. An `sk-ant-oat` value in `x-api-key` on `/anthropic` is moved to `Authorization: Bearer`; credentials are never logged or kept.

**Static-prompt NER memo (spec §20, amendment of 2026-10-12).** A harness sends the same long system prompt in every new session, and the per-session cache (step 4) cannot carry work across sessions. `NerMemo` (`crates/inumaki-proxy/src/memo.rs`) sits beneath that cache: a leaf that hits the session cache never reaches the engine, and the memo serves only the engine pass of an eligible leaf, a system or developer text of at least 2 KiB in a request that carries a valid client header (trusted mode). `inumakid` builds a separate proxy engine per profile (`Engines::proxy_engine`) whose sanitizer and verifier NER detectors the memo wraps, each in its own key namespace; restricted requests and all other leaves run on the shared unwrapped engine (`ProxyHost::engine_unmemoized`), so they never read or write the memo. A hit returns the spans the model computed for byte-identical input (offsets, kinds and scores, no text) and skips only the NER inference: the dictionaries, the other detectors, the policy, minting with the new session's tokens, the consistency pass, every verifier check, and the closure run again. The memo lives in memory only (256 entries, 8 MiB, LRU), is keyed by an HMAC under a key drawn at each start, and is cleared whenever the dictionary of user datasets changes, so the first session after a start or such a change still pays in full. `[proxy] static_cache = false` turns it off. `GET /v1/proxy` reports its counters (`static_cache`) beside a content-free per-request timing split (`timing`), which `inumaki status` prints as a second proxy line. Equal output with the memo on and off is a hard gate (`crates/inumaki-proxy/tests/static_memo_differential.rs`); the membership side channel the memo opens is item (bb) of `docs/threat-model.md`.

**Harness traffic and the profile.** Codex was refused under `support-email` and `strict` (`451`, `PERSON`; measured with Codex 0.159.2 on 2026-10-10) and is not since 2026-10-28: every route runs the leading system and developer messages of a trusted request without the name models (`[proxy] harness_static_ner`), protect the header Codex puts before a command's output, and no longer scan the id of its `additional_tools` item (threat model (ee) to (gg)). Claude Code was refused too, measured 2026-10-11 (Claude Code 2.1.296) under `support-email`: 8 `PERSON` hits with check `Policy` and 1 `CONTRACT_ID` with check `Regex`. GLiNER's escalation band flags the harness's own static text as PERSON, and `on_uncertain = "block"` refuses the request (M8 spec §13 amendments of 2026-10-10). Since 2026-10-28 `[proxy] harness_static_ner = "skip"` (the default) applies to every route, and Claude Code's attribution block is protected (threat model (ee), (gg)); the git status is a user item and stays scanned. `"scan"` restores the earlier behaviour. `[proxy] profile = "fast"` also gets past the old refusal, with lower recall and no independent NER re-scan in the verifier; it is not the recommended default.

**Response path.** A non-streaming answer is read whole (bounded by `max_request_bytes`), scanned, and processed in `respond.rs`: the fields that carry model text, tool-call arguments, reasoning, and citations are found by wire format at their real positions.

- **Tripwire.** Before restoration, model text and tool-call arguments are scanned for known originals only: the chat dictionary at full-match confidence, with kinds the profile preserves skipped, and no validated-regex tier. A hit writes an activity record with check `ClearValue` under the dataset whose entity matched, or under `inumaki-chat`. `tripwire = "notify"` (default) only records. With `"block"`, a hit in a tool-call argument answers `451 privacy_block` and none of the answer is relayed; a hit in visible text never blocks.
- **Restoration by provenance.** Each token is classified by where it resolves. Session tokens restore in model text, in tool-call arguments (JSON-escaped where the arguments are JSON), and in error bodies. Dataset tokens restore in model text only, and only for a request that carries the client header; the gateway rehydrates dataset tokens in tool arguments under its own field contract. Reasoning is never changed. Removed markers and unknown token-shaped text are never restored.
- **The client header.** The daemon keeps one random per-install value (64 hex digits) in the vault's secret section as `inumaki-chat/proxy/client_key`. A request whose `X-Inumaki-Client` matches it (constant-time comparison) runs in trusted mode; any other request runs in restricted mode, where dataset tokens stay tokens. The header never leaves the machine, and trusted and restricted requests never share a session. Adapters read the value from `GET /v1/proxy` and write it into harness configuration.
- **Seeding.** After a completed answer, the proxy enters each assistant text leaf and tool-call leaf under the key of the form the harness will resend (the restored text), with the tokenized text the model wrote as the value, and records the digests of reasoning and citation text as provider-written. The next turn's history hits those entries and is forwarded byte-identical without an engine pass. A seed never replaces an existing entry, and an answer in which the tripwire found a known value in clear seeds none of its text.
- **Failures.** An upstream redirect, or an answer with a `Content-Encoding` other than `identity`, answers `502 upstream_unreachable` and nothing is relayed or committed. A 2xx answer that is not JSON, or whose restoration fails, is refused with a fixed error and none of its body is relayed. A non-JSON error body (status 400 and up) is relayed unchanged.

**Streaming (plan M8-2).** A 2xx answer is a stream when its content type is `text/event-stream`; with any other content type except `application/json`, the first non-empty chunk decides (`looks_like_sse`). Request-side sanitization is the same; the answer takes a different path in `stream.rs`, `sse.rs`, `holdback.rs`, and the codecs in `wire/` (`anthropic.rs`, `responses.rs` for Responses and `/codex`, `chat.rs`).

- **Events.** `SseParser` reads the upstream bytes into events (`event:`, multi-line `data:`, CRLF, comments; one event is capped at 16 MiB, and once the parser refuses it stays refused). A wire's `Codec` classifies each event: an event with no rewritable field is forwarded byte-identical; one with a text, argument, or repeat field is re-serialized with only that string changed (comments, `retry:`, and unknown fields are dropped from rewritten events). Every data payload other than Chat's `[DONE]` must scan as JSON, whatever its event name; one that does not aborts the stream, and so does a named Messages or Responses event whose payload `type` is missing or differs from the name. `sse::serialize` writes every line break of the data as its own `data:` line and refuses an event name or id with CR or LF. Codex shell, patch, computer, and MCP items are argument channels: `mcp_call` arguments stream like function arguments, and every other string and key of these items except `id`, `call_id`, `status`, and `type` is checked whole in every event that carries them, with any other event of theirs that carries more than ids refused. The parser drops one byte-order mark at the start of the stream. Responses sequence numbers are shifted after a synthesized delta so they stay strictly increasing.
- **Channels and the holdback.** Each text or argument stream is a channel (Messages per content-block `index`; Responses per `(output_index, content_index)` for text and per `output_index` for arguments; Chat per `(choice, content)` and `(choice, tool call)`), with one holdback each. The holdback is a lazy DFA built from the token grammar (`Rehydrator::pattern`): it holds the longest suffix of the channel that is still a live prefix of a token and emits the rest; a complete token is resolved by the provenance column of the response path (session tokens in text and arguments, dataset tokens in text for trusted requests); the cap is the longest token the grammar allows. A cap, a channel end, or a flush point (a content-block stop, an `…done` event, a `finish_reason`, `[DONE]`, the stream's end) emits the held text as it is in a synthesized delta, so the worst case is an unrestored token. Argument channels restore session originals JSON-escaped.
- **The driver.** `handler.rs` runs a stream on the blocking pool (the engine's work blocks): it reads the upstream body with an idle timeout of 300 s, feeds each event to the `Rewriter`, and sends the output to the client through a bounded queue of 32 events. The task owns the in-flight permit, so a client that leaves frees it as soon as the driver notices (even while the upstream is silent). An event over 64 KiB, counting the largest open argument channel it may end, takes scan permits first and returns them before it waits on the client (the abort on a timed-out wait is in the threat model), and so does an abort's record-only scan of cut-off channels (skipped with a log line when no permits come); one answer holds at most `max_request_bytes`. The driver catches a panic in the body and ends the stream with the wire's abort event.
- **Repeats and the tripwire.** A full-text repeat (`…done.text`, `…done.arguments`, `output_item.done.item`, `response.completed.response.output`) is replaced by what the channel emitted when its raw text equals the raw deltas; a differing text repeat is tripwired and restored whole, and a differing argument repeat aborts. `"block"` mode queues each tool-call channel until its end.
- **Aborts.** An abort sends the wire's own error event (Messages `error`, Responses `response.failed`, a Chat error chunk) with a fixed class and nothing held. An upstream error event is forwarded and ends the stream. Outcomes: completed (`Ok`), aborted (`stream_aborted`, marks the route failing), tripwire block (`blocked`, never failing), client gone (nothing recorded).
- **Seeding.** The terminal event seeds the next turn's cache from the completed answer (text, arguments, reasoning and citation digests), using the seed stamp taken when the request was sanitized; an answer with a tripwire hit seeds none of its text or arguments.
- **Released-block skip.** `ProxyHost::released(sha256)` answers whether `inumakid::released::ReleasedDigests` (HMAC under a per-process key, one hour, at most 65 536 entries, memory only) holds the digest of a tool-result leaf that `sanitize_blocks` released as a passed free-text block under the proxy's profile for a non-check dataset. In `pipeline.rs` a leaf with that digest skips the engine only after a fail-closed re-check (NFC text, every token real, the single step-2 rule, the validated-regex tier on the masked text); a skipped leaf joins the closure like any passed leaf. The threat model lists what the re-check does not cover.

**The chat dataset and the identity seed.** When the proxy is enabled, `inumakid` creates the reserved dataset `inumaki-chat` (kind `chat`, the proxy's profile) at startup. It holds no tokens (sessions do); it exists because activity records and journal rows need a dataset. A dataset whose id starts with `inumaki-` and is not of kind `chat` keeps the proxy `disabled`. The dataset API refuses to create, delete, rotate, sanitize against, or add upstreams to it. The journal holds only the blocks that missed the cache, and a reveal restores dataset tokens through their namespaces while session tokens stay unresolved. The **identity seed** (`inumakid::identity`, read once at daemon start) adds the OS user's values to the chat dictionary: the account's full name, `user.name` and `user.email` from the global git configuration, and, when distinctive, the login name and the home directory's own name. Only the full names and the email also refuse a tool definition that contains them, unless `[proxy] definitions_account_values = "refuse"` adds the login and home directory names. After a restart the gateway loads `inumaki-chat` with the other datasets; this is harmless: it has no upstreams, the status leaves it out, and `/mcp/inumaki-chat` answers `404`.

**Listener and status.** `[proxy] listen` is loopback only, checked at load. The router is wrapped in the same guard as the gateway (`Origin` not in `[proxy] allowed_origins` is `403`, a foreign `Host` is `403`, `Upgrade` is `501`, no `Access-Control-*` header is ever sent). The listener is served next to the control socket and the gateway. A listener that is not listening is not fatal, whether it could not bind or stopped serving (`server::proxy_serve_ended` runs whenever the serve future returns, for any reason): the daemon runs, a harness already pointed at the proxy reaches whatever holds the address (see the chat-route note in `docs/threat-model.md`), and the status reports `bind_failed`, which means "not listening" and claims no cause. `GET /v1/proxy` (control socket only) reports `enabled`, `listen`, `state` (`running`, `disabled`, or `bind_failed`: not listening), one row per route with its served paths and counters, client and OAuth counters, session and cache counts, and the `client_header` that adapters write into harness configuration. Configuration is the `[proxy]` table (`docs/cli.md`).

**Check routes (plan M8-3).** The end-to-end check (M6 spec §8) sends its canary through the proxy on `/check/<id>/<upstream>/…`, on the same listener and behind the same guard. `<id>` is a 128-bit capability (`CheckId`, 32 lowercase hex digits) registered in the proxy's `CheckRoutes` (`CheckRoutes::new(TokenSettings)`; `Proxy::check_routes()` returns the same `Arc` for the proxy's lifetime). The daemon's check module reaches it through `M8Routes` (`crates/inumakid/src/check/proxy_m8.rs`), which `inumakid::server` installs only inside `if let Some(proxy_addr)`, so a proxy that never bound has no check routes. A registration lives for its TTL, clamped to one hour (the check registers for its own 10-minute lifetime), and the id is never logged. A malformed, unknown, removed, or expired id, an unknown upstream, or an unserved path answers `404 not_served` before the body is read. The upstreams `anthropic`, `openai`, and `openai-codex` are served, streaming and not.

- **Request.** The body goes through the same string-leaf rule and is sanitized as one batch with the check dataset through `ProxyHost::sanitize_dataset`. Unlike a normal route, scanned leaves (reasoning, citation, and search-source text) join that batch and are tokenized, because a check route never reaches a provider that verifies a signature. The fail-closed rules of the normal route apply: a blocked block answers `451`, a blocked tool result becomes the placeholder.
- **Upstream and record.** The scripted upstream (M8 spec §12.1) answers in process, so nothing leaves the machine. Before it answers, the registry records the sanitized body without any header: at most 256 bodies of 4 MiB each per id, never evicted. A body refused over those caps, or discarded by a re-registration of the id or by expiry, is counted in `dropped` (readable for an hour after expiry). `M8Routes` overrides the trait's default `dropped` of 0 with that count, so the check fails closed on any loss (`crates/inumakid/tests/check_full.rs`, `dropped_bodies_reach_the_check`). Model lists and `count_tokens` are answered from the script and not recorded.
- **Answer.** Restored with `Scope::Check(dataset)`: tokens of the check dataset and its companion folder dataset (`<dataset>-f`) only, never session tokens or another dataset's tokens, with or without the client header. A streamed answer runs through the normal stream driver in restricted mode, and the driver holds the in-flight permit until the stream ends. On every wire, script steps that name a tool the request does not advertise are skipped.
- **Nothing is written.** A check route writes no activity record, journal entry, seed, tripwire record, or route counter, and stores no session. `GET /v1/proxy` counts live registrations in `check_routes`.
- **Only while running.** `POST /v1/check` registers routes only while the proxy reports `running` (`check/proxy.rs`); otherwise the proxy path is `not_checked` with `proxy_unavailable`. The app adds its own check before it runs a harness against them (`docs/threat-model.md`).
