# Plan 4a: final measurement (2026-10-09)

Plan 4a (M4 quality work: surface-form tokens, first-name gazetteer, anchor detector, name linker, service-path and sequence evaluation, `tool_json` track, Kiji evaluation) measured end to end on the reference machine (`macos-aarch64`, Apple Silicon), release build of commit `d06addf` (branch `l3/4a-task9` on main `b02476e`), `INUMAKI_MODELS_DIR` pointing at the pinned models. Every report below is a committed `docs/quality/2026-10-09-4a-after-*.json` (counts, rates, provenance; never text). `scripts/quality-4a.sh` reproduces them, including the opt-in-flag sequence runs (their expected exit 5 is printed, not fatal) and the independent surface-form runs; the baseline gates, `--write-baseline`, and the back-to-back linking-off benches are the separate commands listed at the end; `TABLE_ONLY=1 STAMP=<stamp> scripts/quality-4a.sh` prints a table for an existing stamp.

After these runs, comments next to the two opt-in linking flags in `configs/default.toml` gained the measured rates below; that changes the file's digest (the reports' `provenance.config_sha256` is of the file before the comment edit) but no setting.

The machine ran other build and test jobs at the same time (load average 5 to 25), so the latency columns are not comparable between runs; every other column is deterministic and reproduced the 2026-09-28 `4a-task4` reports to the document.

## Opt-in cross-request linking: measured wrong links

`[linking] surnames_across_requests` and `first_names_across_requests` (both `false` by default) let a bare surname or first name link to a person seen in an earlier request within the recency window. Measured with `--sequences` on each profile, each flag on its own (`--config` with only that line changed). Cells are links / wrong links (labeled docs); the labels are from `crates/inumaki-eval/src/sequence.rs`.

Read: with surnames on, every cross-request surname link in a step naming a *different* person with the same surname was wrong (4 of 4 links, 4 of 34 such steps), and the right-person steps gained 4 links in 23. With first names on, every cross-request first-name link to a person never seen in full was wrong (21 of 21 links in 25 steps), against 13 right links in 23 right-person steps. The labels are built so that the flag links wrongly; the rates say how often the window holds exactly one stale candidate in this corpus, not how often a real mailbox would. In-document and in-batch links (`FullThenBare`) are unaffected (61 links, 0 wrong). Both flags stay off; they are opt-in and link bare names to the wrong person at these rates. Reports: `2026-10-09-4a-after-sequence-<profile>-{surnames,first-names}.json`.

## Latency

`inumaki bench --profile support-email` (200 generated documents, seed 42, release, load average about 5): detect p50 28.7 ms / p95 47.9 ms, process p50 65.2 ms / p95 133.9 ms / p99 159.0 ms (`2026-10-09-4a-after-bench-support-email.txt`). The milestone-3 end state was process p50 29.5 ms on an idle machine; the difference here is machine load, not measured as a regression.

What the anchor detector and the linker cost, measured back to back with `[linking] enabled = false, anchors = false`: on `offline` (no models, so only deterministic stages) detect p50 1.3 → 1.4 ms and 1.6 → 1.6 ms in two alternating pairs (p95 9.5 → 15.0 ms and 9.0 → 12.9 ms). On `support-email` four alternating pairs gave detect p50 differences (default minus off) of +10.9, +12.3, −17.0, and +2.3 ms, the sign depending on which run came first under a changing load; the cost is not resolvable there. Plan 4b owns latency.

## Baselines

All six baseline gates (`support-email`, `strict`, `thorough`, `offline`, `held-out-support-email`, `held-out-strict`) exit 0 against the committed baselines. Compared field by field with the reports:

- `support-email`, `strict`: only `verifier_fn_rate` moved, 0.1788 → 0.1317 (improving). Re-recorded.

- `offline`: mixed. Leak rate 22.21% → 21.72%, accepted leak rate 24.13% → 23.73%, verifier false-negative rate 39.9% → 35.2% improved, block rate 7.98% → 8.47% (165 → 175 documents) worse, inside the gate's tolerance. **Not re-recorded**: re-recording would lock in the worse block rate. The verifier FN improvement on every profile matches the identifier-shaped regex re-scan added after these baselines were written (`2026-09-28` 4a-task4 note in the quality README); that it also explains the offline block increase is likely but was not verified by bisection.
