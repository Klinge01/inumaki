# Plan 1 Task 4: calibration matrix — M4 incomplete, 10.76 pp short of the 1% accepted-leak-rate target

Measured 2026-09-25 on `macos-aarch64` (Apple M4, macOS 27.0), git commit
`abda7e16042befd4159574e085c22c61f23eedc1`, with `scripts/quality-matrix.sh`
(models: `gliner-x-small` `d76b3349…`, `mbert-ner-hrl` `1213fdd4…`; full
provenance is in each `docs/quality/2026-09-25-calibrated-*.json`). 32
variants (2 GLiNER thresholds × 2 PERSON label sets × 2 token-classifier
thresholds) × 2 profiles (`support-email`, `strict`) × 2 corpora (tuning
2 058 docs, held-out 200 docs).

**Selection rule (fixed before looking at the results):**

1. Consider only variants whose accepted leak rate is ≤ 1.00 % on both
   corpora for both profiles.
2. Among them, choose the lowest `support-email` tuning block rate; ties go
   to the lower verifier FP rate, then the lower p50.
3. If no variant satisfies 1, choose the variant with the lowest maximum
   accepted leak rate across the four (profile × corpus) cells.

**Result: no variant satisfies rule 1** — every variant's held-out accepted
leak rate is well above 1 % (best case 4.30 % for `strict`/held-out,
11.76–13.56 % for `support-email`/held-out), so rule 3 applies. **M4 stays
incomplete after this task** (spec §13.1): the shortfall against the 1 %
target for the chosen variant is 11.76 % − 1.00 % = **10.76 percentage
points** on the worst cell (`support-email`, held-out).

## Chosen variant: `g0.5-LB-tc0.5`

`[ner.gliner] threshold = 0.5` (unchanged from the shipped default),
PERSON labels **B** (`person`, `name`, `full name` — `street address`,
`city`, `organization`, `phone number` unchanged), `[ner.token_classifier]
threshold = 0.5` (unchanged from the shipped default). The only actual
change to `configs/default.toml` is the two extra GLiNER PERSON labels.

**How the rule selected it.** No variant meets rule 1, so rule 3: lowest
maximum accepted leak rate across the four (profile × corpus) cells.

| variant | max accepted leak across 4 cells |
|---|---|
| g0.3-LA-tc0.4 | 38.30% |
| g0.3-LA-tc0.5 | 39.44% |
| g0.3-LB-tc0.4 | 13.56% |
| g0.3-LB-tc0.5 | 13.56% |
| g0.5-LA-tc0.4 | 38.62% |
| g0.5-LA-tc0.5 | 39.04% |
| g0.5-LB-tc0.4 | 11.76% |
| **g0.5-LB-tc0.5** | **11.76%** |

`g0.5-LB-tc0.4` and `g0.5-LB-tc0.5` tie at 11.76 % (both hit the maximum on
the `support-email`/held-out cell). The brief's tie-break for rule 2
(lower verifier FP, then lower p50) was applied to break this tie too:
`tc0.5` has a strictly lower verifier FP rate than `tc0.4` in all four
cells (2.35 % vs. 2.49 % on both tuning cells, 30.00 % vs. 30.50 % on both
held-out cells) and an equal-or-lower block rate in every cell, so
`g0.5-LB-tc0.5` wins outright — it is never worse than `g0.5-LB-tc0.4` on
any measured cell.

Labels B (adding `name`/`full name`) is the change that matters: compared
to labels A at the same thresholds (`g0.5-LA-tc0.5`), the held-out accepted
leak rate drops from 32.84 % to 6.30 % (`strict`) and from 39.04 % to
11.76 % (`support-email`), with PERSON recall changing only slightly
(73.9 % → 72.8 % held-out, 81.9 % → 83.4 % tuning — a net wash, not a
tradeoff). Lowering the GLiNER model threshold to 0.3 (so the `strict`
retry could in principle recover a low-scoring name) did not help: at the
same label set it either left accepted leak roughly flat (labels A) or
made block rate much worse without lowering accepted leak further (labels
B, tuning block rate 47.2% vs. 24.0% at g=0.5), consistent with the
brief's background note that a lower model threshold mostly lets more
noise through to the policy layer rather than recovering more true names.

**M4's quality gates (spec §13.1) are not met at plan 1.** The curated
safety suite passes with zero residue for both `support-email` and
`strict` (exit 0). The full corpus and held-out targets are missed on
every axis for both profiles: accepted leak rate, block rate, and PERSON
recall all miss target on both corpora; the held-out corpus additionally
misses the verifier false-positive-rate target (30.00 % vs. 5.00 %) for
both profiles. Per the brief and spec §13.1, this is a recorded, acceptable
outcome of this task, not a fix-it-here result: the targets, the profiles'
`min_confidence`/`escalate_below` thresholds, and the held-out corpus were
not touched to close the gap. M4 remains incomplete; Task 5 keeps the
corresponding CI steps informational.

The held-out corpus's much higher accepted leak rate and verifier FP rate
than the tuning corpus (e.g. `support-email` 11.76 % vs. 3.55 % accepted
leak, 30.00 % vs. 2.35 % verifier FP) shows the generalization gap the
held-out set exists to catch (plan 1 Task 2): a configuration tuned to the
generated tuning family's surface patterns does not carry over to the
second generator family's phrasing, and that gap is now measured rather
than assumed away.
