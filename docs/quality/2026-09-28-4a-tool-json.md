## Diagnosis: shared dataset vs. fresh dataset vs. engine path

Task review flagged the 93–94% via-service block rate as possibly confounded by
`ServiceSanitizer` using one persistent `"eval"` vault dataset/namespace for the whole
300-document run, rather than a namespace scoped to each document. The numbers below (support-email,
tuning family) come from **temporary, uncommitted instrumentation** — a debug branch in
`eval.rs` gated on an env var, replaying each document's blocks through
`inumakid::service::sanitize_blocks` directly and tallying blocked *blocks* (not documents) by
block-path suffix and by `(CheckId, EntityKind label)` — reverted immediately after
(`git diff HEAD` against the implementation commit was empty afterward; nothing here changed
committed code).

### The corrected mechanism

The task's first report attributed the block rate to `{CUSTOMER_ID}`/`{CONTRACT_ID}` restated
in the DE/EN free-text snippet templates. That mechanism is real but marginal: `CUSTOMER_ID`
accounts for 7 of 954 blocked-block-reasons in the shared run and 4 of 369 in the fresh run.
**`PERSON` dominates every run** (779 of 954 shared-run reasons; 359 of 369 fresh-run reasons),
and splits into two distinct, additive effects:

1. **Cross-document known-entity accumulation (the confound the review named) is real and
   large.** Block rate drops 94.00% → 77.00% (blocked_docs 282 → 231, an 18-point / 51-document
   swing) purely from isolating each document's namespace. The clearest evidence: the `from`
   block — the *first* mention of a person in a message, and the block that mints that person's
   own token — blocks **265 times** under the shared dataset and **0 times** under a fresh
   dataset or the engine path. A `from` block cannot legitimately leak a "known entity" from
   itself; it is only flagged because an *unrelated earlier document* in the same run happened
   to draw the same name (`Lists::tuning()` has 50 × 50 = 2 500 first/last combinations against
   ~600 draws per 300-document run — collisions are near-certain by the birthday bound) and left
   it "known" in the shared namespace.

   The likely proximate cause is that today's known-entity rule (`inumaki_vault::known::is_known_kind`,
   `crates/inumaki-vault/src/known.rs`) treats **every** tokenized `PERSON` value as a dictionary
   entry, including a bare single-part name (a lone first name matched in a subject line,
   snippet, or the whole-document JSON text block, with no surrounding surname or email to
   disambiguate it). Plan 4a Task 2 (not yet landed) adds `is_known_entity`, which restricts the
   automaton to `PERSON` entities with at least two name parts specifically because a one-part
   `PERSON` row would otherwise become a full-match dictionary hit that outranks NER for every
   later document — precisely the mechanism this diagnosis observed. Landing Task 2 should
   shrink (not necessarily eliminate) this cross-document effect; it has not been evaluated
   against this track.

2. **Even fully isolated, the within-document rate stays high (~77–79%), and this part is not
   an artifact.** The fresh-dataset via-service run and the engine-path run land within 1.7
   points of each other (77.00% vs 78.67%) and share the identical dominant reason count —
   `(Policy, PERSON): 309` in both. A person's name restated in a low-context field (a bare
   `{PERSON}` in a subject line, or folded into the whole-message JSON text block) is not
   detected/tokenized as confidently there as it is in `from`'s `"{PERSON} <{EMAIL}>"` context;
   the mismatch between "a name this document's namespace/context already knows" and "this
   block's own detection didn't confidently re-find it" is exactly the referential-consistency
   check `GoldSpan.entity` linking was added to exercise. This is the track correctly measuring
   a real gap, not a bug in Task 7's code.

### Controller ruling R12 (accepted, no code change)

The shared, persistent dataset is not a bug in `ServiceSanitizer`: a gateway dataset is
persistent across tool calls in production (the whole point of a vault namespace), so
cross-call known-entity accumulation is real gateway behavior that plan 4a Task 5's
`--via-service` is defined to exercise, not an eval-harness artifact to be engineered away. The
Critical review finding is resolved by disclosure (this document) rather than a code change:
`ServiceSanitizer`'s doc comment now says so explicitly (crates/inumaki-cli/src/commands/eval_service.rs).

## What Task 9 must decide

- **Gates.** The committed block rate (93–94%) is not directly comparable to a "clean"
  per-document number — it is inseparable from cross-document accumulation *by design*, per
  R12. Any gate set from this measurement should be read as "block rate of this track's corpus
  against a `--via-service` run that behaves like a long-lived gateway dataset," not as a
  per-document detection quality number. The isolated numbers here (fresh dataset ≈ engine path
  ≈ 77–79%) are the closer proxy for "how often does one document alone trigger this," should a
  gate ever need that distinction.
- **Whether a per-document-dataset mode is needed.** No such mode exists today and R12 says the
  shared default stays; if a future task wants an apples-to-apples per-document measurement
  alongside the gateway-realistic one, that needs a real (committed) mode, not the diagnostic
  instrumentation used here.
- **Template representativeness.** The DE/EN snippet templates (`DE_SNIPPETS`/`EN_SNIPPETS` in
  `crates/inumaki-eval/src/tool_json.rs`) and the bare `{PERSON}`-only subject lines
  (`SUBJECTS`) are what drives the within-document 77–79% floor. Task 9 should judge whether
  restating a bare name with no surrounding context in a subject line, or folding it into a
  JSON text block, is representative of real MCP tool traffic, or whether the corpus should be
  softened in a later revision.
- **Plan 4a Task 2's `is_known_entity`.** Landing it (single-part `PERSON` excluded from the
  known-entity automaton) is expected to reduce, but its effect on this specific track has not
  been measured; re-run this track's `--via-service` reports once it lands.

## Follow-up: implausible one-word person spans (engine path)

The engine path's 78–79% block rate (Policy/PERSON 309 of the reasons) came mostly from
model person spans on single tokens that are not names: `Re`, `INBOX`, `Rechnung`, `Ihnen`,
`Invoice`, and message ids (`mm_<hex>`), each scored 0.5–0.65 and so inside the escalation band.
Real tool results add `vip`, `asc`, `desc` (reported 0.55–0.63). `detect::plausible` now drops
**model-found one-word PERSON spans below 0.85** that are machine ids (underscore and digit),
listed tool or mail vocabulary, or lowercase words of three letters or fewer, unless they are
first names or ambiguous names. Multi-word spans, anything with digits or punctuation, and
every other detector pass through.

| Profile       | Family | Path   | Accepted leak | Block rate | Pass/Docs |
|---------------|--------|--------|--------------:|-----------:|----------:|
| support-email | tuning | engine | 0.00% (0/235) | 21.67%     | 235/300   |
| strict        | tuning | engine | 0.00% (0/234) | 22.00%     | 234/300   |

Reports: `2026-09-28-4a-tool-json-engine-after-plausible-{support-email,strict}.json`
(before: 78.67% and 79.00%, above). The mail corpus gates are unchanged (support-email tuning:
PERSON recall 83.38%, accepted leak 3.54%).

What did not work, recorded so it is not retried: dropping on the whole stoplist, on all-caps
words, or on any non-alphabetic span cost real names (`Grace`, `May`, `Hunter`, informal
lowercase surnames such as `illichmann`, `V-…` ids, email handles) and moved held-out leak
from 8% to 34%. Dropping salutations (`Madam`, `Herren`, `Hello`) lowered the mail block rate
from 23.3% to 18.2% but released six documents whose residue sits elsewhere (accepted leak
3.55% to 3.68%); that trade belongs to the Task 9 baseline pass. Lowercase words of four or
more letters (`status`, `pending`) are not filtered; if a model scores them as persons they
still escalate, and the answer is to add them to the listed vocabulary, not to widen the rule.
The via-service numbers above were not re-measured (the filter is in the shared engine, so they
move with it).
