# Kiji (`DataikuNLP/kiji-pii-model-onnx`): a third NER backend, evaluated as sanitizer and as verifier

Plan 4a Task 8 (M4 spec §16.7). Adds a `kiji` `TokenClassifierBackend` kind, pinned in
`models/manifest.toml` (`default = false`), and measures it as a drop-in replacement for the
shipped `support-email` configuration's sanitizer (GLiNER) and verifier (`mbert-ner-hrl`, the
`token_classifier` section) on both corpora. **Not adopted for either role** — see the verdict
below. No change to `configs/default.toml`, the manifest's `default` flags, `NOTICE`, or any
baseline; per the controller's R7 ruling this stays true even though the fixed adoption rule
resolves to "not adopted" anyway, so there is nothing to defer.

## Model facts (confirmed by loading, 2026-09-29)

Revision `a0c9dd2ff9023b63378f67bafa50e33925663219`, Apache-2.0, `model_quantized.onnx`
(66 338 684 bytes), `tokenizer.json` (668 844 bytes), `label_mappings.json` (2 933 bytes) — all
three hashes verified by `inumaki models verify`. Loading needed none of the contingencies the
brief anticipated:

- **No external-data file.** `model_quantized.onnx` loaded standalone; `model.onnx.data` was
  never referenced. The manifest has only the three roles (`model`, `tokenizer`, `config`).
- **Output names matched the README exactly.** Printed via a temporary diagnostic (not
  committed): `pii_logits` — `Tensor(Float32, [1, -1, 53])` — and `coref_logits` — `Tensor(Float32,
  [1, -1, 7])`. `OutputSelect::Named("pii_logits")` resolves on the first try; the
  keys-based fallback in `run()` is untested by this model but stays in place for a future
  export that renames its outputs.
- **Inputs**: `input_ids`, `attention_mask` — both `Tensor(Int64, [-1, -1])`, **no
  `token_type_ids`** (DistilBERT), matching the existing `Feed` enum without changes.
- `label_mappings.json`'s `pii.id2label` has 53 dense BIO labels (`0`..`52`) plus the `-100:
  "IGNORE"` sentinel, which `read_kiji_mappings` skips per the brief.
- The spec's "CRF/Viterbi" (§16.7) does not match the published artifact: decoding here is
  plain arg-max over `pii_logits`, no transition matrix, confirmed by the README and by the
  53-wide flat output shape (a CRF head would need paired transition parameters, not a bare
  logits tensor). Task 9 corrects the spec text; this file just flags the discrepancy.

## Evaluation as sanitizer and as verifier

`scripts/kiji-eval.sh` builds `inumaki-cli` in release mode, layers a temporary config
(`configs/default.toml` plus `[ner.kiji]` and the `kiji-verifier`/`kiji-sanitizer` profile pairs
from the brief, verbatim) on top of the shipped one, and runs `eval`/`eval --held-out`/`bench`
for `support-email`, `kiji-verifier`, and `kiji-sanitizer`. Measured on `macos-aarch64`,
`cargo build --release -q -p inumaki-cli`, `INUMAKI_MODELS_DIR="$HOME/Library/Application
Support/inumaki/models"`, 2026-09-29. The machine was heavily loaded by other concurrent lane
processes during this run (10 logical CPUs, multiple `rustc`/`inumaki eval` jobs from other
worktrees running at the same time), so **the latency column here is not comparable to the
shipped baseline's own measurement** — `support-email`'s own re-run this session (p50 96.7 ms
tuning / 146.3 ms held-out) is roughly 2× the checked-in `docs/quality/2026-09-28-4a-before-*.json`
numbers (p50 52.3 ms / 59.6 ms) purely from contention, not from any code change. All the other
metrics below reproduced the checked-in baseline closely: `support-email` tuning matched
`docs/quality/2026-09-28-4a-before-support-email.json` on every count field except one verifier
false positive (49 vs. 48 — a single-document difference, not traced further, does not affect the
verdict below); `support-email` held-out matched `…-before-held-out-support-email.json` exactly.

## Adoption rule (fixed before looking, from the brief)

**As verifier** (must hold on **both** corpora): accepted leak rate not higher, verifier
false-negative rate lower, clean false-positive rate not higher, block rate not more than 2
points higher.

- Tuning: accepted leak 2.92% ≤ 3.55% ✓; verifier FN **20.3% > 18.2%** ✗; verifier FP **8.9% >
  2.4%** ✗; block 23.32% = 23.32% ✓.
- Held-out: accepted leak **18.49% > 11.76%** ✗; verifier FN **23.7% > 20.4%** ✗; verifier FP
  27.0% ≤ 30.0% ✓; block 27.00% ≤ 32.00% ✓.

Two of four conditions fail on tuning, two of four fail on held-out (not the same two).
**Not adopted as verifier.** Kiji is not a stronger independent re-scan than
`mbert-ner-hrl` here: it raises the verifier's own false-negative and false-positive rates on at
least one corpus each, and its accepted-leak rate is actually worse on held-out.

**As sanitizer** (must hold on **both** corpora): PERSON recall at least 2 points higher,
accepted leak rate not higher, block rate not higher.

- Tuning: PERSON recall **57.3%, i.e. −26.1 points vs. 83.4%** ✗; accepted leak 0.00% ≤ 3.55% ✓;
  block **98.54% ≫ 23.32%** ✗.
- Held-out: PERSON recall **44.5%, i.e. −28.3 points vs. 72.8%** ✗; accepted leak 0.00% ≤ 11.76%
  ✓; block **99.50% ≫ 32.00%** ✗.

**Not adopted as sanitizer**, decisively, on recall alone: PERSON recall regresses by roughly
26–28 points instead of improving by 2. The block-rate column cannot be read against
`support-email`: the `kiji-sanitizer` profile uses `gliner_verifier` as its verifier, and that
verifier configuration already blocks 1 947 of 2 058 tuning documents (94.6%) with GLiNER as
the sanitizer (`2026-09-28-4a-before-thorough.json`). Kiji pushes it to 98.5% / 99.5%
(30 of 2 058 tuning documents and 1 of 200 held-out documents pass). The accepted-leak rate is
0% only because almost nothing is accepted. The residual few points of block rate are consistent
with Kiji's lower recall leaving names for the verifier to catch, but that was not traced.

The `kiji-sanitizer` rows' verifier FN 0.0% / FP 98.3% and 99.0% are **not** a Kiji effect either.
The clean-candidate trials (`verifier_clean_trials` in `inumaki-eval/src/metrics.rs`) tokenize
the *gold* spans directly and never run the sanitizer under test, so Kiji's recall cannot move
them. They come from `gliner_verifier`: the checked-in `thorough` report shows the same
near-zero FN and near-100% FP (2011 of 2045 clean trials flagged, 98.3%). That is a pre-existing
calibration defect of that verifier configuration (it rejects almost every candidate, clean or
not), open and out of scope here.

**Verdict: adopt = no, for both roles.** The numbers above go into the engine spec §7 in Task 9
regardless (per the brief); no configuration, manifest `default`, or baseline changes are made
here.

## Adaptations from the brief's literal code

- **`run()`'s output-selection code differs from the brief's snippet**, because it does not
  compile against `ort` 2.0.0-rc.13 as written: `SessionOutputs::iter()` yields `(&str,
  ValueRef<'x>)` (an owned view type), not `(&str, &DynValue)`, so `outputs.get(name).or_else(||
  outputs.iter().next().map(|(_, v)| v))` mismatches types (`Option<&DynValue>` vs.
  `Option<ValueRef<'_>>`) and fails to type-check. The landed code instead falls back through
  `outputs.keys()` (whose `Item` is `&'r str`, confirmed in the same vendored source) into
  `outputs.get(key)`, which stays `Option<&DynValue>` throughout:
  ```rust
  let logits_value = match self.output {
      OutputSelect::Named(name) => outputs.get(name),
      OutputSelect::First => None,
  }
  .or_else(|| outputs.keys().next().and_then(|k| outputs.get(k)))
  .ok_or(ModelError::Inference)?;
  ```
  Behavior is identical to the brief's intent (named lookup, then the first available output);
  only the expression shape changed. `merge_adjacent`'s adjacency check was also written as a
  nested `if let` rather than the brief's `if cond && let Some(rule) = …` (a let-chain), since
  let-chains are not yet stable on this toolchain.
- `load_with_tags` (the brief's factored-out shared body of `load`/`load_kiji`) was kept private
  (no `pub`) since nothing outside the module needs it; the brief did not specify visibility.
- `LabelSource` is added exactly as specified in the brief's interface contract but is not wired
  into any branching logic — `load`/`load_kiji` already select the label source implicitly by
  which reader function they call (`read_config` vs. `read_kiji_mappings`), so the enum
  documents the distinction for a reader rather than driving code. Left as public dead-ish API
  per the brief's literal `Produces` list; no clippy warning results since it's a public item
  of a library crate.
- `crates/inumaki-core/src/config.rs`'s `ProfileConfig.ner_sanitizer` doc comment was updated to
  list `kiji` alongside the other section names, for accuracy; not requested explicitly but
  trivial and in scope of the file already being touched.
